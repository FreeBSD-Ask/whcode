# 02 需求工程

需求不是愿望清单，而是**可验证的假设**。每条需求都必须能被证伪、被追溯、被验收。

## 1. 需求分类

- **FR（功能需求）**：系统必须提供的行为或能力；
- **NFR（非功能需求）**：性能、可靠性、安全、可维护性、可移植性、资源上限等质量属性；
- **约束**：平台、工具链、许可、法规、预算等不可协商条件；
- **非目标**：明确不做的事项，必须逐条列出。

## 2. FR 模板

```text
编号：FR-XXX
标题：
优先级：P0/P1/P2
来源：（用户原话/Issue/法规/测量）
描述：系统在什么条件下必须做什么。
输入/前置条件：
输出/后置条件：
失败路径：失败时返回什么、是否可重试、状态如何标记。
验收判据：可执行的二值判据（Given/When/Then 或命令+期望输出）。
证据位置：测试/产物/日志路径。
归属：里程碑/版本。
证伪条件：什么结果会证明这条需求判断错误。
```

## 3. NFR 模板

```text
编号：NFR-XXX
指标：RSS/CPU/延迟/吞吐/句柄/线程/包体/可用性/恢复时间……
目标值：数值 + 单位 + 分位数（p50/p95/p99）。
测量条件：OS/硬件/编译类型/工具链/依赖版本/参数/数据规模/采样窗口/脚本。
承担者：谁负责测量、谁承担不达标的后果。
失效条件：平台/负载/版本变化时何时重测。
```

没有测量条件的 NFR 视为未定义。

## 4. 需求质量判据

1. **可判定**：验收结果只有“通过/不通过”，没有“基本完成”；
2. **可追溯**：FR ↔ 任务 ↔ Check ↔ 测试/证据 四方可达；
3. **无实现绑定**：需求描述“做什么”，不规定“用哪个库/哪个函数”（架构约束除外，须 ADR）；
4. **可证伪**：每条需求写明什么结果会推翻它；
5. **边界明确**：包含失败、超时、取消、并发、权限拒绝等路径；
6. **无孤儿**：没有被任何任务/Check 覆盖的需求；也没有无需求来源的任务；
7. **时效**：标注假设、适用范围与复审日期。

## 5. 追溯

最小闭环：

```text
来源 → FR/NFR → 任务 → 验收 Check → 测试/证据
```

抽查方法：

- 随机取 3 条 FR，沿链路找到测试与证据；
- 随机取 3 个任务，反向找到需求或缺陷来源；
- 随机取 3 个 Check，确认其判据可执行；
- 发现断链时，修需求/任务/Check，不得只补文档说明。

## 6. 需求变更

1. 提出变更：原话、动机、影响范围；
2. 影响分析：FR/NFR、任务、Check、测试、文档、平台矩阵；
3. 记录：ADR 或决策台账（含日期、批准人、替代方案）；
4. 用户批准：范围、优先级、验收标准变化必须由用户签收；
5. 更新基线：规格、任务、Check 同步；旧结论标注“修订前证据”；
6. 复审：变更后重新跑相关门禁。

## 7. 需求反模式

- 把“最佳实践”“行业标准”当需求；
- 用形容词代替指标（“快”“稳定”“安全”）；
- 只写成功路径，不写失败/取消/超时；
- 用实现方案冒充需求（“使用 Redis”不是需求）；
- 把未验证的假设写成事实；
- 需求数量很多但没有一条能验收。

## 8. 需求检查清单

- [ ] 每条 FR 有编号、优先级、描述、验收判据、证据位置、归属、证伪条件；
- [ ] 每条 NFR 有指标、目标值、测量条件、承担者、失效条件；
- [ ] 非目标逐条列出；
- [ ] FR ↔ 任务 ↔ Check 无断链、无孤儿；
- [ ] 失败路径与边界条件已覆盖；
- [ ] 变更均有记录与批准；
- [ ] 文档标注假设与复审日期。
