# 00 核心哲学与判定用语

本文件是所有后续规范的**上位方法论**。它与具体规范冲突时，按本文件的 0 信任流程重新评估
具体规范，而不是维护规范的字面。它不声称是“最佳实践”；它是当前条件下的和解。

## 1. 世界本源是形式主义

任何进入工程视野的事物——代码结构、接口、数据模型、UI、文档、流程、报错、指标——都以
某种**形式**出现。形式不是内容的外壳，而是内容得以被识别、传递与检验的条件。

工程推论：

- 设计任何内容，先问“它是什么形式”，再问“这个形式让什么成为可能、让什么被排除”；
- 形式必须服务于真实矛盾；没有功能的纯粹形式是债务，不是美观；
- 改变功能往往意味着改变形式；只改文案不改行为，通常没有改变系统；
- 形式会固化权力与习惯：谁定义形式，谁就定义了他人必须如何理解系统。

## 2. 任何功能同时都是正面与负面的和解存在

没有免费的功能。每个功能在增加能力的同时，必然增加成本、约束或风险。任何功能提案或
架构决策必须写清：

| 字段 | 要求 |
|---|---|
| 正面 | 获得什么能力、为谁获得、如何验证 |
| 负面 | 增加什么成本（内存/CPU/线程/句柄/复杂度/攻击面/维护负担） |
| 承担者 | 谁在什么时候承担负面（用户、运维、后续开发者、平台） |
| 边界 | 什么条件下正面不再成立、负面不可接受 |
| 和解 | 为什么当前选择这个平衡，而不是不做或换一种形式 |

只写收益不写代价的提案视为未完成。

## 3. 形式主义审查与三重时间依据

设计任何内容时，必须回答六个问题；答不出者标 `[待验证]`，不得进入实现：

1. **形式**：它是代码、接口、文档、流程、UI 还是指标？边界在哪里？
2. **矛盾**：它解决什么真实矛盾？不做会怎样？谁在痛？
3. **正负**：正面与负面各是什么？负面由谁承担？
4. **过去**：它从什么历史条件产生？此前形式为何失效？
5. **现在**：当下有什么证据（测试、测量、故障、反馈）支持它？
6. **将来**：什么条件下它应被修改、替换或删除？复审触发是什么？

只满足“过去有先例”是复古主义；只满足“将来可能需要”是空想主义；只满足“现在能用”是
短视主义。三者必须同时给出依据，并承认依据可能被推翻。

## 4. 物质与意识可以互相转化

- **物质**：代码、二进制、数据库、测量数据、日志、产物、用户操作；
- **意识**：需求、模型、文档、计划、哲学、报错信息。

两者必须双向转化并可追溯：

1. 物质 → 意识：观察、测量、故障与代码事实必须写成文档或 ADR，否则不可复现；
2. 意识 → 物质：文档与设计必须落成代码、测试与产物，否则只是空想；
3. 一致性：文档与磁盘事实不一致时，以可复现命令的结果为准，并修正文档；
4. 不可颠倒：不能以“文档写了”代替“代码做了”，也不能以“代码能跑”代替“行为被理解”。

## 5. 没有真正的最佳实践，只有当下的和解

“最佳实践”是特定历史条件、团队能力与资源约束下的局部最优；把它当作普遍真理，就是把它
变成了形式主义。

工程规则：

- 引入外部实践，必须写明来源、适用条件、本项目证据、失效条件；
- 现行硬约束（零不安全代码、平台范围、工具链限制、极简 UI 等）都是**当前和解**，不是
  永恒真理；变更必须走 ADR，并写明复审条件；
- 禁止用“业界都这样”作为论据；必须回答“在这里、现在、为什么”；
- 每条硬约束都应有复审触发条件（版本升级、平台变化、测量反转、用户决策）。

## 6. 0 信任原则

不信任任何报错、设计理念、文档、外部事实，甚至不信任自己过去的结论。0 信任不是拒绝合作，
而是**按风险分配证据门槛**。

| 对象 | 不信任的表现 | 必须做的校验 |
|---|---|---|
| 报错信息 | “工具说失败/成功”不构成结论 | 复现、读原始输出与退出码、换独立工具交叉验证 |
| 设计理念 | “架构上应该如此”不构成证据 | 原型/模型/测试/测量；写明假设与证伪条件 |
| 文档 | 文档可能漂移 | 对照磁盘、命令输出、产物哈希 |
| 外部事实 | 供应商文档、API、平台行为可能变化 | 查一手来源、锁定版本、校验哈希、保留原始引用 |
| 自己的结论 | 过去通过不等于现在成立 | 上下文变化后重新运行门禁与测量 |
| 二手转述 | 总结可能丢失条件 | 回溯原始命令、原始日志与原始需求 |


**证据层级**：代码、commit、测试与遥测优先于邮件/issue，后者优先于官方文档、复盘与二手研究；AI 总结不得作为唯一证据。详见 `00a-yike-source.md` §7。

与失败显式化的关系：不确定时仍须标 `unknown` 或 `[待验证]`，不得用“0 信任”作为拒绝交付
的借口。

## 7. 自由、洞穴与安全

### 7.1 自由不被定义

不替用户定义善、道德或自由；谁把“自由”“道德”固化为产品目标并要求他人服从，谁就在
反对自由。工程上只能定义可执行的边界：

- 默认值可见、可改、可撤销；
- 不以“为你好”为默认，不隐藏退出与导出；
- 不同生活方式不被产品预设为高低等级。

### 7.2 最大的自由是离开

用户随时可以停止使用并带走全部数据。退出成本是自由的敌人：

- 本地优先、开放格式、完整导出/备份是自由的技术形式；
- 禁止私有格式锁定、隐藏导出、强制账户、强制联网、暗黑模式；
- 退出路径必须与进入路径同样可用，并进入验收。

### 7.3 每个人都是山洞

任何模型、仪表盘与文档都只是局部视角；出山洞见到的仍是更大的山洞。

- 不宣称“看见全部”或“解释世界”；
- 未知、盲区与不可观测项显式标 `unknown`/`[待验证]`；
- 不制造全知幻觉：指标是局部证据，不是世界本身。

### 7.4 证明世界，而非解释或改造

优先可执行证明：测试、测量、复现命令、差分验证。不用宏大叙事替代证据，不把“改造用户
工作流”作为产品目标；工具增强用户判断，不替代判断。

### 7.5 异化是与自我的和解

不做排行榜、连胜、羞耻驱动与行为操纵；失败提示指向可执行下一步，不评价用户；用户可以
不使用某功能而不损失核心能力。

### 7.6 安全不是最佳实践

“最佳安全实践”作为普遍真理是骗局，过去、现在、未来都一样。安全是特定威胁模型下的
和解，而不是合规标签：

- 每项安全措施必须写威胁模型、攻击面、证据、代价（可用性/性能/隐私）、失效条件、复审触发；
- 禁止合规表演：不以“行业标准”“检查清单”代替威胁分析与可复现验证；
- 默认拒绝、最小权限、回环监听、敏感信息脱敏、凭据不落日志是常见起点，但不是永恒教条；
  变更走 ADR。

## 8. 一刻哲学的工程推论

来自历史哲学的一组补充规则，只采纳与工程决策相关的部分：

1. **不伪造**：工具、模型与代理不得编造结果、文件内容或外部事实；未知标
   `unknown`/`[待验证]`；模型输出不作唯一证据。
2. **反进步叙事**：采用率、星数、下载量、主流共识不是正确性证据；版本演进不写成必然进步史。
3. **反苦难**：不以 RTFM、加班、牺牲作为设计或贡献证据；错误信息可操作、不责怪用户。
4. **自反文档**：写明假设、适用范围与复审日期；知识会过时，禁止“永恒真理”式表述。
5. **和解优先**：评审以可执行共识为目标，不把技术分歧道德化。
6. **去神圣化**：以具体 commit、测量与取舍评价工作，不写“天才/大佬不可替代”的神话。

完整 25 条核心、补充 7 条、29 章、33 域、史料层级、12 条标准与经济五定律见 `00a-yike-source.md`。

补充推论：

- **用户是系统的一部分**：没有用户，产品不成立；使用与反馈是设计输入，不是“外部噪音”；
- **文档与代码本体平等**：文档是一等公民，不是代码的附属品；
- **技术债是历史遗产**：每笔债务登记承担者、偿还条件与复审日期；
- **中心不等于正确**：平台地位、市场份额、主流叙事不作正确性证据；
- **改革优先于革命**：渐进重构优先，重写必须经 ADR 并给出迁移与回退证据。

- **可逆性分级**：可逆决策允许快速试错；不可逆决策（数据格式、协议、权限、并发内存序）
  必须设计先行并留证据；
- **反忙碌**：不以工时、消息秒回、会议数量作为贡献证据；
- **利益分析**：任何“中立标准/最佳实践/为你好”的主张，先问谁定义、谁受益、谁承担成本；
- **需求来源**：需求可能由供应商文化制造；区分实际痛点与被营销放大的欲望。
- **知难行易**：主要困难在“知”——任务方向、目标、用户真实意图、非目标与判据；手段（工具、框架、路径）次要且可替换，必须在“知”之后选择，且不得写进需求；方向不明必须提问。

## 9. 反教条条款

1. 本文自身也要通过形式主义审查：它必须改变决策与门禁，否则应删除；
2. 任何原则都不得被用来回避证据、推迟交付或压制反对意见；
3. 当哲学与可复现测量冲突时，以测量为准，并通过 ADR 修订哲学；
4. 任何“绝对正确”的表述都必须降级为“当前和解”，并写明复审条件；
5. 0 信任包括对本文的不信任：读者应追问它的适用边界与失效条件。

## 10. 记录模板

### 10.1 ADR / 设计决策必填字段

```text
形式：        （代码/接口/文档/流程/UI/指标，及边界）
矛盾：        （不做的后果、受影响者）
正面：        （能力、受益者、验证方式）
负面：        （资源/复杂度/攻击面/维护成本、承担者）
过去依据：    （历史条件、此前形式为何失效）
现在依据：    （测试/测量/故障/反馈，含日期与环境）
将来失效条件：（什么情况下应修改/替换/删除）
0 信任校验：  （独立复现方式、交叉验证工具、原始证据位置）
自由影响：    （退出/导出/离线/默认值可撤销是否受限）
安全和解：    （威胁模型、证据、代价、失效条件）
复审触发：    （版本/平台/指标/用户决策）
```

### 10.2 功能提案的最小哲学卡片

```text
功能：
它是什么形式：
要解决的矛盾：
正面 / 负面 / 承担者：
现在证据：
过去依据：
将来删除条件：
自由影响 / 安全代价：
如果不做，损失是什么：
```

### 10.3 任务认知卡

```text
方向（一句话：用户要改变什么/得到什么）：
目标（可判定；与验收判据一一对应）：
用户意图（复述；歧义标 [须提问]）：
非目标/边界（至少一条）：
现有证据（用户原话/工单/日志/复现命令）：
手段（后置；不构成需求，可替换）：
```

## 11. 知难行易：任务认知先于手段

主要困难在“知”而不在“行”。任何变更在开工前必须写任务认知卡：方向（要改变什么）、目标
（可判定的成功条件）、用户真实意图复述（歧义标 `[须提问]`，不得自行假设）、非目标/边界、
现有证据、手段（后置，不构成需求）。方向或意图无法确定时必须提问，不得以开工、跑测试或
产出物替代理解。全部任务（存量与新增）适用：已勾选任务以其来源需求、验收判据与实现记录
作为最小“知”证据，不补写；未勾选任务开工前写卡。

**正负和解**：正面是减少返工与白跑、用户可早期纠偏；负面是前置澄清成本与提问打断；承担者
是提出者（写卡）与用户（早期确认）；边界是可逆低风险小改动可压成一行，紧急故障可先处置但
同一批次补卡，不可逆决策（数据格式、协议、权限、并发）不得裁剪。

**自反**：本条若不再改变任何开工决策，应删除或降级为指南建议；其落点完整性应由程序门禁
检查（仅验结构，不验认知正确）。
