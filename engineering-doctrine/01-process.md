# 01 工程过程与阶段门禁

本文件把 `00-philosophy.md` 落成可重复执行的阶段门禁。门禁不是一次性文档审批，而是每个
增量都可重复执行的最小充分检查。

## 1. 过程模型

采用**迭代增量**：每个里程碑或版本走一遍 G0—G5；范围变化回到 G0，需求/设计变化回到 G1/G2。
禁止跨门禁跳跃：先写实现再补需求、用编译通过冒充运行验证、用未复现的断言改基线，都属于
已发生过的反面案例。

```text
G0 立项与范围 → G1 需求基线 → G2 设计基线 → G3 实现与单测 → G4 集成与验收 → G5 发布与归档
     ▲                              │                              │
     └──────── 范围变化时回流 ──────┴──────── 缺陷修复回流 G3 ─────┘
```

## 2. 门禁细则

### 2.1 G0 立项与范围

| 项 | 要求 |
|---|---|
| 输入 | 用户目标、约束、现有代码/文档、平台与资源限制、风险 |
| 活动 | 界定问题；列出范围内/范围外/非目标；确定平台与验收目标；识别外部依赖与阻塞 |
| 产物 | 范围声明（README/规格）、ADR（范围类决策）、目录边界 |
| 退出判据 | 范围有书面结论；范围外逐条列出；承诺精确到版本/架构/目标；阻塞有登记；代价承担者写明 |
| 评审 | 用户批准；架构角色检查范围与目标是否矛盾；以“找范围漏洞”为目标做对抗式复核 |

### 2.2 G1 需求基线

| 项 | 要求 |
|---|---|
| 输入 | G0 产物、任务书/Issue、运行反馈、缺陷报告 |
| 活动 | 需求获取；冲突与边界分析；FR/NFR 规格化；验收判据；追溯链接；质量审查 |
| 产物 | 规格（FR/NFR）、需求检查表、任务清单、验收清单 |
| 退出判据 | 每条 FR 有编号、优先级、可测判据、证据位置、归属；至少一个任务与一个 Check；未验证项标 `[待验证]`；无实现细节绑定；每条需求有证伪条件；文档标注假设与复审日期 |
| 评审 | 需求工程抽查；AI 反向找“孤儿需求/断链/不可测判据”；用户批准范围与优先级 |

### 2.3 G2 设计基线

| 项 | 要求 |
|---|---|
| 输入 | G1 产物、既有 ADR、平台约束、质量属性 |
| 活动 | 架构与模块划分；数据模型；接口契约；UI 设计；设计原则复核；关键决策 ADR |
| 产物 | 架构/计划、数据模型、契约、模块设计、UI 规范、ADR |
| 退出判据 | 依赖方向明确且可执行强制；跨模块接口有契约与失败语义；状态/错误/schema 有唯一出处；数据所有权与事务边界明确；UI 主题、信息架构、i18n/RTL 与预算明确；关键决策有 ADR；形式主义审查与三重时间依据已记录；并发档案/文献/汇编 ADR 就绪；自由与安全审查已记录；文档自反（形式、矛盾、失效条件） |
| 评审 | 结构门禁/契约核对/文档放置检查；按设计视图清单找缺失；用户批准架构级决策 |

### 2.4 G3 实现与单元验证

| 项 | 要求 |
|---|---|
| 输入 | G2 产物、任务清单、测试位置约定 |
| 活动 | 编码；单元与失败路径测试；静态检查；文档同步；任务状态更新 |
| 产物 | 源码、测试、测试输出、变更记录、模块文档更新 |
| 退出判据 | 格式/静态检查零告警；全量测试通过；新增行为有正向与失败路径测试；结构/目录门禁通过；未完成任务不得勾选；`[待验证]` 不得以推断关闭；测试包含证伪路径；并发实现有模型/差分/压力验证，汇编有回退与差分测试 |
| 评审 | 可执行门禁；PR 清单逐项；AI 按“反例优先”审查；安全/权限/恢复改动必须由用户复核 |

### 2.5 G4 集成与验收

| 项 | 要求 |
|---|---|
| 输入 | G3 产物、验收清单、快速验证指南、基准夹具 |
| 活动 | 集成测试；端到端验证；验收判据逐条判定；证据归档；追溯抽查；安全与性能复核 |
| 产物 | 证据目录（报告、依赖记录、基准、冒烟）、验收清单勾选、执行记录 |
| 退出判据 | 适用验收项有证据；失败项明确记录；追溯抽查通过；已知限制公开；用户验收结论可定位；0 信任复核（换命令/环境/角色）；性能优化有同夹具前后对比；退出路径/完整导出/离线核心能力已验证 |
| 评审 | 证据审计；AI 核对“结论是否超出证据”；0 信任复核；用户签收 |

### 2.6 G5 发布与归档

| 项 | 要求 |
|---|---|
| 输入 | G4 产物、发布范围、已知限制 |
| 活动 | 版本标记；变更记录；发布说明；可复现性核对；归档证据；发布后监控计划 |
| 产物 | 版本标签、变更记录、README、归档报告、已知限制清单 |
| 退出判据 | 标签指向可复现提交；变更记录覆盖本增量；已知限制与未验证项公开；无超出证据的能力声明；用户批准发布或明确“未发布”；已回溯空壳形式并登记复审触发；文档复审日期与过时项已登记 |
| 评审 | 标签与提交哈希核对；发布说明逐句对照证据；用户批准；标签不可改写 |

## 3. 门禁记录的最小字段

| 字段 | 要求 |
|---|---|
| 门禁 | G0—G5 之一 |
| 增量 | 版本/里程碑/变更编号 |
| 输入版本 | 文件路径 + commit 哈希 |
| 角色 | 作者、复核者、批准者分别标注 |
| 判据结果 | 逐条通过/不通过，不写“基本通过” |
| 证据 | 命令、输出摘要、产物路径、环境条件 |
| 未通过项 | 原因、影响、补做任务编号 |
| 形式审查 | 形式、矛盾、正负、承担者；空壳形式不得进入下一门禁 |
| 时间依据 | 过去/现在/将来依据与复审触发 |
| 0 信任 | 独立复核方式与原始证据位置；单一来源不算证据 |
| 自由/安全 | 退出/导出/默认值影响；威胁模型、证据、代价、失效条件 |

## 4. 角色与合并规则

| 角色 | 职责 | 不得做的事 |
|---|---|---|
| 产品负责人（用户） | 范围、优先级、验收与发布批准 | 以口头意见替代需求变更记录 |
| 架构负责人 | ADR、依赖方向、契约、数据所有权 | 绕过 ADR 改变默认后端或平台承诺 |
| 开发负责人 | 实现、测试、失败路径、文档同步 | 把未验证能力写进 README 或验收结论 |
| 测试与质量 | 测试计划、验收判据、证据审计 | 用“测试全绿”替代未执行的验收项 |
| 发布负责人 | 标签、变更记录、可复现性 | 改写已发布标签或删除历史证据 |
| 安全负责人 | 权限、秘密、依赖许可、对外边界 | 以“后续补”关闭安全缺口 |

单人 + AI 代理的合并规则：

1. 角色帽子必须显式声明（作者/复核者/批准者），不得混写；
2. 作者不得单独批准自己的门禁；没有用户批准时记为“未通过”；
3. 能用测试/脚本/契约判定的，不得用文字评审代替；
4. 评审结论必须落到路径、行号、命令输出或产物哈希，不能只写“我看过了”；
5. AI 不是独立评审人；其结论必须可核验，不得作为安全/平台/性能的唯一批准依据；
6. 安全与平台承诺必须人类签收；
7. 冲突时按证据优先；仍不能判定时登记 `[待验证]` 并保留两种说法；
8. 上述机制是补偿控制，不等价于独立评审、外部审计或渗透测试。

## 5. 变更控制

| 变更类型 | 最低影响分析 | 记录 | 批准 |
|---|---|---|---|
| 需求/范围 | FR ↔ 任务 ↔ Check ↔ 测试 ↔ 文档 | ADR 或决策台账 + 规格修订 | 用户 |
| 架构/依赖 | 架构约束、契约、平台矩阵 | ADR + 架构/数据/契约更新 | 用户（平台/安全类必须） |
| 实现缺陷 | 测试、变更记录 | 修复段 | 主开发者（安全类用户复核） |
| 性能基线 | 测量条件、分位数、对比 | ADR/修订记录 + 证据目录 | 用户 |
| 文档/流程 | 链接、目录门禁、编码卫生 | 变更记录（可观察时） | 主开发者 |

## 6. 过程裁剪

裁剪不等于跳过证据：

| 变更类型 | 必须通过 | 可裁剪 | 不可裁剪 |
|---|---|---|---|
| 纯文档 | 目录门禁、EOL 审计、变更记录 | 完整 G1/G2 | 链接与事实可核对 |
| 缺陷修复 | G3 全部门禁；涉及验收语义时补 G4 | 新需求条目（行为未变） | 失败路径测试、变更记录 |
| 需求/范围 | G0/G1/G2/G3/G4 | 无 | 用户批准、ADR、追溯更新 |
| 平台/依赖 | G0/G2/G3/G4 | 无 | ADR、平台矩阵、供应链校验 |
| 紧急修复 | G3；事后补 G1/G4 | 先修复后补文档 | 审计记录、用户知情 |

## 7. 过程自检

1. 门禁产物是否全部存在且可链接？
2. 退出判据是否二值可判（不是“基本完成”）？
3. 未取得证据的项是否明确标注？
4. 变更是否都有 ADR/变更记录？
5. 门禁命令是否全绿？
6. 计数与追溯是否一致（需求、任务、Check 三处）？
7. 结论是否超出证据范围（平台、性能、安全）？

任一项为“否”，不得进入下一门禁。

## 8. 应用反馈循环

采用不是一次性的。每个试点周期：

1. **审计**：按 00—07 对照项目产物，列出通过/缺口；
2. **应用**：只改能改变决策或门禁的项，记录证据；
3. **回流**：把试点中暴露的失效条件写回本目录（新增/修订条款）；
4. **复审**：下一个周期重新审计；不得把“已采用”当作完成。

WHCode 试点暴露的教训：

- 计数会漂移：FR/任务/Check 的声明必须由脚本校验，不能靠手工同步；
- 文档会与磁盘不一致：以可复现命令为准；
- “设计先行”与交付压力冲突时，不得用原型先行绕过；可逆决策可快速试错；
- AI 总结不得作为唯一证据。
