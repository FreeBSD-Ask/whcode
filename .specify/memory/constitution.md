# WHCode Constitution

## Core Principles

### I. 单一持久化基线（Storage Singularity）

DuckDB 是**唯一**默认持久化后端，且一个工作区默认对应一个数据库文件（ADR-001）。全部数据库写入
必须由单一应用层写者服务串行化（ADR-002），经有界队列、幂等键与批量提交完成；同一逻辑变更的任
务状态、关键事件与检查点引用必须在**同一事务**内提交（FR-403）。

不得增加第二个默认后端；未经批准的 ADR 不得以任何平台构建困难为由切换默认存储（§9.1）。`VACUUM`
不得作为磁盘空间回收承诺，空间回收以 CHECKPOINT、空间统计与受控的复制/重建流程为依据（FR-510）。

**理由**：分库与多写者会在任务、事件、检查点之间制造跨库事务边界，破坏可恢复性与审计一致性。

### II. 前端与存储严格分离（Frontend/Storage Boundary）

TUI、CUI、Web 与 SSH **只**依赖应用服务接口（命令／快照／事件），不得直接触库（ADR-003）。SSH 是
独立传输入口，复用同一应用服务，不得每会话各自打开数据库并直接写入（ADR-005）。

**理由**：业务逻辑、权限检查与门禁一旦在各前端分叉，功能对等与可审计性即无法保证。

### III. 独立 Web 形态与业务能力对等（Capability Parity, Not Visual Parity）

Web 是原生 Web UI，通过 HTTP API / WebSocket 访问同一应用服务，**不是** TUI 的 PTY 镜像（ADR-004）。
功能对等按**业务能力**定义：相同能力的行为、权限、状态迁移、错误语义与可审计性必须一致，不要求视
觉或交互方式一致（ADR-009、§4.6）。四端（CUI/TUI/Web/GUI）共用功能能力矩阵，新能力的 API、CLI 行为、权限与测试必须
同 PR 定义（FR-610）。

**理由**：以终端画面或界面外观代替能力，会掩盖权限与状态语义的真实分叉。

### IV. 不承诺跨组件恰好一次执行（No Cross-Component Exactly-Once）

外部工具、文件写入与数据库无法组成一个共同事务，因此系统**不得**承诺 exactly-once（§0.3-8）。外部
副作用一律遵循“意图记录—执行—结果登记”协议（ADR-007）：执行前提交 `prepared` 意图与检查点，启
动后标记 `running`，结束后在同事务登记输出摘要、退出码与副作用凭证。进程在副作用发生后、结果登记
前崩溃时，恢复逻辑不得宣称操作从未发生，须标记 `unknown` 并要求核对、幂等重试或人工决策（FR-410）。

实时广播与持久化写入分离，且**不得**被描述为自动原子双写（ADR-006）；关键事件不得静默丢弃，队列饱
和时须背压、失败返回或触发安全停止。

**理由**：无法证明的 exactly-once 语义会在恢复路径上造成重复副作用或状态谎报。

### V. 不受信任代码一律子进程隔离（Untrusted Code Isolation）

所有运行时（JavaScript、Python、Shell 及其 payload）**必须**在受控子进程中执行（ADR-008）；主进程不
得直接嵌入不受信任脚本执行。子进程默认继承最小化环境变量集合，并受超时、输出上限、取消与可用资源
限制约束；平台不具备可靠内存限制能力时，必须报告“无法强制限制”而非声称已实现（§10.2）。未启用或
未安装的运行时不得加载动态库、占用端口或注册可执行工具（FR-704）。

错误、stderr、模型输出与工具返回均视为不可信数据，不得作为控制指令直接执行（§10.1）。

**理由**：把未验证能力表述为已交付，会把不可靠的资源约束变成发布承诺。

### VI. 平台可构建性与依赖构建分开验收（Buildability ≠ Native Dependency Verification）

平台差异集中封装：无未经封装的平台专有假设，`cfg` 条件编译集中于 `whcode-platform`（NFR-101），
平台依赖与可选功能以 Cargo feature 明确隔离（NFR-102）。Rust target 存在**不等于** C/C++ 依赖、SSH、
终端、TLS 或运行时 payload 已在该平台通过测试（ADR-010）；每个平台的实际数据库构建与运行验证是
M0 退出条件（V-002），不得以交叉编译成功代替运行验证（G-01）。

**理由**：交叉编译通过会制造“多平台可交付”的假象，掩盖依赖构建与运行时的真实平台差异。

### VII. 主张受证据约束（Evidence-Bound Claims）

任何能力主张必须有实测证据：性能数字必须附测量条件（OS、硬件、编译类型、工具链、依赖版本、参数、
数据规模、采样窗口、脚本），不同平台结果不得混为一组平均值，且必须报告分位数而非仅平均值（§5.2
测量纪律、NFR-201—210）。未由实测证明的事项一律标记 `[待验证]`（TBD），不得宣传为已实现能力
（§0.1）。

SDD 门禁必须由应用服务**程序化实施**：门禁失败时拒绝阶段转换；仅向模型追加提示词不构成门禁（G-05、
FR-308）。角色与允许操作由状态机显式注入，不得从历史文本推断（FR-313）。

**理由**：可追踪、可验证、可恢复、指标可复现是本项目的验收基线（任务书 §16 结语）。

### VIII. 原生 GUI 与资源铁律（Native GUI, Bounded Resources）

桌面 GUI **必须**原生渲染或使用原生控件，禁止任何内嵌浏览器引擎的壳层（WebView／WebView2、CEF、
Tauri／wry、Electron、NW.js 等，ADR-026）；Web UI 只作独立浏览器前端，不得充当桌面 GUI。选型按
ADR-027（iced + `tiny-skia` 软件光栅，默认不创建 GPU 上下文）：空闲 1200×800 下 RSS ≤ 96 MB、线程
≤ 24、句柄 ≤ 256、CPU ≤ 0.2% 单核。四套主题（`eink-day`、`eink-night`、`amoled-night`、
`terminal-green`）精确色值见 FR-612/FR-713。窗口最小化或不可见时暂停绘制、动画与轮询，恢复去抖
≥ 250 ms 且单次全量重绘（FR-617）。内存、GPU、线程、句柄四类占用必须可测量；新增任何固定占用须经
ADR，空闲态不得随会话数线性增长（NFR-211）；队列、缓冲、缓存必须有界，文件、套接字、线程句柄一律
RAII（NFR-215）。

**理由**：浏览器壳层与无界资源会把“本地优先”变成不可审计的容器，并在空闲时持续消耗用户机器。

### IX. 自由、退出权与安全反教条（Exit Rights and Security with Evidence）

不替用户定义善/道德/自由；默认值可见、可改、可撤销；用户可随时停止使用并带走全部数据，禁止私有
格式锁定、隐藏导出、强制账户/联网与暗黑模式（philosophy §10、NFR-218）。不做排行榜、连胜、羞耻驱动
与行为操纵。安全措施必须有威胁模型、证据、代价与失效条件，不以“最佳实践/合规”替代分析；默认回环
监听、追踪 `redacted`、凭据不落日志与事件；放宽安全默认值须用户批准并记录 ADR（NFR-219）。

**理由**：把安全与“为用户好”变成不可质疑的默认，会同时侵犯退出权与判断自由。

## Technology & Platform Constraints

- **核心语言**：Rust；工具链、依赖、编译器与 OS 版本在 M0 锁定并写入构建记录（V-001）。
- **目标平台**：唯一验收目标 Windows 11 amd64（`x86_64-pc-windows-msvc`，ADR-013）；不支持任何
  32 位平台；FreeBSD/OpenBSD/NetBSD/DragonFly 全部延后（代码与文档保留，不作验收结论，CI 手工
  触发）；不使用任何 GNU 工具链；Rust 锁定 1.99.1，MSRV 声明 1.99（跟随锁定工具链）。
  支持平台的精确版本与架构必须在发布矩阵公开，不得以“Windows”“BSD”作无限范围承诺（§9.1）。
- **平台差异封装**：见原则 VI。
- **持久化配置基线**：`memory_limit` 默认 192 MB（候选上限 384 MB，仅约束 DuckDB 缓冲管理器）；
  `threads` 初始不高于 `min(4, 可用物理核数)`；`temp_directory` 使用工作区专用目录并检查可写性与
  磁盘余量；`max_temp_directory_size` 提供显式上限；读取连接每查询工作线程独立持有（Rust
  `Connection` 为 `Send`、非 `Sync`）；不在高负载路径无条件强制 checkpoint（§5.4）。以上数值须经
  M0/M1 基准校准，不得写死为架构定理（§0.3-6）。
- **产物格式**：SDD 产物默认保留可读 Markdown，内部解析为版本化结构；不假定上游某一版本的命令、
  模板或插件为稳定 API（FR-303、§4.3）。Markdown 解析器必须报告无法解析段落、重复 ID 与未识别
  字段，禁止静默丢弃（§4.3.3）。
- **命名边界**：受限引擎不得表述为完整生态运行时——Boa 不得称为完整 Node.js；RustPython 不得当作
  完整 Python；Windows Git Bash 与 BSD Shell 是不同能力，不得共用名称伪装等价（§4.7.1、D-08/D-09）。
- **对外契约**：JSON 输出必须含 `schema_version`；错误对象必须含 `code`、`message`、`retryable`、
  `details`；命令与退出码版本化（§8.1、FR-602）。
- **安全默认值**：Web 默认仅监听 `127.0.0.1`，对外监听必须显式启用身份验证、Origin 检查与安全配置
  （FR-606）；追踪默认脱敏，秘密凭据不得以明文写入配置常量、数据库、日志或测试快照（FR-203、§10.1）；
  工具调用按权限白名单执行，破坏性文件操作、任意网络访问、系统级命令与工作区外写入须由策略明确允许
  （§10.2）；SSH 默认仅开放受限 WHCode 入口（FR-608）。
- **原生 GUI 与前端预算**：桌面 GUI 按 ADR-026/027 原生实现，禁止内嵌浏览器引擎；Web 前端无框架、
  无打包器（ADR-014），首屏 JS ≤ 50 KB（gzip）、CSS ≤ 20 KB（gzip）、DOM ≤ 2 000 节点，无 WebGL/
  视频/自动播放/第三方字体；无 JavaScript 时只读视图可用（FR-618）。
- **资源占用**：内存、GPU、线程、句柄四类同时可测量；空闲 1200×800 GUI 的 RSS ≤ 96 MB、线程 ≤ 24、
  句柄 ≤ 256、CPU ≤ 0.2% 单核；不假设 GPU 可用，默认不创建 GPU 上下文；不随会话数线性增长
  （NFR-211、ADR-027）。
- **主题精确色值**：`amoled-night` 背景 `#000000`／前景 `#E6E6E6`；`eink-day` `#FFFFFF`／`#000000`；
  `eink-night` `#000000`／`#FFFFFF`；`terminal-green` `#000000`／`#00FF00`（FR-612/FR-713）。
- **审计**：手动越过门禁、修改 Constitution、清理或压缩数据库、修改运行时配置、执行破坏性工具、权限
  配置变化、数据导出与认证失败的策略性汇总必须记录（§10.3）；审计数据不得随普通会话 TTL 自动清除，
  除非管理员显式设置审计保留策略。

## Development Workflow & Quality Gates

- **交付循环**：`Constitution → Specify → Plan → Tasks → Implement → Converge`，质量步骤为 Clarify、
  Analyze、Checklist（§4.3.1）。这是应用层状态机，非线性五阶段；阶段、门禁与重试策略从版本化工作流
  配置读取。
- **门禁规则**：高优先级未解决澄清项阻止进入 Plan；引用或覆盖检查失败阻止进入 Implement（FR-307）。
  解析失败自动纠偏最多 2 次，仍失败标记 `blocked` 并保留错误与原始产物（FR-309）。Converge 对每条验收
  条件记录 `pass`／`fail`／`not_tested`／`not_applicable` 并附证据引用；失败或未测试项不得使任务静默
  变为完成（FR-310/311）。人工强制放行必须记录 `actor`、`reason`、跳过的门禁、产物版本与时间戳，且
  不得绕过完整性或安全约束而不留审计（FR-312、§8.1）。
- **里程碑纪律**：进入大规模实现前须通过 M0 并冻结平台矩阵、事务边界、Web/SSH 形态与性能预算
  （§12.1、§16）；DuckDB 原生依赖在任一硬目标平台无法构建或运行时，M0 不得通过（V-002、§9.1）。
  不得以未验证的未来能力声称当前阶段完成（R-12）。
- **每个 PR 必须核对**（§15，模板见 `docs/guides/pr-checklist.md`）：需求 ID 与实现范围明确；正向与失败
  路径测试已更新；CUI/API 输出或事件 schema 变化已做版本兼容审查；四端能力矩阵已更新；资源、权限、
  持久化与恢复影响已说明；新的平台限制或依赖升级已更新兼容矩阵；未实现事项被明确标记并写明当前行为。
- **测试与稳定性**：先完成常规功能测试，再运行至少 24 小时稳定性测试；候选发布版本运行 72 小时压力
  测试（§11.5）。测试须覆盖慢客户端、LLM 请求失败、断网、磁盘空间不足、数据库写入失败、重启、终止
  子进程与迁移中断。报告须区分产品缺陷、环境限制与测试工具偏差；不得以“没有崩溃”代替一致性验证。
- **长跑采样纪律**：长跑必须由稳定进程（同一 PID）产生负载并按样本增量落盘，不得只在结束时一次性
  写盘；RSS 斜率、CPU、线程、句柄、库/WAL 大小、事件缺失、失败任务与提交/查询延迟须可归因；未取得
  项标 `null` 并写明原因，不得以 0 冒充（§11.5、NFR-204、`docs/guides/signal-chain-completeness.md`）。
- **实现纪律**：不得以 `Box::leak`、固定线程数或固定批次大小作为普遍优化手段；`SmallVec`、`mimalloc`、
  `jemalloc` 等仅在基准数据支持时采用（§0.3-6、§5.3、D-11）。渲染路径不得执行网络 I/O、阻塞查询或
  长时间工具调用；所有队列设上限并定义满载语义；不得在长历史路径调用等价 `fetch_all` 的无界收集
  （§5.3、§7.3-7）。破坏性命令必须支持 dry-run 或确认机制（§8.1）。
- **需求追溯**：每条功能需求至少关联实现模块、测试用例、验收条件、所依赖 ADR 与未决风险（§15）。
  需求变更必须同步更新任务书、CLI/API schema、功能对等矩阵与测试夹具。

## Governance

本宪法优先于其他开发与评审实践；当其他文档与本宪法冲突时，以本宪法为准，除非存在已批准的 ADR 明确
记录偏离及其理由与替代方案。

- **修订程序**：任何原则的新增、删除或重定义都必须提交书面修订，记录问题、备选方案、影响范围与迁移
  计划，并更新版本号与 `Last Amended` 日期。涉及架构决策变更须先提交并批准 ADR（§2）。修改
  Constitution 本身必须留下审计记录（§10.3）。
- **版本政策**（语义化版本）：**MAJOR**——删除或重定义原则、造成治理上不兼容；**MINOR**——新增原则或
  实质性扩展指导；**PATCH**——澄清、措辞修正与非语义调整。
- **合规审查**：所有 PR 与评审必须验证对本宪法的遵守；新增复杂度必须论证，并说明被否决的更简方案。
  `SHOULD` 级要求的偏离必须在 ADR 中记录理由与替代方案；`MAY` 级能力不得成为核心流程的隐含依赖
  （§0.1）。
- **待验证项治理**：标记 `[待验证]` 的事项在取得实测证据前不得进入验收通过判定；其决策点与责任人记录
  于 `docs/matrices/decisions.md`（D-01—D-12、research.md TBD-01—TBD-10）。
- **文档指引**：运行时开发指引见 `docs/guides/pr-checklist.md`；架构决策见 `docs/adr/`；平台、四端能力与
  运行时矩阵见 `docs/matrices/`。
