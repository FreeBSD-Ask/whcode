# GUI 内存占用分析（2026-10-26）

**问题**：纯 GUI 空闲占用约 59 MB（用户实测），目标是 10—30 MB。本文按测量先行纪律
（NFR-216）给出现场实测、构成归因、软件工程理论分析与可行路径。
**方法**：真实进程采样（`CreateProcess` + `Get-Process`），两次独立启动的 GUI 与一次
`serve --web` 判别实验；单机单样本，不构成预算冻结（V-006）。

## 实测数据（Windows 11，1200×800 默认窗口，空闲，临时工作区）

| 进程形态 | RSS（工作集） | 私有提交 | 线程 | 句柄 |
|---|---|---|---|---|
| `whcode gui`（样本一，12 s） | 105.6 MB | 61.7 MB | 88 | 305 |
| `whcode gui`（样本二，20 s） | 94.0 MB | 60.8 MB | 88 | — |
| `whcode serve --web --tls off`（同库，无 iced） | 56.3 MB | 17.1 MB | 68 | 210 |
| ADR-027 冻结口径的 GUI 实测（历史记录） | 41.1 MB | 17.3 MB | 24 | 244 |

进程映射模块合计 128.6 MB（可共享、按需分页）：`duckdb.dll` 58.5 MB、`whcode.exe`
22.9 MB、shell32 等 OS DLL 次之。GUI 嵌入字体子集共约 8 MB（NotoSansCJKsc 3.5 +
SarasaMonoSC 4.1 + 0.3）。

用户看到的 59 MB 对应**私有提交**（任务管理器默认“内存”列），与本文 60.8—61.7 MB 一致。

## 归因

1. **基座（DuckDB 路径）＝ 私有 17.1 MB、68 线程**。配置是 `SET threads = min(4, 核数)`，
   但 DuckDB 2.0 实际生成 68 线程——调度器规模未按 SET 收敛（待 `SET threads=1` 判别实验
   确认）。这一项已同时突破 ADR-027 的线程预算（≤24）。
2. **GUI 框架栈（iced＋winit＋cosmic-text＋tiny-skia/softbuffer）＝ 私有 +43.7 MB、线程 +20**。
   构成推断：窗口表面（1200×800×4 ≈ 3.7 MB，双缓冲则 ×2）、字形图集与 shaping 缓存
   （cosmic-text 对系统 CJK 字体的缓存）、嵌入字体子集的加载副本（约 8 MB）、帧间分配在
   Windows 堆中的滞留（默认分配器不主动归还 OS，ADR-020 冻结）。
3. **相对 ADR-027 历史实测的回归**：RSS 41.1→94—105.6、私有 17.3→60.8、线程 24→88。
   回归窗口内合入：DuckDB 2.0（ADR-034）、TLS 证书库（ADR-040）、UI 现代化（ADR-041）、
   LLM http feature（ADR-031）。逐项归因需按批次复测，本文先登记总量。

## 为什么“动态加载需要的模块、不需要的及时卸载”不解决问题

1. **动态加载省的是映射，不是工作集**。DLL 代码页是 file-backed、按需分页、可共享：
   空闲时 OS 本来就会修剪它们（Denning 工作集模型——RSS 由时间窗内触碰的页决定，
   而不是“装了什么”）。私有堆（本次的大头）是进程级分配器状态，卸载任何 DLL 都不会
   把堆还给别人。
2. **Rust 没有安全的卸载语义**。安全卸载要求稳定 ABI＋全局状态清算（存活线程、TLS、
   分配器、atexit）；`FreeLibrary` 一个有存活线程或未释放分配的模块是未定义行为。
   项目 NFR-215 禁 `unsafe`、ADR-024 把可选运行时按编译期 feature 门控——动态插件化
   与“内存安全优先”直接冲突。这是内聚/耦合权衡：静态链接用“粒度粗”换类型与内存安全。
3. **GUI 常驻需要的恰恰是大头**。字体、shaping、渲染面每帧都要；DuckDB 可以移出，
   但那是进程拆分（架构决策），不是“加载/卸载”。
4. **卸载的复杂度成本**：插件边界 = C ABI + 版本协商 + 崩溃域 + 逐插件资源核算，
   对单机桌面工具是负收益（形式主义检验：矛盾是“内存”，但“动态卸载”与该矛盾的
   因果链不成立——见 1）。

## 10—30 MB 的可行路径（逐项可判定，须先测量）

- **P0 线程回归（bug，先修）**：定位 68/88 线程来源（`SET threads=1` 判别实验；怀疑
  DuckDB 2.0 调度器按核数生成、不受 SET 约束，或每连接各自成池）。预期省 10—20 MB
  私有（栈提交与线程局部分配）并恢复线程预算。
- **P1 进程拆分（推荐的主路径）**：GUI 进程只保留字体＋渲染＋界面状态，数据经 IPC 向
  后端进程查询。GUI 现状本就不触库（只经 `whcode-app` 快照），拆分与 ADR-018/030 纪律
  一致；需要新 ADR。理论预期：GUI 进程私有回到 ADR-027 历史的 17.3 MB 量级（±字体），
  命中 10—30 目标；“按需加载/卸载”的正确形态是**进程级**起停，不是库级。
- **P2 渲染预算**：glyph atlas 与表面缓冲设上限；脏区重绘减少常驻副本（表面 3.7 MB×N）。
- **P3 字体策略**：嵌入子集约 8 MB，若改走系统字体（ADR-027 修订记录里已验证过
  95.7→41.1 的路径）可再省一截，代价是“无该字体的机器上字形回退”。
- **P4 分配器归还**：ADR-020 冻结默认分配器；若实测证明滞留显著，可提修订。

理论下限估计：Rust 运行时＋iced 最小程序＋系统字体 ≈ 15—25 MB 私有；**10—30 MB 可达，
但 10 MB 一端必须把 DuckDB 移出进程（P1）**，仅靠库级优化到不了。

## 流程要求

当前实测（RSS 94—105.6、线程 88）已超出 ADR-027 冻结预算（RSS ≤96、线程 ≤24）；
按其复审触发条款，应先以官方夹具（`script/measure_nfr_budgets.py`，空闲 1200×800、
AttachConsole 口径）复测确认，再开优化战役与 ADR 修订。本文单机单样本仅作归因输入，
不构成预算结论（V-006）。
