# NFR-204 处置分析：5.5 小时 CI 长跑 RSS 斜率超标（2026-10-25）

- **分析对象**：NFR-204“5.5 小时 RSS 斜率 ≤ 0.5 MB/h”（`specs/001-whcode-harness/spec.md`
  NFR 表；窗口由 ADR-033 定为 5.5 h／300 s 采样；预算值由 ADR-025 冻结）
- **数据来源**：GitHub Actions run `40154046118`，artifact `stability-long-run` 内的 `run.log`
  （本地副本 `local/longrun-40154046118/run.log`），65 个 `sample` 行 + 1 个 `summary` 行，
  65 样本跨度 0.08—5.42 h，测试耗时 19 860 s
- **处置结论**：按现行口径**超预算，不得判为达标**；同时证据不支持“存在泄漏”，且该口径在
  5.5 h 窗口上**不具备判定 0.5 MB/h 的统计分辨力**（§6、§5 对照实验）。最终判定：
  **未判定（口径缺陷）+ 超预算登记**，不得写成“达标”，也不得在无 ADR 的情况下改判。
- **本文件性质**：测量结果处置分析；不含代码改动，不替代 ADR 修订，不构成 Check 通过证据。

## 1. 结论摘要

1. 三条口径都超预算：夹具口径（首末差值）**0.6987 MB/h**、最小二乘 **0.943 MB/h**
   （95% CI 0.504—1.381）、Theil–Sen 稳健斜率 **0.940 MB/h**。预算 ≤ 0.5 MB/h。
2. 超预算的成因**不是**单调增长：序列由“预热爬升（约 +5.9 MB，前 1—2 h）”＋
   “与清理周期（2.33 h）同步的锯齿（σ 3.17 MB，峰谷 30.11—47.32 MB）”构成；
   相位对齐（事件行数对齐）后，后 4.5 h 的世俗斜率只有 **+0.135—+0.161 MB/h**（95% CI 含 0）。
3. 判据上可以排除真实泄漏：线程（22→21，预热后恒 21）与句柄（恒 176）零增长；
   差分序列 lag-1 自相关 −0.555；`Var(y_{t+k}−y_t)` 随 k 不增长（k=1 时 10.56 MB²，
   k=60 时 3.19 MB²），不符合随机游走（泄漏）应满足的线性增长。
4. 对既有材料的**一处更正**：样本 28（2.33 h）与样本 56（4.67 h）不是“重启/进程重置”，
   而是夹具 400 k 清理阈值触发的批量删除（§3），两次降幅 289 720／289 740 行，
   与保留最新 100 k 的 DELETE 语义逐位自洽。
5. 测量纪律有两处硬缺口：**debug（`test` profile）口径**且 summary 记录不含编译类型／OS／
   DuckDB 版本（不满足 spec“测量纪律”条目要求的“必须记录 … 编译类型”）；**夹具未施加产品资源包络**
   （`SET memory_limit`／`SET threads` 只在基准与实验夹具中出现，见 §7）。
6. 推荐**组合处置 D**，顺序为：A′（修夹具保真度与判据定义，不改预算）→ C（带包络的 release
   复测）→ B（经 ADR-025 修订把判据改为可判定的组合判据，而不是调大阈值）。详见 §8—§9。

## 3. 序列结构与一处前提更正

`run.log` 中事件行数只有两处下降，均为清理而非重启：

- 样本 28：391 800 + 10 280（一个采样区间的写入）− 100 000（保留最新 100 k）
  = 102 080，与实测完全一致；
- 样本 56：394 400 + 10 260 − 100 000 = 104 660，同样一致。

清理同时出现 CPU 尖峰（15.78%／15.95% vs 基线 11.2%）与 RSS 局部最大值（47.32／42.11 MB），
即“大批 DELETE 的瞬时工作集”。因此：

- 该点**不是重启点**，剔除“重启点”的斜率没有独立意义（剔除后 OLS 0.938 MB/h，
  变化 −0.005，见 §4 表）；
- 真正的周期性结构是**清理锯齿**：行数 100 k→400 k→100 k，周期 2.33 h，
  与 RSS 的峰谷同步。

进程身份核对：`run.log` 不打印 PID，`pid` 只在 JSONL 样本行中；本次包内无 JSONL，
“单进程未重启”这一点**只能由线程/句柄连续性与事件计数自洽间接支持，标 `[待验证]`**。

## 5. 本地短时对照实验（release，10 分钟）

**目的**：检验 (i) release 口径的 RSS 绝对水平与形状，(ii) 同一“首末差值”口径在无趋势序列上
的误判幅度，(iii) 宿主/资源包络对水平值的影响。

| 参数 | 值 |
|---|---|
| 构建 | `cargo test --release -p whcode-tests --test stability_run --no-run`（`--release` profile，1 m 29 s） |
| 窗口／采样 | 600 s／30 s（19 样本，0.008—0.158 h） |
| 宿主 | Windows 11 10.0.26300，`os.cpu_count()=16`；但进程线程数 81—82，超出部分来源未查清（`[待验证]`） |
| 工作负载 | 同夹具默认（10 万事件／1 万任务，20 事件/500 ms，未触发清理） |

结果（`run.log` 与 JSONL 已按处置要求清理，数值全部记录于此，可用 §9 命令复现）：

| 指标 | 值 |
|---|---|
| RSS 序列 | 68.77, 69.49, 69.51, 65.86, 66.00, 66.03, 67.61, 66.49, 68.35, 67.66, 68.15, 68.48, 66.53, 67.66, 66.85, 66.94, 67.68, 69.45, 69.70 MB |
| RSS 水平 | min 65.86／mean 67.75／max 69.70，**σ 仅 1.27 MB** |
| 夹具口径首末斜率 | **+6.201 MB/h**（summary `rss_slope_mb_per_h`） |
| 最小二乘 | +2.748 ± 6.541 MB/h，CI [−10.07, +15.57] |
| 线程／句柄 | 81—82／恒 228 |
| 事件缺失／failed | 全 0／恒 1 |
| `db_bytes`／`wal_bytes` | 10.5→14.8 MB／0.2—13.5 MB（WAL 随检查点震荡） |

三条可归因结论：

1. **同一口径会把无趋势序列判成 12 倍预算**：RSS 在 ±1.3 MB 内平稳震荡，首末差值仍得
   +6.20 MB/h。说明“首末差值”是噪声放大器，不是斜率估计量；其极端敏感性在 5.5 h 窗口
   同样存在，只是幅度被摊薄。
2. **release 不等于更低 RSS**：本机 release 在 10 万事件处 66—70 MB，而 CI 的 debug 在同样
   事件量处 34—38 MB。差别（约 32 MB）远大于被测趋势（0.5 MB/h × 5.5 h = 2.75 MB）。
   因此“换 release 就能达标”不成立；但“release/包络不统一”确实使 CI 数据无法与其他
   冻结预算（NFR-201／202／210 均在 release 下测得）直接比较。
3. **宿主线程数是强混杂因子**：本机 81—82 线程 vs CI 21 线程，句柄 228 vs 176。夹具从不
   施加 `SET threads`／`SET memory_limit`（§7），DuckDB 按宿主核数自行扩张线程，线程级堆与
   缓冲的工作集随宿主变化。该因果链**尚未直接验证**，标 `[待验证]`，判别实验见 §9。

**实验局限（不得当作 NFR-204 结论）**：10 分钟 ≪ 5.5 h，不覆盖清理周期，不构成任何达标或超标
判定；它只用于口径误判幅度与跨宿主可比性的对照。

## 6. 为什么 5.5 h 窗口判不了 0.5 MB/h（分辨力计算）

用本次序列的噪声结构做设计侧计算（噪声来自工作负载的锯齿与工作集回收，与趋势无关）：

- 预算对应的可观测漂移：0.5 MB/h × 5.5 h = **2.75 MB**；
- 序列自身标准差：**σ = 3.17 MB**（峰谷 30.11→47.32 MB，峰谷差 17.2 MB）；
- OLS 斜率标准误：SE = σ / (√n · sd_t) ≈ 3.17 / (8.06 × 1.54) ≈ **0.25 MB/h**（实测 0.22）；
- 要在 95% 单侧置信下**证明**“≤ 0.5 MB/h”，需观测斜率 ≤ 0.5 − 1.645 × 0.22 ≈ **0.13 MB/h**；
- 要让 0.5 MB/h 的趋势在 2:1 信噪比下可辨，需要 0.5 × T ≥ 2 × 5 MB（半峰谷），即 **T ≥ 20 h**。

结论：**预算与窗口不匹配**。≤ 0.5 MB/h 是在 72 h 窗口下定义的（ADR-025 冻结值即源自
V-006 的 72 h 前提，见 ADR-016 §4）；ADR-033 把窗口缩到 5.5 h（13 倍）并明确“预算值不变”，
但未做分辨力分析。在 5.5 h 内，0.5 MB/h 的可观测漂移小于序列自身的噪声幅度 ——
**无论被测进程是否有泄漏，该口径都无法给出可判定的结论**。这不是“实测偏低就放宽”，
而是“判据与观测窗不匹配”的形式问题。

## 8. 假设与判据

| 假设 | 可区分判据（先声明后检验） | 实测 | 判定 |
|---|---|---|---|
| (a) 预热／分配器与 DuckDB 缓存高水位 | 前 1—2 h 快速上升、其后趋平；时间项在控制行数后衰减 | 前 30 min 均值 32.70 → t≥2 h 均值 ≈38.6（+5.9 MB 电平位移）；t≤1 h 斜率 +7.24；t≥2 h 斜率 +0.027（含清理样本）／+0.244（剔除清理），CI 均含 0；饱和模型边际斜率 2.99→0.56 | **成立（主因之一）** |
| (b) 事件表／索引增长（400 k 阈值下的锯齿） | 周期内 RSS 与行数正相关；清理处出现 RSS 下调＋CPU 尖峰；同相位跨周期水平不升 | 周期内 r = 0.756／0.364（c1/c2），+2.89／+1.02 MB/10 万行；两次清理均 −289.7 k 行、CPU 15.8%、RSS 局部最大；谷值对齐 −0.120 MB/h、峰值对齐 −0.923 MB/h | **成立（主因之一，且有界）** |
| (c) 真实泄漏（连接／缓冲／句柄） | 线程/句柄随时长增长；跨周期同相位水平递增；差分近似随机游走（Var(k)∝k） | 线程 22→21 后恒定、句柄恒 176；相位对齐后周期水平不升（多为负）；Var(1)=10.56 → Var(60)=3.19 MB²（随机游走应为 60 倍）；ΔRSS lag-1 自相关 −0.555 | **不成立（无泄漏证据）** |
| (d) 采样口径误差（工作集 vs 私有字节、宿主差异） | 水平值随宿主/线程数跳变；同代码不同宿主水平差 ≫ 趋势 | 工作集口径（`tasklist`）；本机 release 66—70 MB（81 线程）vs CI debug 34—38 MB（21 线程）；σ 3.17 MB > 预算漂移 2.75 MB；summary 无编译类型 | **成立（口径误差大于信号）** |
| (e) 判据无效力（估计量 vs 窗口不匹配） | 同一估计量在无趋势短序列上给出远超预算的“斜率” | §5：±1.3 MB 平稳序列被首末差值判为 +6.20 MB/h；§6 分辨力计算 | **成立（决定性）** |

排序：**(e) 判据无效力 > (d) 口径误差 > (a) 预热 ≈ (b) 锯齿 > (c) 泄漏（被排除）**。
注意 (a)(b)(d)(e) 相互叠加：即使产品零泄漏，按现行口径仍可能超预算；反之，即使产品有
低速率泄漏，该口径也可能读不出。两者都不能用本次数据判定。

## 9. 处置选项

| 选项 | 内容 | 正面 | 负面／代价 | 失效条件 |
|---|---|---|---|---|
| **A 优化代码** | 降低每行常驻成本（缓冲/行组回收）、缩短清理事务峰值 | 直接减小锯齿幅度，提高信噪比 | 无证据表明存在可优化热点：锯齿幅度由行数×数据页宽与 DELETE 事务决定，属引擎级行为；改分配器须另立 ADR（ADR-020）；工作量大、收益不可预期 | 若把行数上限降到 10 万以下可显著减小振幅，但那是改工作量而非修产品 |
| **A′ 修夹具保真度与判据定义** | ①夹具施加 `SET memory_limit='192MB'; SET threads=min(4,核数)`；②summary 记录编译类型/OS/CPU/核数/引擎版本；③预登记“后预热 + 相位对齐”为主判据；④`--release` 运行 | 成本低（夹具与 workflow 局部改动）；消除 M-1—M-3；使跨宿主与跨预算可比 | 不改预算即不改结论：本次仍登记为超预算 | 若产品真实泄漏，相位对齐估计量仍能捕获（每个周期 +0.375 MB 在当前噪声下已近可辨，多周期可累积） |
| **B 经 ADR-025 修订预算/判据** | 把 NFR-204 改为组合判据：泄漏项＝后预热相位对齐斜率 ≤0.5 MB/h；有界项＝`Var(y_{t+k})` 不随 k 增长且线程/句柄恒定；绝对项＝峰值 RSS 上限；并把“首末差值 0.5—1.0 MB/h”定义为**无权判定**（升级 24 h 深检），>1.0 MB/h 才判违反 | 判据可判定、不掩盖超标、不放大阈值 | 须另立 ADR 并附同夹具前后对比（ADR-025 决策 2）；“>1.0”的边界必须由分辨力推导而非由本次结果反推 | 若 ADR-033 退出条件触发（runner 时限变化/出现长时泄漏证据），判据须重新推导 |
| **C 换 release 口径复测** | 在 A′ 的包络与 release 下重跑 5.5 h | 与冻结表同口径；可区分“debug 放大”与“真实增长” | 消耗一次 5.5 h runner 配额；§5 已表明 release 水平更高（同宿主），不能期待自动达标 | 若复测仍超预算，说明需进 B 或 A，不得再以口径为由拖延 |
| **D 组合（推荐）** | A′ → C → B | 先消除可判定的口径缺陷，再取同口径证据，最后才动判据；顺序不可颠倒 | 需两轮长跑（约 11 h runner 时间） | 任一环节缺证据即停在当步并登记缺口 |

不作为选项的两条（已否决）：

- **直接把 0.5 MB/h 调大到 0.7/1.0 以免超预算**：违反 ADR-025 决策 2“不得修改预算掩盖”，
  且没有任何分辨力或机制依据。
- **把本次结果写成“达标”或“无泄漏”**：首末与 OLS 均超预算；“无泄漏”只有间接证据
  （线程/句柄/有界性），不足以支撑达标结论。
