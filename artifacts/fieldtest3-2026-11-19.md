# 字段测试③：CUI 写类工具链路与授权语义（2026-11-19，ADR-090 取证）

> 任务认知卡：方向＝取证 `--approve` 写链路与未授权现状；判据＝正例（文件逐字产生＋
> 审计事件）与现状行为如实记录；**执行中发现前提失真（见修正节），按 0 信任如实改判**。

## 正例：`--approve workspace-write` 全链（新会话 S-3）

构建：worktree `58764d1`（绕开并行会话在途 WIP）release。提示词要求用 write_file 写
`note.md`。实测：`completed=true`、`iterations=3`、`gaps=0`、4 个工具事件（write 写入
＋读回验证，`duration_ms=13/5`）；**`note.md` 真实产生且内容逐字匹配**；审批决策落审计
（闸门存在且 Allow）。此前无闸门时 CUI 写操作无审计——本批补上了这条通道。

## 现状实证：无 `--approve`（新会话 S-4）

同样写 `blocked.md` 的提示词：**文件同样产生**（模型写入成功，turn 继续）。这与代码
事实一致——闸门检查为 `if let Some(gate)`（turn.rs 通用闸门段），无闸门＝写工具直接
执行（`ApprovalConfig` 默认 write=Allow）。**原“CUI 写类 fail-closed”的前提失真**
（读错了 487 行——该处只管 shell 注册——与 1918 行——只管计划模式退出）。

执行中发现并修复本批自身缺陷：clap `default_value=""` 使缺省时产生空串范围被解析器
拒绝（任何不带 `--approve` 的 `llm run` 都报“未知授权范围”）——已修（空项＝未授权，
跳过），该负例恰好抓住了它。

## 四端“写”姿态对照（诚实盘点）

| 前端 | 写工具执行 | 审计 |
|---|---|---|
| TUI/GUI | 执行（闸门规则默认 Allow） | 有（闸门落审计） |
| CUI（本批前） | 执行 | **无**（无闸门） |
| CUI（本批后 `--approve`） | 执行 | **有**（闸门 Allow 落审计） |
| CUI（本批后无 `--approve`） | 执行 | 无（现状保留） |

**四端在“写”上事实对称（都执行），不对称的是审计**。是否统一为“所有前端写类调用
必须经闸门（至少审计留痕）”是安全姿态决策——显式提交用户裁定，不以默认惯例结项。

## 复审触发

- 用户裁定写姿态后，按裁定口径统一四端（或登记差异为有意设计）；
- `--approve` 的持久化授权配置（自动化高频场景）为后续可选。
