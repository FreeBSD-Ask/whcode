# Phase 0 Research: WHCode — Rust 原生 LLM 编码 Harness

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-10-20

**输入基线**：《WHCode 技术任务书 v3.0》§16 参考资料 [S1]—[S8] 为本项目对依赖能力与语义的核验依据。本文不重新做外部调研：凡任务书已作出架构决定的条目，Decision 记录该决定及其理由；凡任务书标记 `[待验证]` 或设决策截止点的条目，本文不给出结论，只登记候选、判据与决策点（对应 plan.md C-06 门禁：未验证能力不得表述为已交付）。

> **平台范围说明（ADR-013，2026-10-21）**：本文的五平台表述保留为历史研究记录；当前唯一验收目标是 Windows 11 amd64，FreeBSD/NetBSD/OpenBSD/DragonFly 全部延后。凡涉及五平台验收的 Decision 与 TBD，均以 ADR-013 与 `docs/matrices/platform-matrix.md` 为准。

## R-01 Rust 工具链与平台目标矩阵

**Decision**: 工具链版本由 M0 锁定并写入每平台构建与依赖记录；首版优先 `x86_64` 五平台目标（FreeBSD/OpenBSD/NetBSD/DragonFly/Windows），`aarch64-unknown-freebsd` 按需验证、列为扩展目标（D-01）。
**Rationale**: 任务书 §9 明确 "Rust target 的支持等级随工具链版本变化"，须在每次发布时按锁定的 Rust 版本更新平台表（V-001）；Rust target 存在不等于 C/C++ 依赖、SSH、终端、TLS 或运行时 payload 已通过测试（ADR-010、[S6]）。
**Alternatives considered**: 以交叉编译成功代替运行验证——被 §1.1 G-01 明确否决；不锁定版本、跟随 stable——被 V-001 的"锁定 Rust、DuckDB、编译器与 OS 版本"要求否决。
**状态**: 决策已定，执行归属 M0；具体版本号 `[待验证]`（由 M0 基线报告产出）。

## R-02 DuckDB 原生依赖跨 BSD 构建

**Decision**: DuckDB 作为唯一默认持久化后端；五平台原生构建、打开/创建数据库、事务写读、关闭重启与迁移冒烟全部通过是 M0 退出条件；任一硬目标平台失败则 M0 不通过并形成 Go/No-Go 决策。
**Rationale**: 任务书封面约束"未经 ADR 批准不得增加第二个默认后端"；R-01 风险登记为"高"，对策为"固定工具链/编译器，记录补丁与上游状态"；[S1] 说明单进程内并发写与多进程读写限制，[S5] 说明 Rust 连接线程安全属性。
**Alternatives considered**: 预先引入 SQLite/PostgreSQL 作为 BSD 退路——被 §9.1 否决（"不得在默认只有 DuckDB 约束下，未经批准偷偷切换为其他数据库"）；以交叉编译产物代替原生构建验证——被 ADR-010 否决。
**状态**: M0 硬退出条件；结论 `[待验证]`（尚无实测证据）。

## R-03 写入路径与事务边界

**Decision**: 每个工作区一个 DuckDB 文件（ADR-001）；全部写入经单一应用层写者服务串行化（ADR-002），命令携带 `idempotency_key` 与期望状态版本；队列有界；批量提交按"行数上限或时间上限先到者"触发，初始基线 500 行 / 50 ms，须由 M0/M1 基准校准（FR-503）；事务成功后才向调用方返回持久化确认（§7.3）。
**Rationale**: 任务、事件、消息、产物、检查点须在同一事务边界内更新，避免跨库事务；单写者便于有界排队、批量事务、顺序编号、去重与审计（[S1]）。
**Alternatives considered**: 每会话一库（v2.0 原方案）——被 §0.3-2 否决，因产生跨库事务边界；连接池并发分发写入——被 ADR-002 与 §5.4 否决（DuckDB Rust `Connection` 为 `Send`、非 `Sync`，[S5]）；为凑批次而无限等待——被 §7.3-4 否决。
**状态**: 架构决定已冻结；批次参数与写者线程/执行上下文的具体取值属实现期基准调优项（D-06 关联）。

## R-04 事件持久化分级与广播分离

**Decision**: 原始事件持久化与实时广播分离（ADR-006）；事件按三级处理——关键事件（状态转换、请求最终结果、工具意图与结果、门禁结果、强制放行、审计）不得静默丢弃，饱和时背压/失败返回/安全停止；内容事件按追踪级别控制，省略或采样须留可查询标记；展示快照允许合并或丢弃。不得把"实时广播 + 数据库写入"描述为原子双写。
**Rationale**: 广播与持久化的可靠性诉求互斥，单一队列无法同时满足（§4.2 事件可靠性分级）；须处理"广播已发出、写入失败"与"写入已成功、客户端未收到"两种半态（§4.2）。
**Alternatives considered**: 单一队列双写——被 ADR-006 否决；以 2PC 保证广播与库写原子性——广播目标为消费者集合不可变，无对应事务参与者（§0.3-8）。
**状态**: 已冻结。

## R-05 Web 服务端与前端技术栈

**Decision**: Web 为独立原生 Web UI，经 HTTP API / WebSocket 访问同一应用服务，前端状态由同一事件流驱动，不采用 TUI 的 PTY 镜像（ADR-004、D-03）。具体 Web 框架、WebSocket 库与前端构建方式在 M6 前按五平台验证证据确认，当前不表述为已交付能力。
**Rationale**: 功能对等必须基于命令和状态而非终端画面（ADR-004）；§9.1 要求 Web 对外部署使用 TLS 终止、身份认证、Origin 校验、速率限制与最小权限；FR-606 要求默认仅监听 127.0.0.1。
**Alternatives considered**: PTY 桥接 TUI（v2.0 原方案）——被 §0.3-1 明确调整为独立前端；每个前端各持状态源——被 R-04 风险登记与 ADR-003 否决。
**状态**: 形态已冻结，技术选型 `[待验证]`（M6 决策点）。

## R-06 SSH 服务端与 BSD 认证差异

**Decision**: SSH 作为独立传输入口，复用应用服务，不允许每会话各自打开数据库写入（ADR-005）。首版权限为公钥认证 + 受限 WHCode 交互入口，不默认授予任意系统 Shell（D-04、FR-608）。服务端实现选型（内建 Rust SSH 服务 vs 依赖系统 sshd 的受限子系统）在 M0 风险原型（V-004）后定案。
**Rationale**: R-02 风险登记要求分平台集成测试，"不得以单一 FreeBSD 测试代替四 BSD 验收"；M0 须验证公钥认证、终端尺寸、断连与权限边界，无法完成的平台须记录明确阻塞原因。
**Alternatives considered**: 直接复用系统 sshd 的 `force-command`/`subsystem`——优点是不引入新端口与自研认证栈，缺点须验证四大 BSD 的 sshd 版本行为差异；自研 SSH 服务端——可完全控制会话隔离，但增加协议实现面与审计要求；两者均保留为候选。
**状态**: `[待验证]`（M0 原型 → M7 验收）。

## R-07 SDD 产物表示与解析

**Decision**: 默认产物保留可读 Markdown，应用内部解析为版本化结构；不要求上游 Markdown 改为 JSON，也不假设原始 Markdown 是 JSON Schema 文档（FR-303）。每条需求与任务具备稳定 ID 及显式引用（FR-304/305）。解析器报告无法解析段落、重复 ID 与未识别字段，禁止静默丢弃；纠偏重试默认最多 2 次，仍失败标记 `blocked` 并保留错误与原始产物（FR-309）。
**Rationale**: 保持与上游 Spec Kit 概念/产物兼容，同时不假定上游某版本的命令、模板或插件为稳定 API（§4.3）；R-06 风险登记的对策为"版本化解析器、失败保留原文、纠偏次数限制"。
**Alternatives considered**: 直接把 spec/plan/tasks 规范为 JSON——破坏可读性与上游兼容，被 FR-303 否决；以提示词要求模型遵守流程——不构成门禁，被 FR-308 与 G-05 否决。
**状态**: 已冻结；解析器版本与 schema 演进策略为实现期任务。

## R-08 长程任务、检查点与恢复协议

**Decision**: 检查点以增量状态差分与引用为主（FR-402），任务状态变化、关键事件与检查点引用在同一数据库事务内提交（FR-403）。外部工具执行遵循时序：执行前提交 `prepared` 意图与检查点 → 启动后标记 `running` → 结束后记录输出摘要、退出码与副作用凭证并在同一事务登记结果。恢复时加载检查点引用的元数据、产物与上下文游标，完整历史继续按需读取（FR-404）。无法判断外部操作是否完成时标记 `unknown`，要求核对、幂等重试或人工决策（FR-410、ADR-007）。
**Rationale**: 文件系统、子进程与数据库无法组成单一原子事务，故不承诺 exactly-once（§0.3-8）；"进程在副作用发生后、结果登记前崩溃"时恢复逻辑不得宣称操作从未发生（§4.4 检查点时序）。
**Alternatives considered**: 盲目重放有副作用操作——被 R-07 风险登记明令禁止；每步复制完整历史——被 FR-402 否决；轮询独占写者以保证顺序——被 FR-407 否决（轮询须走只读快照）。
**状态**: 已冻结；并行子任务调度为 P1，须待状态与写入一致性测试通过后实现（FR-406）。

## R-09 空间回收与数据库压缩

**Decision**: 不把 `VACUUM` 作为磁盘空间回收保证（FR-510、§4.5 空间回收规则）。`CHECKPOINT` 用于同步 WAL 并可能部分回收已删除数据所占空间；需要显著缩小文件时提供受控的 `db compact`：复制到新数据库 → 校验副本 → 原子切换，含停写、备份与失败回滚（D-10）。清理操作必须有预览、确认、审计与活跃会话保护（FR-509），并记录清理前后文件大小、WAL、已用块与可用块（FR-510）。
**Rationale**: [S3] 说明 `VACUUM` 的基本语义与不保证回收空间的限制；[S4] 说明 `CHECKPOINT`、删除空间回收与通过复制数据库压缩的机制；R-10 风险登记要求"区分行删除、块回收、WAL checkpoint 和文件重建"。
**Alternatives considered**: 以 `VACUUM` 充当压缩承诺——被 §0.3-7 与 [S3] 否决；Windows 文件替换与 BSD 文件锁语义共用一套流程——被 §7.4 否决（须分别测试）。
**状态**: 已冻结。

## R-10 可选运行时的交付方式与能力声明

**Decision**: 运行时不是主进程依赖，一律在受控子进程执行（ADR-008）；统一 Runtime Provider 接口（探测、能力声明、版本指纹、执行、取消、结果归一化，FR-701）；能力等级 `Full`/`Restricted`/`ShellOnly`（FR-702）；payload 独立分发并校验来源、版本、哈希与平台兼容性（FR-703、D-07）。命名与兼容边界：Boa 只作为受限 ECMAScript 引擎，不得称为完整 Node.js（D-08、[S8]）；Python 先验证受控子进程协议与平台解释器再决定是否捆绑（D-09、[S7]）；RustPython 等受限实现须列明不支持的标准库与系统调用；Windows Git Bash 为独立 PortableGit payload，不写死安装体积；BSD Shell 与 `gitbash` 是不同能力，不得共用名称伪装等价（§4.7.1）。未启用运行时不加载动态库、不占端口、不注册工具（FR-704）。
**Rationale**: R-08 风险登记的对策为"明确 capability level、固定兼容性测试、完整运行时采用独立 payload；未验证能力不得出现在 Full 中"；"动态链接 `libpython`"不等于交付完整 Python 环境，`deno_core` 不等于 Node.js 兼容层（§4.7.1）。
**Alternatives considered**: 在主进程内嵌入脚本引擎——被 ADR-008 与 §1.3 范围外否决；把 Boa/RustPython 直接标注为 Node/Python 支持——被 D-08/D-09 与 R-08 否决；运行时随主二进制默认携带——被 D-07 否决（独立 payload、按需安装、支持离线镜像）。
**状态**: 边界与纪律已冻结；是否内置/默认携带/按需下载须在 P1 实现前形成独立 ADR（§4.7.1，决策点 M8 前）。

## R-11 性能实现原则与内存策略

**Decision**: 不将 `Box::leak`、固定线程数、固定批次大小规定为普遍优化手段，改为可配置基线与基准驱动决策（§0.3-6）。`SmallVec`、`ArrayVec`、`mimalloc`、`jemalloc`、Unicode 宽度缓存等仅在基准数据支持时采用；全局分配器默认使用 Rust 系统分配器，仅当基准证明有益后才改变（D-11）。渲染线程只读不可变快照或轻量状态，不执行 LLM 网络 I/O、阻塞查询或长时间工具调用；以脏标记或事件驱动触发重绘；所有队列设上限并定义满载语义；不在渲染帧路径反序列化完整 JSON payload（§5.3）。
**Rationale**: §0.3-6 的直接修订；§5.3 的测量与隔离要求；D-11 的默认值。
**Alternatives considered**: 预先引入自定义分配器以压低 RSS——被 D-11 与 §5.3（"不得以源代码层面的零分配表述替代端到端测量"）否决；`Box::leak` 作为通用长期对象方案——被 §5.3 明令禁止。
**状态**: 原则已冻结；分配器与容器选择的实测结论归属 M9（D-11 决策点）。

## R-12 性能测量纪律与预算冻结

**Decision**: NFR-201—210 保留为候选目标而非承诺。M0 须提供同一版构建、固定硬件与固定数据集的基线报告，据此冻结或修订 §5.2 指标（V-006、D-06）；目标无法达到时先分析热点，再经 ADR 修订目标与架构。测量必须记录 OS、硬件、编译类型、Rust 工具链、DuckDB 版本、数据库参数、数据规模、采样窗口与脚本；不同平台结果不得混为一组平均值；分位数（p50/p95/p99）不得以平均值代替。`memory_limit` 仅约束 DuckDB 缓冲管理器，须另行监控总 RSS。
**Rationale**: §5.2 测量纪律与 [S5]；R-09 风险登记的对策为"固定测试夹具、分别报告平台结果和分位数；指标没有测试条件不得作为发布承诺"。
**Alternatives considered**: 沿用 v2.0 未经验证的内存比例与渲染提速比例结论——被 §0.3-5 删除；以交叉编译通过推断性能——被 G-01/ADR-010 否决。
**状态**: 纪律已冻结；预算数值待 M0 基线冻结。

## R-13 游标、索引与历史注入

**Decision**: 历史查询使用稳定排序键 + 游标分页，不以大 `OFFSET` 作为默认长历史分页路径（FR-504）；游标须能形成稳定全序，不得仅依赖可能重复的时间戳（§7.2）；向前/向后翻页使用明确定义的比较方向。历史注入使用有界迭代，达到字符/token/时间预算后停止并返回截断原因（FR-505）；上下文加载器契约固定为返回 `items + next_cursor + consumed_budget + truncated_reason`（§4.1 约束）。索引与查询计划须经真实基准验证，不规定"所有全表扫描都失败"（§7.2）；查询结果以流式迭代或有界批次处理，禁止等价于 `fetch_all` 的无界收集（§7.3-7）。高频概览使用显式维护的预聚合表，并区分强一致字段与最终一致概览字段、提供重建逻辑（FR-506、§7.3-8）。
**Rationale**: G-04 要求长会话加载成本不随完整历史线性增长；R-05 风险（内存与数据库膨胀）对策为有界 payload 与引用化。
**Alternatives considered**: 时间戳单键游标——重复时间戳导致漏读/重读；UI 层从完整历史切片——被 §4.1 约束明确禁止。
**状态**: 索引集合已建立（T036）。本机 DuckDB 1.5.6 实测：单列索引可用于等值与范围扫描，复合索引未触发扫描；收益待 T054/T055 大规模复测（`artifacts/query-plan-report.json`）。

## R-14 数据库配置基线

**Decision**: `memory_limit` 默认 192 MB（候选上限 384 MB，仅约束 DuckDB 缓冲管理器，须监控总 RSS）；`threads` 初始不高于 `min(4, 可用物理核数)` 且可配置；`temp_directory` 使用工作区专用目录并在启动时检查可写性与磁盘余量；`max_temp_directory_size` 提供显式可配置上限，超限返回明确错误并保护一致性；`preserve_insertion_order` 仅在确认事件查询语义不依赖其默认行为后再设置；读取连接为每查询工作线程独立持有（`Connection` 为 `Send`、非 `Sync`）；写事务由单一写者服务管理；WAL/CHECKPOINT 按阈值、空闲窗口或显式维护触发，不在高负载路径无条件强制 checkpoint（§5.4）。
**Rationale**: §5.4 表格与 [S5]；§0.3-6 要求参数可配置而非写死为"架构定理"。
**Alternatives considered**: 固定线程数与固定批次写死——被 §0.3-6 否决；连接池共享单连接跨线程读取——被 [S5] 与 §5.4 否决。
**状态**: 基线已定，数值须由 M0/M1 压测校准。

## R-15 追踪级别与秘密处理

**Decision**: 默认追踪级别为 `redacted`（D-05，M1 决策点）；提供 `off`/`metadata`/`redacted`/`full` 四级（FR-203）。API Key、访问令牌与运行时凭据不得以明文常量写入数据库、日志或测试快照；`full` 模式须在 UI 警告敏感信息写入并提供访问控制、清理与导出策略；导出与诊断包提供脱敏预览，默认不附带完整提示词与环境变量。错误、stderr、模型输出与工具返回一律视为不可信数据，不得作为控制指令直接执行（§10.1）。
**Rationale**: FR-203、§10.1 与 R-11 风险登记的对策（默认脱敏、权限白名单、最小环境、身份认证与审计）。
**Alternatives considered**: 默认 `full` 便于调试——被 §10.1 与 R-11 否决；默认 `metadata`——被 D-05 建议默认值否决。
**状态**: 已定，D-05 在 M1 正式确认。

## R-16 三端与 SSH 的能力对等判据

**Decision**: 功能对等按业务能力定义，不按视觉交互定义（ADR-009）：相同业务能力、权限检查、状态迁移、错误语义与可审计性必须一致；CUI 输出 JSON、TUI 使用键盘、Web 使用浏览器组件。三端共用功能能力矩阵，新能力的 API、CLI 行为、权限与测试须在同一 PR 内定义（FR-610）。任一端产生的更改须在其他在线端可见，断线端可从持久化游标补齐（FR-605）。
**Rationale**: §4.6 三端对等定义；R-04 风险登记（不同状态源导致功能漂移）对策为统一 app service、事件协议与命令级契约测试。
**Alternatives considered**: 以 Web 复用 TUI 键盘交互——被 §4.6 明确否决；按界面截图判断对等——被 ADR-004/009 否决。
**状态**: 已冻结；能力矩阵文档为 §12.2 交付物。
