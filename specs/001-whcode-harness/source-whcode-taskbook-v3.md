## 0. 文档规则与修订原则

### 0.1 规范用语

- **必须（MUST）**：验收前不可缺失的要求。
- **应该（SHOULD）**：默认实现；如不采用，必须在 ADR 中记录理由与替代方案。
- **可以（MAY）**：可选能力，不得成为核心流程的隐含依赖。
- **待验证（TBD）**：尚未由目标平台实测或基准测试证明，不得宣传为已实现能力。

### 0.2 需求属性

| 标记 | 含义 |
|---|---|
| `[硬性]` | 原始需求中明确要求的能力 |
| `[架构]` | 为保证一致性、可维护性与可靠性而新增的约束 |
| `[优化]` | 以性能、操作体验或维护成本为目标的建议 |
| `[待验证]` | 取决于具体依赖、操作系统或基准环境的事项 |

### 0.3 本版核心修订

1. 将 Web 从“PTY 桥接 TUI”调整为独立前端，通过统一应用服务访问状态与命令；SSH 终端接入作为独立传输适配器。
2. 默认采用**每个工作区一个 DuckDB 文件**。不再默认按会话分库，避免任务、事件与检查点之间出现跨库事务边界。
3. 将 Spec Kit 的核心交付流程、质量检查和 WHCode 自定义门禁分离，允许 Implement 与 Converge 循环。
4. 区分 Boa JavaScript 引擎与 Node.js 兼容运行时；不再把“能够执行 ECMAScript”表述为“完整支持 Node.js”。
5. 删除未经验证的内存比例、渲染提速比例等性能结论；保留部分原始性能目标作为**候选预算**，由 M0 基准测试冻结。
6. 删除把 `Box::leak`、固定线程数、固定批次大小等直接规定为普遍优化手段的做法，改为可配置基线与基准驱动的工程决策。
7. 修正 DuckDB 清理语义：`VACUUM` 不能作为磁盘空间回收保证；回收流程以 `CHECKPOINT`、空间统计以及必要时的数据库重建/复制为依据。[S3][S4]
8. 对“恰好执行一次”作出限制：外部工具、文件写入与数据库无法形成一个共同事务；系统必须记录执行意图并在恢复时核对结果，不得承诺无法证明的 exactly-once 语义。

## 1. 产品定位与设计目标

WHCode 是一个 Rust 原生的 LLM 编码 Harness，承担会话管理、上下文构建、模型调用、工具执行、任务编排、Spec-Driven Development（SDD）门禁、事件追踪与状态恢复。项目不以重新实现完整 IDE 为目标。

### 1.1 设计目标

| ID | 目标 | 验收原则 |
|---|---|---|
| G-01 | 五类目标操作系统可构建、可运行 | 每个平台均有实际构建和冒烟测试证据；不能只以交叉编译成功代替运行验证 |
| G-02 | 资源使用可度量、可约束 | 提供固定测试负载和测量脚本；性能预算在 M0 后冻结 |
| G-03 | LLM 调用可追踪 | 请求、响应、工具调用、状态变化可以按 ID 关联与重放；敏感数据按配置脱敏 |
| G-04 | 长会话加载成本不随完整历史线性增长 | 切换会话只加载元数据、概览和有限活跃尾部；历史按需分页或流式读取 |
| G-05 | SDD 流程由程序实施门禁 | 门禁失败时应用服务拒绝阶段转换，而非仅向模型追加提示词 |
| G-06 | 三端共享业务能力 | TUI、CUI、Web 调用同一组应用命令与状态服务；交互形态可不同 |
| G-07 | 运行时可选启用 | 未安装或未启用运行时不影响核心启动；请求缺失能力时返回结构化错误 |
| G-08 | 可恢复与可审计 | 崩溃后识别未完成请求、外部操作不确定状态和最近有效检查点 |

### 1.2 范围内

- 会话与任务管理、上下文窗口管理和长程任务续跑。
- LLM Provider 抽象、流式响应与可配置追踪。
- DuckDB schema、迁移、单写者服务、读取连接管理、检查点与清理工具。
- Spec Kit 风格的 SDD 流程、产物验证、追溯检查和 Converge 循环。
- TUI、CUI、Web UI，以及四大 BSD 上的 SSH 接入。
- 可选 JavaScript、Python、Shell 与 Windows Git Bash 执行能力。
- 测试夹具、性能压测、跨平台 CI、部署和安全说明。

### 1.3 范围外

- 全功能代码编辑器、完整 LSP、调试器和 IDE 插件市场。
- 多租户 SaaS、云端账单系统、组织级计费与协作管理。
- 移动端原生应用。
- 默认使用 DuckDB 以外的持久化后端。
- 把任意不受信任脚本在主进程内执行。

## 2. 核心架构决策（冻结前提）

以下决策是实现各模块前必须遵守的架构基线。如需更改，必须提交 ADR（Architecture Decision Record），记录问题、备选方案、风险、基准数据和迁移影响。

| ADR | 决策 | 理由与约束 | 状态 |
|---|---|---|---|
| ADR-001 | 一个工作区默认对应一个 DuckDB 数据库文件 | 任务、事件、消息、产物、检查点可在同一事务边界中更新；暂不引入分库和全局索引双写 | 建议冻结 |
| ADR-002 | DuckDB 写入通过单一应用层写者服务串行化 | 便于有界排队、批量事务、顺序编号、去重和审计；这是 WHCode 的应用策略，不是 DuckDB 唯一允许的并发方式 [S1] | 建议冻结 |
| ADR-003 | TUI/CUI/Web 只依赖应用服务接口，不直接写数据库 | 避免业务逻辑、权限检查和门禁在不同前端出现分叉 | 必须冻结 |
| ADR-004 | Web 是原生 Web UI，不是 TUI 的 PTY 镜像 | 功能能力对等必须基于命令和状态，不可由 xterm.js 终端画面代替 | 必须冻结 |
| ADR-005 | SSH 是独立传输入口，复用应用服务 | 不允许每个 SSH 会话各自打开数据库并直接写入 | 必须冻结 |
| ADR-006 | 原始事件持久化与实时广播分离 | 广播队列可丢弃可恢复的低优先级快照；持久化队列按事件等级提供不同的背压与确认语义 | 必须冻结 |
| ADR-007 | 外部工具调用采用“意图记录—执行—结果登记”协议 | 文件系统、子进程与 DuckDB 不能组成单一原子事务；恢复时必须识别 `unknown` 状态 | 必须冻结 |
| ADR-008 | 运行时均在子进程中执行 | 限制崩溃、泄漏和脚本资源使用对主进程的影响；主进程不得直接嵌入不受信任脚本执行 | 必须冻结 |
| ADR-009 | 功能对等按业务能力定义，不按视觉交互定义 | CUI 输出 JSON，TUI 使用键盘，Web 使用浏览器组件；同一能力的行为和权限必须一致 | 必须冻结 |
| ADR-010 | 跨 BSD 可构建与 DuckDB 原生构建分开验收 | Rust target 存在不代表所有 C/C++ 依赖均能构建；每个平台的实际数据库构建是 M0 退出条件 | 必须冻结 |

## 3. 术语与状态模型

| 术语 | 定义 |
|---|---|
| Harness | 承载 LLM 会话、工具调用、状态管理与任务编排的运行时外壳 |
| 工作区（Workspace） | 配置、数据库、任务产物和运行时状态的持久化边界 |
| 会话（Session） | 一次可恢复的智能体交互上下文 |
| 任务（Task） | 有标识、依赖、状态、验收条件和阶段归属的工作单元 |
| 产物（Artifact） | 规范、计划、任务列表、分析报告、代码差异、测试报告或收敛报告 |
| 事件（Event） | 表示请求、工具执行、任务状态或持久化行为的不可变记录 |
| 检查点（Checkpoint） | 用于恢复任务的状态差分、产物引用、消息游标和外部操作标记 |
| 应用服务（Application Service） | 接收命令、校验权限与状态、协调模块并返回事件或快照的共享业务层 |
| SDD | Specification-Driven Development，规范驱动开发流程 |
| 门禁（Gate） | 对产物结构、一致性、能力可用性或验收结果执行的程序化检查 |
| 预加载层 | 会话元数据、任务概览和少量活跃上下文；不包含完整历史 |
| 细节层 | 按页或按预算读取的消息、事件与产物内容 |
| 写者服务（Writer Service） | 唯一接受应用数据库写命令的组件，负责事务、去重和提交结果 |
| 运行时 Provider | 对某一种执行环境进行能力声明、版本探测、执行与结果归一化的适配器 |

### 3.1 状态常量

- 任务状态至少包括：`pending`、`ready`、`running`、`blocked`、`completed`、`failed`、`aborted`、`interrupted`、`unknown`。
- LLM 请求状态至少包括：`queued`、`started`、`streaming`、`completed`、`failed`、`interrupted`。
- 运行时执行状态至少包括：`prepared`、`running`、`completed`、`failed`、`timed_out`、`interrupted`、`unknown`。
- SDD 阶段转换必须记录来源阶段、目标阶段、执行者、校验结果与时间戳。
- 状态名应在代码、数据库、CUI JSON Schema 和 Web 协议中使用同一套枚举定义。

## 4. 功能需求

### 4.1 会话、上下文与历史

| 编号 | 要求 | 优先级 |
|---|---|---|
| FR-101 | 创建、恢复、重命名、归档、删除和列出会话 | P0 |
| FR-102 | 切换会话时仅加载元数据、概览、上下文指针和有限的活跃尾部 | P0 |
| FR-103 | 随时生成工作区与当前会话的任务总览，包括阶段分布、完成度、阻塞任务和活跃任务 | P0 |
| FR-104 | 按需返回当前任务详情、依赖、步骤、产物引用、最近事件和失败原因 | P0 |
| FR-105 | LLM 上下文注入必须按预算读取历史，禁止将整个历史集合一次性载入内存 | P0 |
| FR-106 | 支持稳定游标分页；滚动方向、排序键与游标语义必须明确定义 | P0 |
| FR-107 | 支持上下文压缩和摘要指针；压缩后仍可查阅原始历史 | P1 |
| FR-108 | 用户可查看当前上下文预算、实际装入内容的来源与截断原因 | P1 |

**约束**：历史详情查询必须使用有界批次。上下文加载器应返回 `items + next_cursor + consumed_budget + truncated_reason`，不得要求 UI 或 LLM 层自行从完整历史中切片。

### 4.2 LLM 调用透明性

| 编号 | 要求 | 优先级 |
|---|---|---|
| FR-201 | 统一事件类型：请求开始、流式增量、请求完成/失败、上下文状态、进度变化、工具调用开始/结束、运行时终止与持久化异常 | P0 |
| FR-202 | 实时事件可广播；断线重连后可依据持久化游标补拉事件 | P0 |
| FR-203 | 提供追踪级别：`off`、`metadata`、`redacted`、`full`；默认不把秘密凭据写入日志 | P0 |
| FR-204 | 通过 `request_id`、`session_id`、`task_id`、`tool_call_id` 串联一次调用的完整链路 | P0 |
| FR-205 | CUI 支持 JSON / JSONL 事件查询与导出，并在导出中注明脱敏策略 | P0 |
| FR-206 | 流式事件积压时可以合并 UI 更新或降低仅用于展示的 chunk 频率；不得静默丢失关键状态转换 | P0 |
| FR-207 | 能记录 token 数、模型参数、延迟和成本；估算值必须标记为估算，供应商返回的计量值另行保存 | P1 |
| FR-208 | 追踪记录需要提供完整性标记，包括是否存在缺失 chunk、脱敏、降采样或持久化失败 | P1 |

**事件可靠性分级**：

1. **关键事件**：任务状态转换、请求最终结果、工具执行意图与结果、门禁结果、人工强制放行、审计事件。不得静默丢弃；队列饱和时必须背压、失败返回或触发安全停止。
2. **内容事件**：请求/响应正文与流式增量。是否持久化由追踪级别控制；若内容被省略或采样，必须留下可查询的标记。
3. **展示快照**：帧率、重复进度通知等可重建信息，允许合并或丢弃。

不得把“实时广播 + 数据库写入”描述成自动原子双写。实现须明确事件何时被确认持久化，并处理“广播已发出、写入失败”和“写入已成功、客户端未收到”两种情况。

### 4.3 Spec Kit / SDD 工作流

WHCode 应实现可配置、可版本化的 SDD 工作流。它与上游 Spec Kit 保持概念与产物兼容，但不得假定上游某一版本的命令、模板或插件实现就是稳定 API。

#### 4.3.1 工作流模型

核心交付循环：

`Constitution（项目级约束） → Specify → Plan → Tasks → Implement → Converge`

质量检查：

- `Clarify`：澄清规格中的歧义；未解决的高优先级问题阻止进入 Plan。
- `Analyze`：检查 spec、plan、tasks 之间的引用完整性、覆盖关系与矛盾；未通过时阻止进入 Implement。
- `Checklist`：可选的人工质量审查清单；如项目策略将其设为强制，必须将结果纳入审计。
- `Converge`：实现后对照规范与任务检查差距；发现缺口时追加可追溯任务，再执行 Implement → Converge，直到收敛或被人工明确阻断。[S2]

上述工作流是应用层状态机，而不是简单的线性五阶段。阶段、门禁和重试策略必须从版本化的工作流配置中读取。

#### 4.3.2 产物格式与验证

| 编号 | 要求 | 优先级 |
|---|---|---|
| FR-301 | 初始化工作区时创建或导入 Constitution，并记录版本与变更审计 | P0 |
| FR-302 | 每个阶段定义允许输入、必需产物、校验器和成功/失败转换 | P0 |
| FR-303 | 默认产物保留可读的 Markdown 文件；应用内部解析为版本化结构，不直接假设原始 Markdown 是 JSON Schema 文档 | P0 |
| FR-304 | 每条需求有稳定 ID；每条任务有稳定 ID、验收条件、依赖和需求引用 | P0 |
| FR-305 | Plan 的关键决策可追溯至需求；任务可追溯至需求和计划决策 | P0 |
| FR-306 | Analyze 检出遗漏需求、孤儿任务、无效引用、循环依赖和覆盖不足 | P0 |
| FR-307 | 高优先级未解决澄清项阻止 Plan；引用或覆盖检查失败阻止 Implement | P0 |
| FR-308 | 每次阶段转换均由应用服务校验；仅提示词要求遵守流程不构成门禁 | P0 |
| FR-309 | 解析失败可自动纠偏重试，默认最多 2 次；仍失败则标记 `blocked` 并保留错误与原始产物 | P0 |
| FR-310 | Converge 对每条验收条件记录 `pass`、`fail`、`not_tested` 或 `not_applicable`，并附证据引用 | P0 |
| FR-311 | 失败或未测试的验收条件不得使任务静默变为完成；必须产生差异报告或阻塞原因 | P0 |
| FR-312 | 人工强制放行必须记录 `actor`、`reason`、跳过的门禁、相关产物版本和时间戳 | P0 |
| FR-313 | 每次模型调用显式注入当前阶段角色和允许操作，角色由状态机提供，而非从历史文本推断 | P0 |
| FR-314 | TUI、CUI、Web 显示同一份阶段状态、门禁结果和产物版本 | P0 |

#### 4.3.3 产物规范

内部规范化的任务对象至少包含：

```json
{
  "id": "T-001",
  "title": "可验证的任务标题",
  "status": "pending",
  "requirement_refs": ["REQ-001"],
  "plan_refs": ["DEC-001"],
  "acceptance_criteria": ["存在可执行或可审查的验收断言"],
  "depends_on": []
}
```

这只是内部规范化结构示例，不意味着上游 Markdown 必须改成 JSON。Markdown 解析器必须报告无法解析的段落、重复 ID 和未识别字段，禁止静默丢弃信息。对“应该可用”“表现正常”等不可验证条件，门禁应要求补充可执行断言、人工检查清单或明确的不可自动化说明。

### 4.4 长程任务、检查点与恢复

| 编号 | 要求 | 优先级 |
|---|---|---|
| FR-401 | 任务步骤支持持久化进度、依赖关系、重试计数和恢复状态 | P0 |
| FR-402 | 检查点以增量状态差分和引用为主，避免每步复制完整历史 | P0 |
| FR-403 | 任务状态变化、对应关键事件和检查点引用必须在同一 DuckDB 事务内提交 | P0 |
| FR-404 | 恢复时加载检查点引用的元数据、产物与上下文游标；完整历史继续按需读取 | P0 |
| FR-405 | 定时、按步骤和危险操作前可触发检查点；间隔与保留数量可配置 | P0 |
| FR-406 | 子任务支持依赖图；并行调度为 P1，必须在状态和写入一致性测试通过后实现 | P1 |
| FR-407 | 提供轮询兜底机制；轮询读取只读快照，不得独占或阻塞写者服务 | P0 |
| FR-408 | 单个可重试任务失败不得让整个会话丢失；不可恢复错误需向上传播 | P0 |
| FR-409 | 子进程被终止、超时或主进程崩溃时，记录终止原因、退出状态、stderr 尾部和执行状态 | P0 |
| FR-410 | 恢复协议必须处理外部副作用不确定的情况；不能判断是否已完成时标记 `unknown` 并要求核对、幂等重试或人工决策 | P0 |

**检查点时序**：外部工具执行前先提交 `prepared` 意图与检查点；启动后标记 `running`；工具结束后记录输出摘要、退出码与副作用凭证，再将结果写入同一数据库事务。如果进程在副作用发生后、结果登记前崩溃，恢复逻辑不得盲目宣称操作从未发生。

### 4.5 数据库与清理

| 编号 | 要求 | 优先级 |
|---|---|---|
| FR-501 | 提供版本化 schema 与可重复执行的迁移机制 | P0 |
| FR-502 | 提供有界写入队列、幂等键、批量提交与写入结果确认 | P0 |
| FR-503 | 批量提交按“达到行数上限或时间上限先到者”触发；初始基线为 500 行或 50 ms，须由 M0/M1 基准校准 | P0 |
| FR-504 | 历史查询使用稳定排序键和游标分页，不以大 OFFSET 作为默认的长历史分页路径 | P0 |
| FR-505 | 历史注入必须使用有界迭代；达到字符、token 或时间预算后停止并返回截断原因 | P0 |
| FR-506 | 高频概览使用显式维护的预聚合表；更新延迟和一致性语义必须可测 | P0 |
| FR-507 | 提供数据库统计、查询计划分析、WAL 状态和写者队列监控 | P0 |
| FR-508 | 提供会话归档、按时间清理、TTL 和导出/导入能力 | P0 |
| FR-509 | 清理操作必须有预览、确认、审计和活跃会话保护机制 | P0 |
| FR-510 | 数据库维护记录清理前后文件大小、WAL、已用块与可用块；不得承诺 `VACUUM` 一定释放文件空间 | P0 |
| FR-511 | 只有经基准证明有收益时，才启用额外缓存、分区、分库或更复杂的物化结构 | P1 |

**空间回收规则**：`CHECKPOINT` 用于同步 WAL 并可能部分回收已删除数据所占空间；效果受删除分布等条件影响。DuckDB 的 `VACUUM` 不是通用磁盘空间回收操作。若业务要求显著缩小文件，应提供受控的“复制到新数据库/重建”流程，包含停写、校验、切换、备份与失败回滚。[S3][S4]

#### 4.7.1 运行时命名和兼容边界

| 能力 | 实现建议 | 必须声明的限制 |
|---|---|---|
| JavaScript | Boa 可作为受限 ECMAScript 引擎后端 | 不得称为完整 Node.js；不具备 Node API 或 npm 兼容性时，必须明确标注 |
| Node.js | 独立 Node.js 可执行文件或官方运行时 payload | 与主二进制分离；版本、平台、文件树和许可证信息须可审计 |
| Python | 子进程 Worker，可对接经验证的 Python 解释器与 `libpython` | C 扩展兼容性取决于 Python 版本、ABI、平台和依赖包；不能承诺普遍兼容 |
| 受限 Python | 可选 RustPython 等受限实现 | 明确不支持的标准库、扩展和系统调用；门禁不得当作完整 Python |
| Windows Git Bash | 独立 PortableGit payload | 安装体积随版本变化，不写死固定 MB 数；验证 Bash、coreutils、管道与重定向 |
| BSD Shell | 系统 `/bin/sh` 或用户指定 Shell provider | 与 Windows Git Bash 是不同能力，不得共用 `gitbash` 名称伪装为完全等价 |

运行时是否内置、默认携带还是按需下载，应在 P1 实现前形成独立 ADR。不得把“动态链接 `libpython`”直接等同于已交付完整 Python 安装环境；也不得把 `deno_core` 单独等同于 Node.js 完整兼容层。

### 5.2 内存与 CPU 性能预算

以下数值保留为候选目标，而非未经测量即可承诺的事实。M0 必须提供同一版构建、固定硬件和固定数据集的基线报告；若目标无法达到，应先分析热点，再通过 ADR 修订目标与架构。

| 编号 | 候选指标 | 初始目标 | 测量条件 |
|---|---|---:|---|
| NFR-201 | 主进程空载 RSS | ≤ 35 MB | 启动 10 秒、数据库已打开、无活跃请求；跨平台分别测量 |
| NFR-202 | 单会话活跃 RSS | ≤ 80 MB | 明确消息长度、活跃尾部大小和事件缓冲上限 |
| NFR-203 | 长历史会话切换后 RSS 增量 | ≤ 10 MB | 10 万事件数据集，切换 20 次并记录峰值与稳态 |
| NFR-204 | 72 小时 RSS 斜率 | ≤ 0.5 MB/h | 记录稳态时间序列，说明回归方法与采样间隔 |
| NFR-205 | TUI 空闲 CPU | ≤ 0.5% 单核 | 固定终端尺寸、无动画、无输入；报告采样窗口 |
| NFR-206 | LLM 流式期间 CPU | ≤ 8% 单核 | 固定响应速率与 chunk 大小；网络等待与解析成本分开记录 |
| NFR-207 | 会话切换响应 | ≤ 200 ms | 10 万事件数据集；给出 p50、p95、p99 |
| NFR-208 | 任务概览查询 | p95 ≤ 50 ms | 1 万任务与固定阶段分布；包括冷/热缓存差异 |
| NFR-209 | 历史单页查询 | p95 ≤ 30 ms | 固定页大小与索引；不得仅报告平均值 |
| NFR-210 | 事件写入吞吐 | ≥ 2,000 条/秒（候选） | 固定事件大小、批次策略、持久化等级和磁盘环境 |

**测量纪律**：RSS、CPU 和文件大小的统计方式必须记录操作系统、硬件、编译类型、Rust 工具链、DuckDB 版本、数据库参数、测试数据规模、采样窗口与测试脚本。不同平台的结果不得直接混为一组平均值。DuckDB 的 `memory_limit` 约束的是其缓冲管理器，不代表整个 WHCode 进程的 RSS 上限。[S5]

### 5.3 内存和渲染实现原则

- 渲染线程只读取不可变快照或轻量状态，不执行 LLM 网络 I/O、阻塞数据库查询或长时间工具调用。
- 使用脏标记或事件驱动触发重绘；终端尺寸变化、用户输入和实际状态变化必须立即得到处理。
- UI 数据结构在状态变化时构建或更新；绘制路径尽量避免全量克隆、全历史遍历与不必要的分配。
- 所有队列设上限并定义满载语义。关键命令不能因满载而静默丢失，低优先级展示快照可以合并。
- `SmallVec`、`ArrayVec`、`mimalloc`、`jemalloc`、Unicode 宽度缓存等只能在基准数据支持时采用；不得以源代码层面的“零分配”表述替代端到端测量。
- 禁止将 `Box::leak` 作为通用的长期对象优化方案；必须通过所有权设计、缓存上限和 profiling 解决分配与生命周期问题。
- 不在渲染帧路径对完整 JSON payload 做反序列化；事件应通过轻量枚举、`Bytes` 或按需解析处理。

### 5.4 数据库配置基线

| 配置项 | 初始策略 | 备注 |
|---|---|---|
| `memory_limit` | 默认 192 MB，上限由用户配置；候选最大 384 MB | 仅约束 DuckDB buffer manager，必须监控总 RSS |
| `threads` | 初始不高于 `min(4, 可用物理核数)`，可配置 | 以实际工作负载压测为准，不将固定值写死为架构定理 |
| `temp_directory` | 工作区配置的专用临时目录 | 启动时检查可写性、磁盘余量；不假定所有系统都有独立 SSD |
| `max_temp_directory_size` | 提供显式可配置上限 | 超限需返回明确错误并保护数据库一致性 |
| `preserve_insertion_order` | 仅在确认事件查询语义不依赖其默认行为后再设置 | 以实际查询和兼容测试为依据 |
| 读取连接 | 每个查询工作线程持有自己的连接或受控连接对象 | DuckDB Rust `Connection` 为 `Send`、非 `Sync`；不得无锁共享同一连接给多个线程。[S5] |
| 写事务 | 单一写者服务管理事务和批量提交 | 不直接依赖连接池对写入进行并发分发 |
| WAL / CHECKPOINT | 监控 WAL 大小并按阈值、空闲窗口或显式维护触发 | 避免在高负载路径无条件强制 checkpoint |

## 6. 系统架构

### 6.1 逻辑分层

```text
┌────────────────────────────────────────────────────────────┐
│ 前端：TUI │ CUI │ Web UI │ SSH Terminal Adapter            │
└───────────────────────────┬────────────────────────────────┘
                            │ Application Commands / Snapshots / Events
┌───────────────────────────▼────────────────────────────────┐
│ whcode-app：统一应用服务、权限检查、命令路由、状态快照       │
├────────────────────────────────────────────────────────────┤
│ 会话服务 │ 任务调度 │ SDD 状态机 │ 上下文构建 │ 审计          │
├────────────────────────────────────────────────────────────┤
│ LLM Provider │ Tool Executor │ Runtime Manager │ Event Router│
├────────────────────────────────────────────────────────────┤
│ whcode-store：DuckDB 写者服务、读取连接、迁移、清理与归档    │
└────────────────────────────────────────────────────────────┘

外部边界：LLM HTTP API、子进程运行时、文件系统、SSH/Web 网络接口
```

### 6.2 Crate 划分

| Crate | 职责 | 依赖原则 |
|---|---|---|
| `whcode-domain` | 核心领域类型、任务状态、事件类型、门禁结果 | 尽量不依赖 UI、网络和数据库具体实现 |
| `whcode-app` | 命令处理、权限检查、用例编排、快照生成 | 依赖 domain 与 trait，不让前端直接触库 |
| `whcode-llm` | Provider、流式响应、重试、模型计量 | 通过事件接口报告，不直接修改 UI 状态 |
| `whcode-store` | DuckDB schema、迁移、读写、事务、清理和导出 | 实现 domain/app 定义的存储接口 |
| `whcode-speckit` | 工作流配置、Markdown 解析、产物校验、追溯、门禁 | 版本化 schema 与解析器 |
| `whcode-tools` | 工具注册、权限策略、调用意图与结果记录 | 外部副作用需走统一执行协议 |
| `whcode-runtime` | 运行时 provider、payload 管理、worker 协议 | 所有脚本放在子进程执行 |
| `whcode-tui` | ratatui UI、键位和终端事件 | 通过 app command/snapshot/event 接口工作 |
| `whcode-cui` | clap 命令、JSON / JSONL 输出 | 命令与退出码版本化 |
| `whcode-web` | Web API、WebSocket、静态资源或独立前端协议 | 不经由 PTY 访问应用状态 |
| `whcode-ssh` | SSH 认证、会话生命周期、终端流适配 | 复用 app；不得直接打开数据库写入 |
| `whcode-platform` | 操作系统差异、进程控制、PTY/终端能力、路径与资源探测 | `cfg` 条件编译集中在此层 |
| `whcode-bin` | 主程序、配置加载、日志初始化、feature 装配 | 避免将可选运行时静态纳入默认依赖树 |

Crate 名称允许在实现前调整，但职责边界必须保持。不得为形式上的模块数量制造过度拆分；若两个模块尚无稳定接口，优先在同一 crate 中使用模块边界。

### 6.3 并发模型

| 组件 | 执行模型 | 禁止事项 |
|---|---|---|
| UI 渲染 | 终端事件循环或 Web 客户端事件循环 | 不阻塞等待 LLM 或数据库 |
| 应用服务 | Tokio async runtime；CPU 密集工作移至受控线程池 | 不在 async executor 中执行无界阻塞 I/O |
| LLM I/O | 异步网络流 | 不绕过事件和请求状态管理 |
| 写者服务 | 有界队列 + 专用线程/执行上下文 | 多个模块直接并发写数据库 |
| 查询执行 | 有界查询任务与每工作线程独立连接 | 查询结果不得无界收集进内存 |
| 运行时 | 受控子进程 | 不在 UI 或主应用线程执行用户脚本 |
| SSH/Web | 网络任务与独立客户端状态 | 不允许单个慢客户端阻塞其他会话的状态广播 |

### 7.2 索引与游标

- `events`：至少对 `(session_id, seq)`、`request_id`、`task_id` 建立满足实际查询的索引。
- `messages`：对 `(session_id, ts, id)` 或等价的稳定游标键建立索引。
- `tasks`：对 `(session_id, status)`、`stage` 和依赖引用建立查询所需索引。
- 游标必须包含能形成稳定全序的键；不能只依靠可能重复的时间戳分页。
- 向前/向后翻页使用不同明确的游标比较方向；示例 `seq > last_seq` 仅适用于按升序向后读取的场景。
- 索引与查询计划必须通过真实基准验证；不能简单规定“所有全表扫描都失败”，因为小表或完整聚合的扫描可能是正确计划。

### 7.3 事务与写入队列

1. 写者服务接收结构化命令，命令携带 `idempotency_key` 和期望的状态版本（适用时）。
2. 队列有界；超过容量时关键命令返回明确背压/失败，禁止无限堆积。
3. 写者将兼容的普通写入合并为事务，达到 500 行或 50 ms 任一阈值即提交；该参数须基准校准。
4. 对关键事件和危险操作意图，提供显式 flush/提交确认，不得为达到批次大小而无限等待。
5. 数据库事务成功后才向调用方返回持久化确认；失败时应返回错误并保留可重试信息。
6. 同一幂等键重复到达时返回既有结果或确定的冲突，不得重复创建状态转换。
7. 查询结果以流式迭代或有界批次处理；不得在长历史路径调用等价于 `fetch_all` 的无界收集接口。
8. 预聚合表可异步更新，但必须明确“强一致字段”和“最终一致概览字段”，并提供重建逻辑。

### 7.4 备份、导出与迁移

- 导出格式必须包含版本、工作区元数据、产物、事件和内容清单；大对象使用可校验的分块格式。
- 导入前检查 schema 兼容性、文件路径、重复 ID、哈希和剩余磁盘空间。
- schema 迁移前生成可恢复备份或确认已有备份；迁移失败时数据库不得被误标记为新版本。
- 数据库压缩/重建操作需独占维护锁、先验证副本、再原子切换文件；Windows 文件替换和 BSD 文件锁语义分别测试。

## 8. 接口设计

### 8.1 CUI 命令草案

命令树为接口草案。实现时必须统一参数命名、退出码、错误 JSON 和 `--json` 语义；破坏性命令需支持 dry-run 或确认机制。

```text
whcode
  session new|list|show|rename|archive|delete
  run [--session ID] [--model MODEL] [--trace-level LEVEL]
  status [--json]
  task list|show|retry|abort
  spec status|next|validate|analyze|converge|force-advance
  events list|show|export --session ID [--after SEQ] [--format jsonl]
  db stats|check|purge --before TS|checkpoint|compact|archive --export PATH|explain QUERY
  runtime list|status|enable|disable|install NAME
  serve --web [--bind 127.0.0.1:PORT]
  serve --ssh [--port PORT]
  doctor [--json]
```

修订说明：

- `db vacuum` 不作为通用空间回收承诺；CLI 可提供与 DuckDB 原生命令一致的 `vacuum` 子命令，但必须提示其语义与局限。建议将用户关心的磁盘压缩能力命名为 `db compact`。
- 数据库命令不接受任意未受控 SQL 作为默认公开 API。`db explain` 应只运行只读查询或内部预定义查询模板，并实施超时与输出限制。
- `spec force-advance` 必须要求 `--reason`，且只用于明确列出的门禁；不得绕过完整性或安全约束而不留下审计。
- JSON 输出必须有 `schema_version`，错误对象包括 `code`、`message`、`retryable` 和 `details`。

### 8.2 状态快照示例

```json
{
  "schema_version": 1,
  "session": {"id": "S-001", "title": "Example", "stage": "Implement", "status": "running"},
  "overview": {"total_tasks": 42, "done": 30, "blocked": 2},
  "active_task": {"id": "T-017", "status": "running", "retry_count": 1},
  "context": {"estimated_tokens": 18432, "budget": 128000, "truncated": false},
  "llm": {"request_id": "R-889", "state": "streaming", "elapsed_ms": 1840},
  "event_cursor": 9912,
  "runtimes": {"javascript": {"enabled": false}, "python": {"enabled": false}}
}
```

### 8.3 事件结构示例

```json
{"schema_version":1,"kind":"RequestStarted","event_id":"E-100","request_id":"R-889","session_id":"S-001","ts":"2026-10-20T06:00:00Z"}
{"schema_version":1,"kind":"StreamingChunk","event_id":"E-101","request_id":"R-889","seq":12,"persistence":"omitted_by_policy"}
{"schema_version":1,"kind":"RequestCompleted","event_id":"E-102","request_id":"R-889","prompt_tokens":2100,"completion_tokens":540,"latency_ms":7321,"cost_estimate":0.0042,"cost_is_estimate":true}
{"schema_version":1,"kind":"RuntimeTerminated","event_id":"E-103","runtime":"python","reason":"timeout","state":"timed_out","stderr_ref":"A-900"}
```

事件 schema 必须声明字段必需性、兼容规则、敏感字段与最大 payload 尺寸。不得把大段响应正文重复塞进每个进度事件。

### 8.4 Provider / Tool / Runtime 接口约束

Rust trait 的具体签名留给实现设计，但必须满足以下语义：

- LLM Provider：模型能力探测、请求取消、流式结果、计量来源、超时和供应商错误归一化。
- Tool Executor：参数 schema 校验、权限策略、执行意图持久化、超时/取消、stdout/stderr 限制与结果引用。
- Runtime Provider：`name`、`capability`、`is_available`、`env_fingerprint`、`execute`、`terminate`；执行返回退出码、持续时间、资源观察值和输出引用。
- 所有异步执行操作必须有取消语义；若底层无法保证立即取消，应说明取消请求何时生效。

## 9. 平台与部署矩阵

Rust target 的支持等级会随工具链版本变化；平台表须在每次发布时根据锁定的 Rust 版本更新。Rust target 可用并不代表 DuckDB 原生依赖、SSH、终端、TLS 或运行时 payload 已在该平台通过测试。[S6]

| 平台 | 优先目标 | 验收范围 | 主要风险 |
|---|---|---|---|
| FreeBSD | `x86_64-unknown-freebsd`；按需验证 `aarch64-unknown-freebsd` | 原生构建、TUI、DuckDB、LLM、SSH server、Web、清理/恢复 | DuckDB 及 C/C++ 工具链版本组合 |
| OpenBSD | `x86_64-unknown-openbsd` | 必须在目标 OpenBSD 版本上原生构建并运行最小工作区；逐步扩展 SSH 与长期任务测试 | Rust 官方保障等级、系统库差异及本机依赖构建 |
| NetBSD | `x86_64-unknown-netbsd` | 原生构建、TUI、DuckDB、存储/恢复；随后验证 SSH | 工具链与 pkgsrc 环境差异 |
| DragonFly BSD | `x86_64-unknown-dragonfly` | 原生构建、DuckDB、TUI、进程/文件操作、SSH | 依赖上游测试覆盖和特定版本 ABI |
| Windows | 首选 `x86_64-pc-windows-msvc` | 构建、TUI、Web、文件操作、DuckDB、子进程退出/超时；Git Bash payload 后置 | 原生依赖、终端差异、文件替换与子进程树终止 |

### 9.1 平台承诺原则

- 支持平台的确切 OS 版本和 CPU 架构必须在发布矩阵中公开，不以“Windows”“BSD”作为无限范围的承诺。
- CI 至少分为：构建检查、可运行的原生测试、依赖验证、定期 24/72 小时稳定性测试。
- 如果某个平台无法构建 DuckDB Rust/native 依赖，M0 必须形成明确的 Go/No-Go 决策。不得在“默认只有 DuckDB”约束下，未经批准偷偷切换为其他数据库。
- OpenBSD、NetBSD、DragonFly 的 Rust target 状态和依赖能力分别处理；不得统一写成“必须自行构建 Rust 标准库”。
- Web 对外部署应使用 TLS 终止、身份认证、Origin 校验、速率限制和最小权限；默认 localhost 绑定不替代生产部署安全方案。

## 10. 安全与信任边界

### 10.1 敏感信息

- API Key、访问令牌和运行时凭据不得以明文配置常量写入数据库、日志或测试快照。
- 默认追踪等级应对疑似秘密字段脱敏。显式 `full` 模式必须在 UI 中警告潜在敏感信息写入，并提供访问控制、清理和导出策略。
- 错误、stderr、模型输出和工具返回均视为不可信数据，不得作为控制指令直接执行。
- 导出与诊断包应提供脱敏预览，默认不附带完整提示词和环境变量。

### 10.2 工具和运行时安全

- 工具调用按权限白名单执行；破坏性文件操作、任意网络访问、系统级命令和工作区外写入必须由策略明确允许。
- 子进程默认继承最小化环境变量集合，而非完整继承主进程环境。
- 对工作目录、输出大小、执行时长、并发进程数和可用内存设置上限。平台不具备可靠内存限制能力时，必须报告“无法强制限制”，而不是声称已实现。
- Windows 需要处理子进程树；BSD 需要处理进程组、信号、子进程残留和权限边界。
- Web token 不应通过 URL query 参数传递；WebSocket 连接须进行来源校验、身份认证、授权检查和消息大小限制。
- SSH 默认只开放 WHCode 交互功能；任意系统 Shell 应作为显式独立权限，不得隐式授予。

### 10.3 审计

以下操作必须有审计记录：手动越过门禁、修改 Constitution、清理或压缩数据库、修改运行时配置、执行破坏性工具、权限配置变化、数据导出以及认证失败的策略性汇总。审计数据不得随普通会话 TTL 一并自动清除，除非管理员明确设置审计保留策略。

### 11.5 稳定性与性能测试

- 先完成常规功能测试，再运行至少 24 小时稳定性测试；候选发布版本运行 72 小时压力测试。
- 记录 RSS 时间序列、CPU、线程数、文件大小、WAL 大小、写者队列深度、最老队列项年龄、提交延迟、查询延迟、事件缺失计数和失败任务数。
- 测试必须包含慢客户端、LLM 请求失败、断网、磁盘空间不足、数据库写入失败、重启、终止子进程和迁移中断等情形。
- 报告须区分产品缺陷、环境限制和测试工具偏差。不得以没有崩溃代替一致性验证。

| R-01 | DuckDB Rust/native 依赖在个别 BSD 版本构建失败 | 高 | M0 原生验证，固定工具链/编译器，记录补丁与上游状态 | 任一硬目标失败则 M0 不通过 |
| R-02 | SSH server 与目标 BSD 的认证、终端尺寸或断连语义存在差异 | 高 | 分平台集成测试；限定首版认证与交互范围 | 不得以单一 FreeBSD 测试代替四 BSD 验收 |
| R-03 | DuckDB 写入吞吐或查询行为不适合事件负载 | 高 | 基准测试批次、payload 大小、查询索引；削减不必要分析型查询 | 先调整模型与写入批次，再讨论替代后端 ADR |
| R-04 | Web 与 TUI 因不同状态源发生功能漂移 | 中高 | 统一 app service、事件协议、命令级契约测试 | 每个功能 PR 必须更新功能矩阵 |
| R-05 | 大段 prompt / response 或 tool output 导致内存和数据库膨胀 | 高 | 有界 payload、引用化、分块写入、追踪级别与保留策略 | 超预算时截断并记录标记，不得静默删除 |
| R-06 | 模型产物不稳定，解析器误判或丢失内容 | 高 | 版本化解析器、失败时保留原文、纠偏次数限制 | 未通过解析校验的产物阻断门禁 |
| R-07 | 外部工具在崩溃前已执行但结果尚未登记 | 高 | 执行意图、幂等键、side-effect 凭证与 `unknown` 恢复状态 | 禁止盲目重放有副作用操作 |
| R-08 | 把 Boa / RustPython 当作完整生态运行时 | 高 | 明确 capability level、固定兼容性测试、完整运行时采用独立 payload | 未验证能力不得出现在 `Full` 中 |
| R-09 | 性能指标在不同硬件/OS 上不可比 | 中 | 固定测试夹具、分别报告平台结果和分位数 | 指标没有测试条件不得作为发布承诺 |
| R-10 | 数据清理未释放物理空间，用户误以为清理失败 | 中 | 区分行删除、块回收、WAL checkpoint 和文件重建 | 输出各类空间统计并解释限制 |
| R-11 | Web 或工具执行泄漏密钥/执行不受信任指令 | 高 | 默认脱敏、权限白名单、最小环境、身份认证和审计 | 安全测试失败阻断发布 |
| R-12 | P0 范围过大导致长期无法交付 | 高 | 按 M0—M9 分段验收；运行时后置；先打通最小闭环 | 任何阶段不得以未验证的未来能力声称已完成 |

## 15. 需求追溯与变更控制

每条功能需求须至少关联：实现模块、测试用例、验收条件、所依赖的 ADR 和未决风险。需求变更必须同步更新本文件、CLI/API schema、功能对等矩阵和测试夹具。

建议每个代码 PR 具有以下清单：

- [ ] 需求 ID 与实现范围明确。
- [ ] 正向测试与失败路径测试已更新。
- [ ] CUI/API 输出或事件 schema 若有变化，已做版本兼容审查。
- [ ] 三端能力矩阵已更新。
- [ ] 资源、权限、持久化和恢复影响已说明。
- [ ] 新的平台限制或依赖升级已更新兼容矩阵。
- [ ] 未实现事项被明确标记并写明当前行为，不得依赖隐含默认值。

## 16. 参考资料与核验依据

以下资料用于核验依赖能力与语义。依赖升级时应重新检查；本文不把第三方文档中的能力等同于 WHCode 已经完成相应实现。

- **[S1] DuckDB — Concurrency**：单进程内并发写语义、多进程读写限制与并发冲突说明。https://duckdb.org/docs/current/connect/concurrency
- **[S2] GitHub Spec Kit — Quickstart / Agentic SDD**：核心工作流以及 Clarify、Analyze、Converge 等质量步骤。https://github.com/github/spec-kit/blob/main/docs/quickstart.md
- **[S3] DuckDB — VACUUM Statement**：`VACUUM` 的基本语义和不保证回收空间的限制。https://duckdb.org/docs/current/sql/statements/vacuum
- **[S4] DuckDB — Reclaiming Space**：`CHECKPOINT`、删除空间回收与通过复制数据库压缩的说明。https://duckdb.org/docs/current/operations_manual/footprint_of_duckdb/reclaiming_space
- **[S5] DuckDB — Rust Connecting / Limits**：Rust 连接线程安全属性、连接使用建议与 `memory_limit` 的适用边界。https://www.duckdb.org/docs/current/clients/rust/connecting ；https://duckdb.org/docs/current/operations_manual/limits
- **[S6] Rust Compiler — Platform Support**：Rust target 等级和平台保证。https://doc.rust-lang.org/rustc/platform-support.html
- **[S7] PyO3 — Building and Distribution**：嵌入式 Python 的动态/静态链接与分发方式。https://pyo3.rs/v0.29.3/building-and-distribution.html
- **[S8] Boa JavaScript Engine**：JavaScript 引擎项目资料。https://github.com/boa-dev/boa

**文档结束。** v3.0 的目标是让需求可追踪、架构可验证、失败可恢复、指标可复现。进入大规模实现前，先完成 M0 并冻结平台矩阵、事务边界、Web/SSH 形态与性能预算。
