# 软件工程规则的数理逻辑充分性：审计与公理化重构

**日期**：2026-11-17 | **性质**：治理分析（不承载需求承诺；结论转化为承诺须走 G0—G5 门禁，口径同 `research/` 规则，ADR-045）
| **对象**：`AGENTS.md`、`docs/guides/`（方法论类）、`engineering-doctrine/`、`specs/001-whcode-harness/` 的门禁条款
| **判据**：一致性、独立性、相对完备性、可判定性四项，每项给结论与反证条件

本文做的是两件事：把现行规则重述为一个带模态与优先级的形式系统，再按数理逻辑的四个标准
判定它在什么范围内充分、在什么范围内必然不充分。本文的形式化是**重构**，不是仓库原文的
自我声明：原文从未说自己是公理系统，因此“某条规则可被导出”这类判断的可争议点全部列在
§9 的对应表里，逐条给原文位置，反对意见可用同一位置反驳。

## 0. 任务认知卡

| 字段 | 内容 |
|---|---|
| 方向 | 判定本仓库工程规则集在数理逻辑意义上的充分性，并把规则压缩到最小公理基 |

| 用户意图 | 复述：不满足于“规则很多很严”，要知道这套规则在逻辑上到底够不够、哪里不够、能不能判 |

## 1. 结论

1. **结构片段充分，语义片段必然不充分**。对“已登记的有限产物集合上的可机械判定义务”——追溯、
   分层、目录、计数、证据态、编码卫生、action 版本——规则集一致、闭合、可判定且已被程序强制；
   对“开放世界声明”——用户意图是否被正确理解、设计是否优劣、威胁模型是否完备、文档语义是否与
   代码一致——不存在有限判定程序能覆盖，这不是本仓库的缺陷，而是这一类系统的共同边界。
2. **一致性与充分性依赖三个前提，其中两个未明写**。三者是：外部分层（对象规则与修订规则
   不同层）、冲突优先级（自由与安全高于证据高于进度）、外部批准预言机（用户批准不可在系统内
   导出）。第三个已在 `software-engineering-process.md` §4.2 明写，前两个只是隐含在实践中。
   未明写不破坏一致性，但使一致性成为**有条件的**结论。
3. **最小公理基为九条**。现行规则可归并到九条公理与八条推理规则；约三百六十处规范模态
   大多是其派生实例或同一公理在不同文档的重复落地。重复是防御性设计（一处漏改仍有多处拦截），
   代价是漂移风险，本仓库已用 `check-knowing-first.py` 一类“落点一致性”门禁对冲。
4. **规则集有一条关键的元规则**：门禁判据必须二值可判，不得使用“基本完成”“整体良好”
   （`software-engineering-process.md` §3、§8）。这是一条**可判定性卫生规则**，正是它使结构片段
   的充分性成立；本文 §8 把全部条款按可判定性分四档，第 IV 档由预言机与抽样承担，不以门禁冒充。

## 3. 形式语言 L_SE

**排序**（sorts）：

| 排序 | 元素 | 说明 |
|---|---|---|
| `Ag` | `u`（用户）、`a`（作者）、`v`（复核者）、`m`（代理） | 角色是帽子不是人，见 process §4.2 |
| `Ar` | FR、NFR、T（任务）、C（Check）、ADR、commit、test、artifact、measure、doc | 有限可枚举产物 |
| `G` | `G0 … G5` | 门禁 |
| `S` | 七值证据态 | `present ≺ wired ≺ exercised ≺ outcome-supported`；`missing`、`unobserved`、`not-applicable` 为不可比元 |
| `Cl` | 声明（对外能力主张、验收结论、发布说明） | 0 信任与 A1 的宾语 |
| `Tm` | 批次／时点 | 规则版本与复审触发随时间变化 |

**谓词与函数**：

```text
inScope(fr)                需求在范围内
hasTask(fr, t)             FR 与任务相连
hasCheck(fr, c)            FR 与验收点相连
evid(c, s)                 Check c 处于证据态 s
rank : S → N ∪ {⊥}         present 1、wired 2、exercised 3、outcome-supported 4；其余 ⊥
pass(g, inc, τ)            门禁 g 在增量 inc、时点 τ 通过
claim(x, d)                产物 x 声明 d
holds(c, inc, τ)           条款 c 在 inc、τ 被满足
approved(u, x)             用户批准 x
obs(e, x)                  证据 x 观察过事件 e
bound(c, n)                容器 c 的上限为 n
revise(r, τ')              规则 r 在 τ' 被修订
```

**模态与算子**：`O`（义务，对应“必须”）、`F`（禁止，对应“禁止／不得”）、`P`（许可，对应“可以”）、
`D`（默认义务，对应“默认值”，现行文本未使用独立模态）、`≻`（冲突优先级）、`¬`（否定）。
可废止性由 `D` 与 `≻` 表达，不由经典否定表达：一个默认义务被推翻不是矛盾，是优先级消解。

**关于语言的三点限定**（0 信任要求，不得把本文符号当作仓库事实）：

1. 仓库原文没有形式化语义，L_SE 是本文赋予的解释层；同一批条款可以有别的解释层。
2. 证据态的偏序 `≺` 与 `rank` 直接取自 `evidence-states.md` §2 与 `check_counts.py` 的枚举，
   这两处是原文与代码，不是我构造的。
3. `≻` 在本仓库只有零散表述（`AGENTS.md` §1.2 冲突判定、`design-principles.md` §15 共同失效条件），
   尚无全序；§10 缺口 G1 处理它。

### 4.1 公理（九条，互相独立，见 §6）

| 编号 | 名称 | 形式 schema | 原文来源 |
|---|---|---|---|
| A1 | 证据约束 | `claim(x, d) → ∃e (obs(e, d) ∧ independent(e))` | 宪法原则 VII；process §4.3；`philosophy.md` §6 |

## 5. 判定一：一致性

**定义**：系统一致当且仅当不存在条款 `φ` 使 `φ` 与 `¬φ` 同时可导。

**命题 1（切片一致）**：固定时点 `τ` 与规则版本，把 L_SE 解释到当前仓库状态
（谓词由 `traceability.py`、`check_counts.py`、`test_layering`、`test_layout` 的输出取值），
全部结构类公理与推理规则同时为真，因此该片段一致。

证明思路：结构片段是 Horn 型正条件集（不含否定后件与析取），存在模型即仓库事实本身；
§2 实测断链 0、幻影 0、计数一致，模型非空。空模型才是这类片段的不一致来源。

**冲突候选与处置**（逐项给原文，均可反驳）：

| 候选冲突 | 形式表述 | 是否矛盾 | 消解机制 |
|---|---|---|---|
| “禁止以最佳实践替代证据” vs “开工前必须研读标准” | `A1` 与标准研读义务 | 否 | 标准文本是**证据源**不是**权威源**；`standards-baseline.md` 判定列与 ADR-045 的“研究不承载承诺”已把研读产物的地位写明 |
| “0 信任不信任文档” vs “规则文档是规范源” | `A1` 应用于 A8 | 否，但需分层 | `philosophy.md` §9 第 5 项显式承认自指；分层见命题 2 |
| “禁止跨门禁跳跃” vs “紧急修复可先进 G3” | `R4` 与其例外 | 否 | 例外是**带条件的可废止规则**，条件（ADR＋用户批准＋列出被跳判据）在 process §2.2 写明 |
| “无超出证据的能力声明” vs “`v0.1.0` 已发布而 Check 464 仍 missing” | `A1` 与 R3 | 否 | 发布声明是**有范围的**：缺口公开登记且态为 `missing`，非伪装为 `exercised`；这正是 §2 表里 missing 1 的含义 |
| “作者不得单独批准自己的门禁” vs 单人项目 | `A9` | 否 | 角色是帽子；用户作为 `u` 是外部批准者，不违反 `A9` |

**命题 2（自指条款不可内嵌）**：A8 若与对象层规则同层，则 A8 约束自身，得到“A8 可被 A8
废除”，系统的正当性无法在系统内建立（循环辩护）。仓库实践已把它拆成两层：对象层规则
（门禁、判据）与元层规则（复审触发、删除条件），元层规则的成立依据是**行为改变**而非证据
（`knowing-before-doing.md` §7 第 2 项：“卡片字段从未改变任何决策即复审是否空壳”）。
这是可接受的解，但它意味着系统的可靠性锚点是实践效果，不是演绎闭合。

**结论**：一致性成立，条件有三——时点固定、结构片段、自指条款上移到元层。三项中只有第三
在文档里有部分表述（反教条条款），建议在 `philosophy.md` §9 显式声明分层（缺口 G4）。

## 6. 判定二：独立性

**定义**：公理 `A_i` 独立，若其余公理与推理规则不能导出 `A_i`。

**九条公理相互独立**（每给一条反模型思路）：

| 公理 | 反模型（去掉它后系统仍可满足） |
|---|---|
| A1 | 允许无证据声明的系统：全部门禁绿，声明仍可虚构——其余公理管不到 |
| A2 | 允许不可证伪需求：追溯与证据态仍可成立（判据存在但永不为假） |
| A3 | 允许不问就开工：任务认知卡被删后，R1—R7 无一条涉及意图确认 |
| A4 | 允许多写者：资源有界、证据约束都可满足 |
| A5 | 允许无界容器：分层与追溯不受影响 |
| A6 | 允许伪造输出：A1 只约束声明，不约束产出内容本身 |
| A7 | 允许锁定格式：安全与资源条款都可满足 |
| A8 | 允许永久真理：全部对象规则仍可满足，只是永不复审 |
| A9 | 允许自批：其余八条不涉及批准主体 |

**派生条款示例**（现行规则中可导出者，不独立）：

| 现行条款 | 导出 |
|---|---|
| 信号链完备三原则 | A1 ＋ A6（null 不是观察，故不构成证据） |
| 0 信任与三次复查 | A1（`independent(e)` 的展开）＋ A2 |
| 证据层级表 | A1 ＋ A2 |
| 不伪造工具结果、未知标 `unknown` | A6 ＋ R5 |
| 任务认知卡先于手段 | A3 |
| 前端不触库、SQL 只在 store | A4 |
| 有界队列与上限测试、RAII 释放测试 | A5 |
| 反教条条款、复审触发 | A8 |
| 用户批准是硬性项 | A9 |
| 拒绝评分制（`evidence-states.md` §4） | A1 ＋ A8（分数会把证据形态压缩成排序，诱导为分数补证据） |

**冗余度量**（防御性重复，不是逻辑冗余）：同一公理在多份文档的落地次数按实测——A1 族在
`AGENTS.md`、`philosophy.md`、`requirements-engineering.md` §3.1、`pr-checklist.md`、
`review-protocol.md`、`evidence-states.md`、`engineering-doctrine/` 六份中均出现；A3 族有
专用结构门禁 `check-knowing-first.py` 校验落点。结论：冗余是**故意的**，其代价是修订漂移，
本仓库的对冲手段是“落点一致性门禁”而非删除重复。逻辑上，这类重复不影响独立性判定，
因为被导出的都是同一 schema 的实例。

## 7. 判定三：相对完备性

**定义（相对完备）**：规则集 `R` 相对声明集 `Σ` 完备，当 `Σ` 中每一条声明的成立与否都能由
`R` 的某个判定程序在有限步内给出二值结论。不存在“相对一切”的完备性，只有相对某个 `Σ`。

**命题 3（结构片段相对完备）**：取 `Σ_s` = 有限可枚举产物上的义务集合（追溯三元组、
crate 依赖边、目录归类、文件计数与编号、证据态枚举、行尾与编码、i18n 键集一致、
action 引用与清单、ADR 必填字段、根文件白名单）。`Σ_s` 中每条义务都有对应判定程序，
实测断链为 0。因此 `R` 相对 `Σ_s` 完备。

**命题 4（语义片段不完备，且不可通过增门禁消除）**：取 `Σ_m` 含四类声明：

1. 用户意图是否被正确理解（A3 的宾语）；
2. 某设计是否为当前最优和解；
3. 威胁模型是否对威胁类全体完备；
4. 文档语义是否处处与代码事实一致。

对第 3 类构造论证：设有限门禁集 `G` 判定所有威胁声明。存在未登记的威胁类 `T*`（新平台、
新依赖、新协议语义），`G` 中无任一条款以 `T*` 为参数，故对 `T*` 的声明既不被支持也不被反驳，
按 R5 只能标 `unobserved`。故 `G` 不完备。第 1 类由 A3 直接给出：`approved(u, intent)` 是
外部预言机调用，其正确性不在系统内可判；第 2 类含未量化的“可接受”谓词（§2 末段）；
第 4 类只能在有限事实清单上判定（本仓库正是这样做的：`test_frontend_parity`、
`check-standards-baseline`、值层守卫测试各覆盖一份清单）。

**结论**：充分性成立的范围是 `Σ_s`，不成立的范围是 `Σ_m`；规则集对此是**诚实的**——
它以“用户批准”“缺口登记”“`unknown`”“抽样一致性”四种机制承认自己的边界，而不是宣称覆盖。
这是本文“条件性充分”结论的正面依据。

## 8. 判定四：可判定性

| 档 | 含义 | 本仓库条目 | 判定方式 |
|---|---|---|---|
| I | 可判定且已机械化 | `test_layering`、`test_layout`、`test_frontend_parity`、`fmt`／`clippy`／`test`、`traceability.py`、`check_counts.py`、`check-knowing-first.py`、`check-eol.py`、`check-docs-style.py`、`check-actions.py`、`check-adr-limits.py`、`check-standards-baseline.py`、`check-workflows.py`、`check-coverage.py`、`i18n-po.py --check`、`measure-resources.py`、`check-release.py` | 程序，退出码即结论 |
| II | 可判定但未机械化 | G0／G2／G4 的多数退出判据、ADR 的正负和解是否成立、八道质量门、发现四要件、评审调和纪律 | 人工二值判定，落点为文字＋行号；`review-protocol.md` 已把它写成可核对清单 |
| III | 半可判定（只可反驳） | “全部测试通过”（终止性不可判）、“无 open 安全告警”（依赖远端 API 可用，不可用时按 AGENTS §5.2 记“阻塞”）、跨平台性能结论 | 一次真实运行给见证，不给证明；这正是 ADR-037“验收以 CI 日志与 artifact 为准”的逻辑理由 |
| IV | 不可判定 | 意图正确性、设计优劣、威胁完备、文档语义全同、可用性 | 预言机（用户）＋统计（季度抽样一致性阈值 90%）＋显式标注，不得以门禁绿冒充 |

**命题 5（判定卫生）**：`software-engineering-process.md` §3 与 §8 要求判据二值可判、禁用
“基本完成”“整体良好”。形式上是把第 IV 档谓词从判据语法中排除。抽查 54 条退出判据，
这三处模糊词只出现在禁令中，未出现在判据本体。该元规则是结构片段充分性的直接原因：
它把可判定性变成书写要求，而不是事后审查要求。

**命题 6（第 IV 档的处理方式在逻辑上是替代而非解决）**：抽样、预言机与显式标注都不产生
判定程序。因此本仓库不能用“门禁全绿”代替 G4 的人工复核，也不能反过来。AGENTS §5.2 与
ADR-037 把这条边界写成纪律，逻辑地位与命题 4 一致。
