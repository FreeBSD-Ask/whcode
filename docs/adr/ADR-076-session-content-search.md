# ADR-076：会话内容关键词检索（P3.3 第一步，FTS 显式延后）

- **状态**：已批准（2026-11-15，proposal-v3 P3.3；用户指令“继续功能开发”）
- **来源**：`research/synthesis/proposal-v3.md` P3.3（“全文检索（session_overview 关键词先行，后 FTS）”，域 L，4—8 单元）；FR-746（侧栏标题/ID 搜索）；ADR-018（SQL 只在 store）
- **责任人**：会话与存储负责人
- **退出条件**：消息量级使 `LIKE`/`contains` 全表扫描不可接受，或 DuckDB 随包提供 `fts` 扩展时复审

## 1. 问题与边界

现状：侧栏搜索（FR-746）只匹配会话**标题与 ID**，用户无法按“聊过什么”找回会话。P3.3 要
补内容检索，并明确分两步：先关键词，后 FTS（全文索引）。

边界与事实：

- 本仓 `session_overview` 是**任务计数预聚合**（`by_stage_json/total/done/blocked`），没有
  summary 文本，故“session_overview 关键词”在本仓落地为“会话目录（元数据）关键词”——
  已由 FR-746 覆盖；P3.3 的实际缺口是**消息正文检索**；
- `messages.content_ref` 是当前唯一的持久化自由文本（user/assistant 正文）。事件
  `payload_json` 受追踪级别与脱敏管线影响（`redacted` 默认），不适合做检索面；
- DuckDB 的 `fts` 扩展**不在**预编译 DLL 内，加载需联网安装——与本地优先/离线可用冲突，
  故本批不做 FTS，登记为后续（§6）。

## 2. 决策

1. **检索语义**：`messages.content_ref` 上的**大小写不敏感子串**匹配（DuckDB `contains`，
   字面量语义——`%`/`_` 不当通配符），按消息时间倒序，最新命中优先。不做分词、不做
   相关性排序（关键词阶段的显式简化，登记在 §6）；
2. **有界性**（NFR-215／§7.1）：搜索词 1—128 字符；返回条数 1—100（默认 20）；每条命中只
   返回**定长片段**（80 字符，含命中位置，换行/控制字符折叠为空格），整段正文不进内存、
   不进界面、不落日志；
3. **分层**：SQL 只在 `whcode-store::search`（`search_messages`）；权限（`session.read`）、
   入参校验与 limit 夹取在 `whcode-app::search`（`search_session_content`）；前端只透传
   ——与 ADR-018／分层门禁一致；
4. **接口面**：
   - CUI：`whcode session search --query <关键词> [--limit N]`（新增子命令；JSON 信封含
     `hits`/`count`，人类输出为 ID/标题/角色/摘要表）；
   - Web：`GET /api/search?q=<关键词>&limit=N`（`session.search`；缺 `q` 为 400 参数错误，
     不静默返回全量）；
   - GUI：只读 v1 无搜索输入面，登记 `Reserved`（T319）；
   - TUI：终端列表视图不做内容检索，登记 `NotApplicable`（侧栏检索语义属 GUI/Web，FR-746）；
5. **与目录搜索并存**：内容检索不并入 `session_directory`（返回形状不同：目录行 vs 命中
   片段），避免把“过滤”和“命中”混成一种类型；
6. **空结果 vs 错误**：无命中返回空列表（正确的空）；空搜索词/超长/缺参数是显式错误
   （错误的空不得冒充“没有相关会话”）。

## 3. 正负和解

**正面**：不引入外部依赖即可按内容找回会话；有界、可测（store 6 项＋app 4 项＋CUI 1 项＋
Web 1 项）；片段定长，内存与带宽可控。

**负面与承担者**：

- 全表扫描：`contains` 无索引，消息量级大时延迟随表增长——由用户在 M9 规模下的实测承担，
  触发 FTS（§6）；
- 无相关性排序/分词：关键词阶段只做“最新优先”，对中文无分词能力（子串匹配对中文短词可用，
  长句不友好）——登记为限制，不自称为“全文检索”；
- 无跨会话聚合/高亮：片段只做首处命中。

**和解理由**：先给出“能按内容找回”的最小闭环，把 FTS 的依赖与性能问题留在可量化的
触发条件下，而不是提前引入联网扩展或自造索引表。

## 4. 三重时间

- **过去**：FR-746 侧栏搜索只覆盖标题/ID；proposal P3.3 明确“关键词先行，后 FTS”；
- **现在**：本批实现与测试（store/app/CUI/Web），抽查：中文与 ASCII 混合内容可命中、
  `%`/`_` 按字面量、片段有界；
- **将来失效条件与复审触发**（绑定命令＋判定）：消息表超过 100 万行且检索 p95 > 200 ms
  （用 `cargo test -p whcode-tests --test extreme_scale` 或新增夹具测）→ 复审本 ADR 并
  设计 FTS/倒排表；DuckDB 随包提供 `fts` → 重新评估外部依赖为零的 FTS 方案。

## 5. 回退方案

删除 `session search` 子命令与 `/api/search` 路由、移除 `search` 模块即可；数据无迁移
（纯读），回退不涉及 schema。

## 6. 已知限制与失效条件

- **不是全文检索**：无分词、无相关性、无高亮、无跨字段权重；对外文案不得称“全文检索”；
- **性能随消息量线性增长**：`contains` 全表扫描；触发条件与复审见 §4；
- **检索面只有消息正文**：任务标题/交付物/事件正文不在范围内（事件正文受脱敏影响）；
- **中文长句**：子串匹配要求连续字符，断行会漏检；
- **GUI 未实现**（Reserved，T319）：不得因 CUI/Web 已实现而声称四端对等。

## 7. 文献依据（标准研读记录，§1.6 口径）

- ISO/IEC 25010:2023（已登记，部分覆盖）：functional suitability 的 functional
  completeness/appropriateness——关键词检索作为“找回”能力的最小操作化；
- ISO/IEC/IEEE 15939:2017（已登记，已覆盖）：指标→测量→判定；本 ADR 的性能触发条件
  （p95 > 200 ms）即该链的 decision criteria；
- 一手文档：DuckDB 2.0 `contains` 函数（字面量子串、大小写敏感，需 `lower` 归一）；
  DuckDB 扩展机制（`fts` 需 `INSTALL/LOAD`，非随包）——两项均以本机实测确认（store 测试
  `percent_and_underscore_are_literal`）。

## 8. 形式审查

- **真实矛盾**：用户知道“聊过什么”却无法找回，只能靠标题记忆；而引入 FTS 会破坏离线前提；
- **正负和解**：见 §3，扫描代价与分词缺失显式，触发条件可判定；
- **0 信任校验**：语义（`%`/`_` 字面量、大小写、CJK）由 store 测试实证，非文档断言；
  片段有界由测试断言；
- **知难行易**：方向＝P3.3 关键词先行；目标＝CUI/Web 可检索消息正文且有界；手段＝
  `contains` 子串（不引入扩展）、片段定长——选型在确认“fts 不随包”之后。
