# ADR-025：性能预算冻结（Windows 11 amd64）

- **状态**：已批准（2026-10-23；冻结范围为 Windows 11 amd64，未测项保持候选）
- **来源**：D-06、NFR-201—NFR-210、V-006、SC-021、Task T027／T028／T055；
  ADR-010（平台承诺）、ADR-012（192 MB 过渡基线）、ADR-013（唯一验收平台）
- **责任人**：性能与存储负责人（决策）；基准夹具维护者（执行与归档）
- **退出条件**（任一触发即复审）：取得首个 BSD 原生运行证据；DuckDB 引擎或关键查询计划
  发生版本级变化；完成 5.5 小时时间序列（ADR-033）；用户环境基线与冻结夹具显著偏离（如逻辑核数、
  可用内存、持久化介质变化）

## 决策

1. **冻结范围**：预算只在 **Windows 11 amd64**（`x86_64-pc-windows-msvc`）上作为发布门槛。
   BSD 无运行证据，**不参与**冻结，平台矩阵标注“未验证”，不得与他平台合并或平均。
2. **冻结值沿用 spec 候选值**（NFR-201—210），不因实测偏低而放宽：实测优于预算即视为达标；
   劣于预算则进入优化待办，**不得修改预算掩盖**。修订预算须另立 ADR 并附同夹具前后对比。
3. **冻结依据**为固定夹具与归档证据（下表“证据”列，均在 `artifacts/` 内可复现）。
4. **未测项保持“候选”**：NFR-201／202／203／205／206／209 尚无合规测量，登记责任人与
   退出条件（发布前补齐，或按第 2 条以 ADR 修订），不得以“未复现失败”代替测量。
5. `memory_limit`（192 MB）仍是 DB 缓冲管理器的过渡基线（ADR-012），**不等于**进程 RSS 预算。

## 历史基线（不构成冻结）

- `artifacts/baseline-windows-amd64.json`（2026-10-21 05:40 UTC）：写入吞吐中位
  **158 条/秒**，聚合 p95 12 305 µs。该样本低于 NFR-210 候选值，已在平台矩阵登记偏差；
  其后同夹具优化（写者改为分块查键 + 分块多行插入、插入前分配连续 `seq`）在 384 MB 组
  达到 3 359 条/秒、192 MB 当前口径达到 6 921 条/秒。三次结果**不得**合并平均，
  冻结采用 192 MB 当前口径，历史值保留以备回归对照。

## 理由（正负和解）

- **正面**：把“未冻结”的长期模糊状态收敛为可判定的发布门槛；两项已达标的预算立即
  可用于回归拦截；未测项有责任人与退出条件，避免“看起来达标”。
- **负面**：Windows-only 冻结会让 BSD 用户缺少本平台的性能承诺；按 spec 候选值冻结
  可能偏严，后续开发会被较紧的预算拦住。
- **承担者**：性能负责人（补齐未测项）、后续功能开发者（受预算约束）、BSD 用户
  （无预算承诺，只有“未验证”标注）。
- **和解理由**：先用唯一验收平台把口径锁死，比维持“候选”更有用；偏严可通过
  ADR 修订放宽，而“无预算”无法被任何门禁拦截。

### 判据失效的量化理由

5.5 h 窗口内，0.5 MB/h 对应的可观测漂移为 2.75 MB，而本次序列自身 σ = 3.17 MB（峰谷
30.11—47.32 MB）；OLS 斜率 SE ≈ 0.22—0.25 MB/h。要在 95% 单侧置信下证明“≤0.5 MB/h”，
需观测斜率 ≤ 约 0.13 MB/h。另以 2:1 信噪比要求计算，0.5 MB/h 趋势需 ≥20 h 窗口才可辨。
即：≤0.5 MB/h 源自 72 h 前提（ADR-016 §4 的 V-006 冻结条件），ADR-033 把窗口缩到 5.5 h
（13 倍）而“预算值不变”，但未做分辨力分析，导致判据与观测窗不匹配。
本地 10 分钟对照（release、无趋势、σ 1.27 MB）被同一“首末差值”口径判成 6.201 MB/h，
是该估计量无效力的直接演示。

### 建议的预算处置（供批准决定，三选一或组合）

- **方案 B（判据修订，推荐；与分析文件 §9 的选项 B 同义）**：冻结值 0.5 MB/h **不改**，只把
  NFR-204 改为组合判据：
  1. **泄漏项（主判据）**：预热后（丢弃前 10% 样本）且按事件行数相位对齐的斜率 ≤ 0.5 MB/h，
     报 95% CI；
  2. **有界项**：`Var(y_{t+k}−y_t)` 在 k ≥ 10 样本处不高于 k = 1 处（比值 ≤ 1.0），且线程数、
     句柄数全程不增；
  3. **绝对项**：峰值 RSS ≤ 80 MB（沿用 NFR-202 的单会话活跃上限，本次 47.32 MB）；
  4. **判定带**：首末差值口径落在 0.5—1.0 MB/h 记“无权判定”，须 24 h 本机深检；
     >1.0 MB/h 记违反。1.0 = 0.5 + 2 × 0.25（实测分辨力）由噪声推导，**不得**用本次实测
     斜率反推阈值。
  5. **前提**：release 构建 + 施加 `SET memory_limit`／`SET threads` + 完整 JSONL；前提未满足
     的长跑不产生判定。
- **方案 C（复测优先；分析文件选项 A′+C）**：不改判据，先修夹具保真度（施加包络、记录编译
  类型/OS/引擎版本）、改 `--release` 重跑 5.5 h；若同口径仍超预算，再进方案 B。代价：多一轮
  5.5 h runner 配额。
- **方案 A（优化优先）**：以降低锯齿幅度为优化目标（缩小清理事务峰值、降低每行常驻成本），
  验证方式：同夹具前后对比的相位对齐斜率与峰值 RSS，且不得以“debug 数据”作前后判据。
  当前无热点证据，ADR-020 已否决分配器替换方向，故本方案暂不具备可执行前置。

**推荐**：方案 C 的夹具保真度修正（它同时是方案 B 的前提），再取同口径证据，最后按方案 B 立 ADR
（即分析文件的组合处置 D：A′ → C → B）。

### 为什么原判据不可判

1. 现行口径是夹具的首末差值 `(y_last − y_first)/(t_last − t_first)`。它不是斜率估计量，而是
   噪声放大器：本地 10 分钟 release 对照中，RSS 在 ±1.3 MB 内平稳震荡，同一口径仍算出
   +6.201 MB/h（`artifacts/nfr204-disposition-2026-10-25.md` §5）。
2. 5.5 h 窗口对 0.5 MB/h 无可判分辨力：预算对应的可观测漂移为 0.5 × 5.5 = **2.75 MB**，
   小于该序列自身噪声 σ = **3.17 MB**（样本标准差；总体 σ 3.14）。全样本最小二乘的
   SE 为 0.224 MB/h（预热后子集 0.254—0.293），95% CI 半宽 0.45—0.59 MB/h，与预算同量级。
3. 由 2 可得两条硬结论：要在 95% 单侧置信下**证明**“≤0.5 MB/h”，观测斜率须 ≤ 约 0.13 MB/h；
   当真值恰在 0.5 MB/h 时，按单侧 5% 水平宣称达标的概率至多 0.05——判据对边界值天然难以给出通过。
4. 因此，基于本次 5.5 h 序列**既不得宣称达标，也不得宣称失败**；本轮只能登记
   “按现行口径超预算、判据无权判定”。

### 提议的组合判据

冻结值 0.5 MB/h 不变；把 NFR-204 的判定改为“前置条件 + 五要素 + 三态结论”。

**前置条件**（任一不满足即记“无权判定”，并登记缺口，不得产出达标/失败结论）：

- **release 构建**（`cargo test --locked --release`），summary 必须记录 `build_profile`；
- **300 s 采样**（ADR-033），窗口 19 800 s，**有效样本 ≥ 60**；
- **单 PID**：全程 `pid` 唯一且无重启记录，`pid` 必须随样本归档；
- `event_missing = 0`（全程，非仅末样本）；
- **线程数与句柄数全程恒定**：允许预热期一次性下降（如 22→21），之后不得再变。

**五要素**（须同时报告，缺一不得判定）：

1. **RSS 最小二乘斜率** s 及其 95% 置信区间：预热后子集（丢弃前 10% 样本），并按事件行数相位
   对齐（与上一节方案 B 第 1 条同义）；
2. **首末斜率** `b_fl`：仅作交叉核对，不作主判据；
3. **线程/句柄全程恒定**：给出全程序列与任何变化点；
4. **`event_missing = 0`**：给出逐样本计数；
5. **噪声带宽**：σ（样本标准差）与 bootstrap（成对重采样 ≥ 10 000 次）95% CI，并显式给出
   本窗口可分辨的最小斜率 `1.645 × SE`。

**三态结论**（阈值不新增）：

- **通过**：s 的 95% 上界 ≤ 0.5；
- **违反**：s 的 95% 下界 > 0.5；
- **无权判定**：区间跨越 0.5（含点估计超预算但区间含 0.5）→ 登记“按现行口径超预算”，并升级
  24 h 深检；不得写成通过，也不得写成失败。

**冲突条款**：若 `b_fl` 与 s 的结论不一致（例如一个 ≤0.5、另一个 >1.0），强制记“无权判定”，
先排查清理周期、进程重启与采样缺口，再谈趋势。

**分辨力披露**：报告必须写明“本窗口在本轮噪声下能证明的上界”。按本轮 SE ≈ 0.22 MB/h，
认证通过要求 s ≤ 0.5 − 1.645 × 0.22 ≈ 0.13 MB/h；即当前噪声水平下 5.5 h 基本无法证明达标，
只能证伪或存疑。若连续两轮长跑仅产出“无权判定”，须改用更长窗口或降低噪声（缩小清理振幅），
不得继续消耗 runner 配额。

### 对本轮运行（run `40154046118`）的适用

按本节判据，本轮结果为**无权判定**，理由是三项前置不满足：debug（`test` profile）、
`pid` 未随产物归档、未施加 `SET memory_limit`／`SET threads` 包络；且写者队列两项指标为
`null`。现行口径的超预算登记（0.6987／0.943 MB/h）保留，但不构成本判据下的失败结论。
数值、公式与复算方式见 `artifacts/nfr204-adr025-proposal-2026-10-25.md`。

### 正负和解

- **正面**：判据可判定且三态明确；把“通过”与“无权判定”分开，杜绝把噪声写成趋势（本地对照
  已出现 12 倍预算的假斜率）；不调大阈值，符合本 ADR 决策 2“不得修改预算掩盖”。
- **负面**：直接后果是 5.5 h CI 在当前噪声下几乎只能给出“无权判定”，达标结论将依赖 ≥20 h
  深检或降低清理振幅；组合判据增加分析与字段维护成本（summary 增字段、样本带 `pid`、
  需 bootstrap 与功效计算）；判定周期变长。
- **承担者**：性能与稳定性负责人（实现字段、判定脚本与深检）；发布决策者（接受更长的证据
  周期）；后续功能开发者（噪声一旦上升会更频繁触发“无权判定”）。
- **和解理由**：现行二值判据在数学上无分辨力，继续使用只会把噪声写成达标或失败；三态判据把
  不确定性显式化，符合“未知不得默认为确证”的既有纪律。

### 失效条件

1. 噪声结构改变（清理阈值/周期、写入速率、行宽、分配器行为）使 SE 显著减小或增大，须按新噪声
   重新推导最小可辨斜率；
2. ADR-033 的窗口或 GitHub runner 时限变化；
3. DuckDB 引擎或 `memory_limit`／`threads` 默认值变更；
4. 连续两轮长跑仅产出“无权判定”（说明判据未解决分辨力，须换窗口或换测量对象）。
