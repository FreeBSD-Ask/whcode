# ADR-063: 迁移前自动备份、SHA-256 校验与有界保留（P3.4）

- **状态**：已批准（2026-11-08，路线级批准见 ADR-059 决策 1；本条为 Phase 2 的 P3.4）
- **日期**：2026-11-08
- **关联**：ADR-059（终态路线全量采纳）、ADR-037（CI 唯一验收入口）、ADR-002（store 为唯一写者边界）、
  ADR-013（Windows 11 amd64 验收平台）、ADR-015（并发设计档案，本 ADR 不需要——见决策 7）；
  `specs/001-whcode-harness/data-model.md` §5、`spec.md` NFR-103、`docs/guides/disaster-recovery.md`；
  `research/dsh-comparison/`（域 L：备份/恢复）、`research/zcode-comparison/`（域 L：SHA-256 与预迁移备份）。
- **编号说明**：`research/synthesis/proposal-v3.md` P3.4 行把载体写作“修订 ADR-038”；复核发现
  ADR-038 是**会话归档的确认与审计口径**，与备份无关。本 ADR 按“无既有承载 → 新立”处理，
  不改动 ADR-038。

## 问题

1. **升级没有退路**：`apply_migrations` 只在事务内逐版本应用；迁移失败会回滚该版本，但**没有
   迁移前的可恢复副本**。data-model §5 与 NFR-103 要求“schema 迁移前生成可恢复备份或确认已有
   备份”，此前只有用户手工 `copy` 文件这一条外部约定（`disaster-recovery.md` §3），
   工具侧不提供、也不记录。
2. **备份没有完整性证据**：手工复制的文件无法证明“复制完整”。导出通道（`db archive --export`）
   有分块 FNV 校验和，但那是 JSON 导出，不是可直接回退的库文件。
3. **副本会无限累积**：若每次启动都复制，目录随启动次数线性增长——违反资源铁律中的有界性口径。

## 决策

1. **时点与判定**：只在“库文件已存在、`schema_migrations` 存在、且 `MAX(version) <
   STORE_SCHEMA_VERSION`”时复制一次。新库（迁移表未创建）、同版本重开、版本高于目标（降级场景）
   均不复制——不制造无意义副本，也不在降级时假装“备份过”。
2. **位置与命名**：`<workspace>/backups/<库文件名>.v<四位迁移前版本>-<十三位毫秒>.bak`。
   时间戳零填充到十三位，保证目录内文件名字典序＝时间序（裁剪依赖该性质）。
   先写 `<目标>.partial` 再改名：崩溃只会留下不参与校验与裁剪的半截文件。
3. **完整性**：复制同时以 64 KiB 缓冲流式计算 SHA-256（内存不随库大小增长），落盘后核对字节数；
   `verify_backup(path, expected)` 可复算比对，不符返回 `invalid_state` 且消息含期望/实际摘要。
   口径与导出校验和一致：**只防意外损坏，不防蓄意篡改**（无签名）。
4. **有界保留**：`backups/` 只保留最近 [`MAX_BACKUPS`](../../crates/whcode-store/src/backup.rs)（5）份，
   超出按文件名时间序删除最旧副本；目录扫描上限 256 条，防止异常目录拖住启动。
5. **fail-closed**：`CHECKPOINT` 或复制任一步失败即返回错误，调用方**不得继续迁移**。
   宁可启动失败，也不出现“无备份却已升版”的状态。
6. **时序（Windows 专属约束）**：备份必须在打开主连接**之前**执行。DuckDB 在 Windows 上以独占
   方式持有库文件，连接存续期间 `File::open` 得到 sharing violation（实测 `os error 32`）。
   因此 `whcode_store::pre_migration_backup` 自带短生命周期连接：读版本 → `CHECKPOINT`
   把 WAL 合入主文件 → **`drop` 连接释放句柄** → 复制。备份因此包含最近一次提交。
7. **并发纪律**：不新增线程、不新增后台任务，只在启动路径同步执行一次；不需要 ADR-015
   并发设计档案。代价是启动时多一次“打开—读版本—关闭”的往返（仅版本落后时触发）。
8. **不改恢复路径**：恢复仍是两条既有通道——`db restore --from`（导入到空库，JSON 导出）
   或文件级还原（停进程后覆盖库文件）。本 ADR 的备份文件属后者：回退时先备份现场，
   再用 `.bak` 覆盖 `whcode.duckdb` 并删除同名 `.wal`。

## 正负和解

- **正面**：升级第一次有工具侧的可恢复点与可复算校验和；目录有界；失败时阻断而非静默；
  不需要用户记住“迁移前先手工 copy”。
- **负面**：启动路径多一次文件复制（库大小 × 1 次写盘，仅版本落后时）；备份与工作区同盘，
  磁盘故障或误删会同时失去两份；`backups/` 未加密；备份不是“定期快照”，只是迁移前那一刻。
- **承担者**：使用者（升级时多一份磁盘占用，最多 5 份）；存储维护者（保留策略与扫描上限）；
  装配根维护者（时序约束：必须在主连接之前调用）。
- **和解理由**：迁移是不可逆的结构变更，而“备份可恢复”是 data-model 已写明的既有要求；
  把外部约定落成程序行为，成本是一次阻塞复制，收益是失败可回退。资源铁律的约束通过
  “只在版本落后时触发 + 保留 5 份 + 64 KiB 缓冲”满足。

  “无启动期完整性校验、无自动备份、无快照保留策略”。
- **现在证据**：`crates/whcode-store/src/backup.rs`（5 项测试）、`crates/whcode-bin/src/workspace.rs`
  （接线与端到端备份测试）、Check 375 取证记录；验证命令见下节复审触发 1。
- **将来失效条件与复审触发**（绑定命令 + 判定规则，ADR-046 口径）：
  1. `cargo test -p whcode-store backup` 或 `cargo test -p whcode-bin workspace` 不再全绿 →
     复审实现与接线；
  2. 工作区不再是单文件库（改用附加库、多文件布局或外部存储）→ 文件级复制口径失效，
     复审并改为 `ATTACH` + `COPY FROM DATABASE` 或导出通道；
  3. DuckDB 在目标平台不再独占库文件（可共享读）→ 复审“必须在主连接之前”的时序约束；
  4. `backups/` 实际条目数超过 `MAX_BACKUPS` 或出现 `.partial` 残留累积 → 复审裁剪与扫描上限；
  5. proposal-v3 P3.4 追加 CLI 面（备份列表／校验／还原演练命令化）→ 本 ADR 修订，
     把演练从测试提升为用户可执行命令；
  6. 2027-05-07（与 D15 覆盖率复审同批）→ 复查保留份数与触发时点是否匹配真实升级频率。

## 已知限制

- **只覆盖迁移前时点**：不做定期快照、不做手动“立即备份”命令；用户想在任何时刻留档仍走
  `db archive --export`（JSON 导出，可跨版本带离）。
- **不防篡改**：SHA-256 只证明“复制与读取一致”，不提供签名或来源认证；备份文件与库文件
  权限相同，任何能改库文件的主体也能改备份。
- **不跨磁盘容灾**：备份目录与库文件同在 `<workspace>/backups/`，同盘故障、误删工作区、
  勒索加密都会同时影响两者。
- **不加密**：与本地优先一致，静态加密由用户的操作系统/磁盘层负责。
- **旧版本兼容边界**：备份是 DuckDB 文件副本，能否被打开取决于 DuckDB 自身的前向兼容；
  回退到旧版二进制是安全路径，用新版打开旧备份不承诺。
- **恢复仍手工作业**：`.bak` 不能经 `db restore --from` 回灌（该入口吃导出 JSON）；
  回退按 `disaster-recovery.md` §3 的文件级流程执行。
- **门禁只校验结构**：本 ADR 的“已知限制／失效条件”节由 `check-adr-limits.py` 检查是否存在，
  不校验内容是否充分。
