# ADR-011：平台承诺修订——OpenBSD 与 DragonFly BSD 改为经内置 SSH 客户端控制

- **状态**：已批准（2026-10-21，用户决策；tasks.md T028/T030、D-13）
- **来源**：《WHCode 技术任务书 v3.0》§9 平台矩阵、§12.1 M0 退出条件、R-02；ADR-005、ADR-010；`docs/adr/ADR-DB-BUILD.md` 的平台结论
- **责任人**：平台矩阵负责人（决策）；落地维护：`whcode-ssh` 维护者
- **退出条件**：M7 交付完整客户端能力并取得四平台证据（OpenBSD/DragonFly 的客户端连通性与受限命令执行，FreeBSD/NetBSD 另含服务端验收）；在此之前客户端只以 M0 风险原型存在，不得表述为已交付
- **批准依据**：2026-10-21 用户四项决策之三（平台承诺修订）；`tasks.md` T028/T030 要求以 ADR 记录平台承诺变更（V-006/V-007）；`docs/adr/ADR-DB-BUILD.md` 记录官方预编译 DuckDB 包仅覆盖 Windows，FreeBSD/NetBSD 的获取路径尚未定案，OpenBSD/DragonFly 无原生路径

## 决策

1. OpenBSD（`x86_64-unknown-openbsd`）与 DragonFly BSD（`x86_64-unknown-dragonfly`）**不再作为原生安装目标**。WHCode 不在其上安装原生二进制，也不要求其具备 Rust 与 DuckDB 原生的构建链。
2. 两类平台改由 WHCode **内置 SSH 客户端**控制：建立连接、执行受限命令、取回有界输出，并按 ADR-007 的“意图记录—执行—结果登记”协议登记。
3. `whcode-ssh` 的职责由“服务端入口”扩展为“**客户端 + 服务端**”；服务端仍在 M7（tasks.md T096—T099），M0 只交付客户端风险原型（T025）。
4. 客户端安全边界（默认值，M7 不得放宽）：
   - 默认公钥认证，不接受口令；
   - 仅执行白名单命令或受限入口，不提供任意系统 Shell；
   - 不继承本地敏感环境变量与凭据；
   - 输出有界（上限与截断策略须可查询，NFR-107）；
   - 每次执行有超时与取消；
   - 执行前登记意图，执行后登记退出状态与输出摘要；无法判定是否完成时记 `unknown`（ADR-007）；
   - 主机密钥校验：M0 原型**未实现**（`check_server_key` 恒接受），M7 必须补齐；未补齐前不得宣称具备中间人防护。
5. 需求与验收修订（`specs/` 由需求基线维护，本 ADR 只记录并引用，不修改该目录）：
   - **FR-611** 已写入 `specs/001-whcode-harness/spec.md`（P1）：WHCode 提供内置 SSH 客户端，连接 OpenBSD 与 DragonFly BSD 目标、执行受限命令并取回输出；单次执行须有超时与输出上限，并按 ADR-007 登记。该需求服务于本 ADR 的平台承诺修订，不阻塞首个可用版本。
   - **FR-607** 已同步为“FreeBSD/NetBSD 提供 SSH 服务端；OpenBSD/DragonFly 由内置 SSH 客户端控制”。
   - **V-004** 的判据由“四 BSD 服务端验收”改为“FreeBSD/NetBSD 服务端验收 + 四平台客户端连通性/命令执行证据”。M0 只完成客户端原型，四平台均**无**证据。

## 理由

- R-02 要求“不得以单一 BSD 测试代替四 BSD”，而这四类平台的 Rust 与 DuckDB 原生依赖可用性差异大：`ADR-DB-BUILD.md` 记录官方预编译包仅覆盖 Windows，FreeBSD/NetBSD 须依赖 ports 或源码构建，OpenBSD/DragonFly 无可用路径。
- 内置客户端可在不落地原生产物的前提下提供控制能力，避免为两类平台维护第二套构建、打包与发布链。
- 将“控制面”与“原生安装面”分离后，平台承诺可按实测证据分级陈述，不再以“BSD”作无限范围承诺。

## 约束与影响

- 平台矩阵：OpenBSD/DragonFly 的角色列为“经 SSH 客户端控制”，构建状态“不适用”，运行验证“M0 无证据”（见 `docs/matrices/platform-matrix.md`）。
- 追溯关系：ADR-005 的平台覆盖与 V-004 判据随之修订；ADR-010 的“跨 BSD 可构建”结论只对 FreeBSD/NetBSD 保留，且仍为阻塞。
- 安全：客户端依赖 `russh` 0.64.1 已引入，但主机密钥校验、命令白名单、输出上限与凭据隔离均未实现；不得把原型能力写成已交付，也不得把 D-04 的公钥认证描述扩大到客户端已验证。
- 里程碑：M0 交付客户端风险原型；完整能力与四平台证据属 M7。

## 替代方案

- **为 OpenBSD/DragonFly 维持原生构建**：需每平台自建 DuckDB 与 C 工具链，并承担 ports 版本与 crate 绑定版本不一致的风险，构建面与维护成本高；`ADR-DB-BUILD.md` 已记录该路径仅作为候选保留。
- **仅用外部 `ssh` 人工操作**：无法满足“意图—执行—登记”协议、审计留痕与输出有界，也不能复用应用服务的权限模型。

## 退出条件

M7 交付完整客户端能力（公钥认证、主机密钥校验、命令白名单、超时、输出上限、按 ADR-007 登记）并取得四平台证据；任一平台失败须记录明确阻塞原因，不得以单一平台代替（R-02）。

## 批准记录

- 批准日期：2026-10-21（用户决策）。
- 修订关系：ADR-005（SSH 平台覆盖）、ADR-010（OpenBSD/DragonFly 判定）、`docs/matrices/decisions.md` 的 D-04 与 D-13。
- 未决项：四平台客户端连通性与受限命令执行证据缺失（现有测试为回环测试）；主机密钥校验未实现；命令白名单、输出上限与凭据隔离仅有设计约束，未实现。
