# ADR-012：`memory_limit` 基线复核——192MB 的 OOM 断言未被独立复现

- **状态**：部分批准（2026-10-21；对 T027 断言的证伪证据充分，但“冻结 192MB 基线”的证据不足，未决条件已列明）
- **来源**：《WHCode 技术任务书 v3.0》§5.2（测量纪律）、§5.4（数据库配置基线）、NFR-301—NFR-306；tasks.md T027、T028；`crates/whcode-bin/src/bench.rs` 的 `MEMORY_LIMIT` 注释；`crates/whcode-bin/src/config.rs` 的 `DEFAULT_MEMORY_LIMIT_MB`
- **责任人**：存储与基准负责人（决策）；落地维护：`whcode-store` 与基准夹具维护者
- **退出条件**：M1 基准校准在更大载荷、更长负载与临时目录异常条件下复核本结论；在此之前 192MB 只是“未复现失败”的过渡基线，不得表述为已冻结的性能结论
- **判定依据**：`tests/integration/test_memory_limit.rs`（`#[ignore]` 实验记录器）于 2026-10-21 的实际运行输出；`artifacts/memory-limit-experiment.json`；运行期 DuckDB 引擎 `v1.5.6`；rustc 1.99.1（`x86_64-pc-windows-msvc`）；Windows 11 10.0.26300，i7-1260P（12 物理核 / 16 逻辑核），内存约 16.9 GB；测试为 debug 构建
- **未决条件**：T027 未留下 OOM 错误原文与触发点，原始失败条件无法重建；本实验未覆盖接近单条载荷上限的数据、长时稳定性、进程 RSS 与多平台

## 问题

T027 的基准夹具实现者在代码注释与报告文字中报告：“`memory_limit = 192MB` + `threads = 4` 时，写入约 1000 条事件触发 DuckDB OOM，因此夹具改用 §5.4 的候选最大值 384MB。”

该断言此前只存在于文字中，没有错误原文、触发位置与可复现条件。本 ADR 要回答三个问题：

1. 该断言在可复现条件下是否成立；
2. §5.4 的默认值 192MB 是否可用，是否需要改为 384MB 或其他值；
3. `DEFAULT_MEMORY_LIMIT_MB` 是否需要调整。

## 方法（可复现）

- 运行命令：`cargo test -p whcode-tests --test memory_limit -- --ignored --nocapture`
- 写入路径：`whcode_store::EventWriter`（与真实路径一致，不自造 SQL 写入路径），批次行数上限 500、时间窗口 3,600,000 ms（只由行数阈值触发提交），与 `bench.rs` 的固定夹具一致。
- 数据：主对照每组 2000 条 `StreamingChunk` 事件，payload 为 `{"text":"x"×120}`（JSON 131 字节），持久化等级 `redacted`；另设规模探针 20000 条（`whcode bench baseline` 的默认事件数）。
- 数据库：临时目录下的**文件库**，每组独立文件；`threads = 4`。
- 每组用 `SELECT CAST(current_setting('memory_limit') AS VARCHAR)` 与 `current_setting('threads')` 回读，确认设置真的生效（V-001 报告纪律），并按 1% 容差校验回读值与请求值一致。
- 每组结束后关闭写连接，重新打开执行显式 `CHECKPOINT`，统计事件行数与数据库文件字节数。
- 本测试是**实验记录器**，不是断言器：OOM 发生与否都不判失败；只断言“设置已生效”与“写入条数统计自洽”（库内行数 + 待写条目数 = 已发起写入条数）。
- 局限（明确标记）：
  - `EventWriter` 独占连接，无法在写入期读取缓冲管理器瞬时占用；DuckDB 拒绝同一进程二次打开同一数据库文件（实测报错 `File is already open in ... (PID ...)`），因此本实验不记录该指标，也不以进程 RSS 代替；
  - 单机单次样本、debug 构建、payload 固定为 131 字节；不构成跨平台结论。

## 实测证据

2026-10-21 实际运行，全部四组均无 DuckDB 错误：

| 组 | 设置 | 回读（`current_setting`） | 事件数 | 成功 | 首个失败 | 结果 | 错误原文 | `CHECKPOINT` | 文件字节 | 墙钟 |
|---|---|---|---:|---:|---|---|---|---|---:|---:|
| 192MB | `192MB` | `183.1 MiB` | 2000 | 2000 | 无 | 未触发 OOM | 无 | 成功 | 1,060,864 | 296.2 ms |
| 384MB | `384MB` | `366.2 MiB` | 2000 | 2000 | 无 | 未触发 OOM | 无 | 成功 | 1,060,864 | 272.6 ms |
| 1024MB | `1024MB` | `976.5 MiB` | 2000 | 2000 | 无 | 未触发 OOM | 无 | 成功 | 1,060,864 | 252.2 ms |
| 192MB@20000（规模探针） | `192MB` | `183.1 MiB` | 20000 | 20000 | 无 | 未触发 OOM | 无 | 成功 | 1,847,296 | 4068.4 ms |

补充读数：

- 三组主对照的数据库文件字节数完全相同（1,060,864 字节），说明在该数据规模下 `memory_limit` 的取值没有改变写入结果或文件规模；
- 墙钟仅作记录，单次样本不构成性能结论：首轮运行时首组出现 1118.1 ms 的冷启动开销，复跑后消失；本次记录取复跑值；
- 规模探针写入 20000 条后文件为 1,847,296 字节，`CHECKPOINT` 成功，无错误。

结论：**在 131 字节 payload、2000 条与 20000 条、`threads = 4`、文件库、DuckDB v1.5.6 的条件下，192MB 下没有复现 OOM，也没有任何失败写入。T027 的 OOM 断言未被独立复现。**

## 取证要点与可能解释

**取证要点一：183.1 MiB 不是用量证据。** 192MB 按 MiB 表示为 183.1 MiB（384MB 为 366.2 MiB，1024MB 为 976.5 MiB）。T027 记录中的“缓冲管理器用满 183.1 MiB”与配置上限的回读显示值完全一致；在没有原始错误文本的情况下，无法区分它是 `current_setting('memory_limit')` 的回读值还是实测峰值用量。本实验在 192MB 组的回读值同样是 `183.1 MiB`，可作对照。

**取证要点二：没有错误原文。** 本实验没有产生 DuckDB 错误，T027 也未留下错误原文，因此无法按原文比对两次失败是否同源。这本身是证据缺口，不是对本实验结论的反驳。

**可能解释（均未验证，不得当作结论）：**

- **载荷规模不同**：若单条 payload 接近 `MAX_PAYLOAD_BYTES`（1 MiB），500 行批次约 500 MiB，192MB 上限可能不足；本实验单条仅 131 字节，相差约 8000 倍。这是最可能的原因。
- **临时目录不可写或受上限约束**：DuckDB 在缓冲管理器满且无法溢写时报 OOM。本实验使用系统临时目录且可写；若原探针的临时目录不可写或受限，失败点会显著提前。
- **并发与规模不同**：同一进程内多个数据库实例、更多事件、多个 run 共用实例等，均会改变内存占用；本实验每组使用独立文件库、顺序执行。
- **版本与构建差异**：原探针的引擎版本与构建类型未记录；本实验为 DuckDB v1.5.6、debug 构建。
- **断言可能来自另一条写入路径**：如直接用 SQL 写入、内存库或不同的批次策略，而非本例的 `EventWriter`。

按报告纪律，三组主对照与规模探针的结果全部列出，不因“未复现”而删去任何一组，也不挑选有利数据。

## 决策

1. **保持 `DEFAULT_MEMORY_LIMIT_MB = 192`，不修改 `crates/whcode-bin/src/config.rs`。** 依据：在可复现条件下 192MB 完成了 2000 条与 20000 条写入，没有失败；没有任何数据支持把默认值提高到 384MB。§5.4 的候选最大值 384MB 仍然保留为用户可配置上限。
2. **不把 384MB 表述为“已冻结基线”。** 决策已落地（同日）：`bench.rs` 的 `MEMORY_LIMIT` **改回 192MB**（即 §5.4 基线默认值），注释中的 OOM 理由已替换为“未复现”的更正记录，并复测确认可用（见下节）。任何引用旧注释的文档不得再把 OOM 断言写成事实。
3. **保留可复跑的实验记录器。** 新增 `tests/integration/test_memory_limit.rs`（`#[ignore]`）与 `tests/Cargo.toml` 的 `[[test]]` 目标声明；结果落盘 `artifacts/memory-limit-experiment.json`。它不进入常规定时 CI，需要手工 `--ignored` 运行。

## 替代方案

- **立即把默认值改为 384MB**：本轮证据不支持；只有在 M1 用更大载荷或更长负载复现失败时才采用。
- **改为其他值（如按载荷动态设定）**：缺少实测边界数据，当前无法定值；须由 M1 校准给出。
- **保持 192MB 但继续沿用 T027 的 OOM 说法**：会让未经证实的结论继续传播，违反报告纪律，不可接受。

## 影响

- `whcode-bin/src/config.rs` 的 `DEFAULT_MEMORY_LIMIT_MB`：**不需要改**；本 ADR 未修改该文件。
- `whcode-bin/src/bench.rs` 的 `MEMORY_LIMIT`：**已改为 `192MB`**（2026-10-21 落地，见下节），夹具现在测量默认基线而非未验证的放大值。
- 测试与 CI：新增 `memory_limit` 测试目标，标注 `#[ignore]`，`cargo test --workspace` 不运行它；不增加常规 CI 时间。
- 证据：`artifacts/memory-limit-experiment.json`（含环境、夹具、四组结果与结论）。
- **口径约束（§5.2）**：`memory_limit` 只约束 DuckDB 缓冲管理器，**不代表** WHCode 进程 RSS 上限；本 ADR 的任何数值都不得被解释为进程内存上限或性能预算。

## 决策落地与复测（2026-10-21，同日）

按决策 2 选定“把夹具改回 192MB 以测量默认基线”，并对同一固定夹具复测：

- 命令：`whcode bench baseline --out artifacts/baseline-192mb.json --events 20000 --repeat 3`
- 构建：release；DuckDB v1.5.6；`memory_limit` 回读为 192MB 对应值、`threads = 4`。
- 结果：吞吐 7 427.5 / 6 921.2 / 6 242.1 条/秒，中位数 **6 921.2 条/秒**；关键事件延迟（600 样本）p50 **3 942.7** / p95 **5 586.7** / p99 **10 994.8** µs；每次 20 200 行落库，库文件 1 847 296 字节，无 OOM。
- 对照：同一夹具在 384MB 下的上一轮结果为 3 359.1 条/秒、p50 6 975.4 µs（`artifacts/baseline-after-opt.json`）。

**口径约束（不得过度解释）**：192MB 组的吞吐高于 384MB 组，但这只是**单机、单次会话、三样本**的观测，不能推断“降低 `memory_limit` 会提速”。两者差异可能来自缓冲策略、页面回收时机或运行噪声；要下因果结论必须做受控重复实验（M1 校准）。本 ADR 仅确认：**192MB 在 20 000 条规模下可用且无 OOM**，因此夹具没有理由使用未经验证的 384MB。

## 退出条件

M1 基准校准必须完成以下事项后，才可冻结或修订该基线：

1. 覆盖更大载荷（至少包含接近单条 1 MiB 上限的载荷）与更长写入负载；
2. 记录 `temp_directory` 配置、可写性与磁盘余量，并验证溢写路径；
3. 取得缓冲管理器用量的**直接证据**（DuckDB OOM 原文或受控诊断读数），不得以 `current_setting` 回读冒充峰值；
4. 在本机重复运行并保留错误原文，按平台分别报告；
5. 届时根据数据决定：冻结 192MB、改为 384MB，或采用其他取值。

## 批准记录

- 批准日期：2026-10-21。
