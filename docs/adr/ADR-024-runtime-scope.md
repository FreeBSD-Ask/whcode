# ADR-024：M8 运行时范围与验收口径

- **状态**：已批准（2026-10-23）
- **来源**：D-07—D-09、FR-701—FR-710、V-301—V-307、Task T100—T114；ADR-008
  （受控子进程，不嵌入不受信任脚本）、ADR-013（Windows 11 amd64 唯一验收平台）
- **责任人**：运行时负责人
- **退出条件**：Python worker 与 Git Bash payload 的验收证据齐备后转“已交付”；
  若要引入内置 JS 引擎、改变 payload 分发方式或新增运行时依赖，必须另立 ADR 并附
  基准（RSS／体积／许可证／启动时延）与回退路径

## 决策

1. **JS 不交付引擎**。`JsProvider` 以 `Restricted` 声明能力，任何执行请求返回结构化
   `runtime_unavailable`（能力不足 + 不支持项清单），不得崩溃、不得静默降级；
   UI、门禁输出与文档不得把它表述为 Node.js 兼容（D-08）。
2. **Python 以子进程 worker 交付**。必须记录解释器**绝对路径、版本、实现名
   （CPython/PyPy 等）、ABI 标签、依赖与 C 扩展探测结果**，并列出不支持项；
   执行统一经 `worker`（超时、输出上限、取消、输出尾部保留、凭据环境剥离）。
3. **Git Bash 走独立 payload**。payload 不随主二进制分发；安装校验为
   “来源白名单 + 版本 + 哈希 + 平台”四重；执行覆盖管道、重定向、含空格路径、
   信号终止、目标命令五类，哈希可核验（V-304）。
4. **不引入新依赖**（Boa／RustPython 等内置引擎）：以能力不足的错误路径替代。
5. **装配依赖边界**：`whcode-bin` 可依赖 `whcode-runtime`，但仅用于**读取能力声明与
   探测**（`runtimes::inventory`、`doctor`、Web `/api/runtimes`）；不得在请求路径加载
   动态库、启动常驻子进程或注册工具（FR-704 不变，Check 103 继续据此判定）。

## 理由（正负和解）

- **正面**：维持“资源占用优先”——内置 JS 引擎会带来常量级 RSS 与启动开销，
  与本项目“空闲态不得随会话数线性增长”的纪律相冲突；保持零新增供应链与
  零 `unsafe` 包装；Windows-only 验收下，跨平台引擎的收益无法被本仓库验证。
- **负面**：JS 场景不可用，用户需自行改用外部工具；Git Bash 需要用户提供 payload。
- **承担者**：需要 JS 的用户与被要求“一个二进制全搞定”的部署者。
- **和解理由**：错误信息可操作（说明缺什么、怎么补），比“半个 Node.js”更诚实；
  若真实需求增长，可由新 ADR 携带基准重开，而不是现在预付不可验证的成本。

## 替代方案（已否决）

- **内置 Boa／RustPython**：新增依赖、许可证与体积成本，且无可信 Windows 基准；
  以“主流选择”替代测量与边界，不符合本项目证据要求。
- **继续维持“引擎待接入”的模糊状态**：正是 V-302／Check 153 长期无法判定的原因，
  状态不明确会让门禁与文档互相矛盾。

## 影响

- Check 110（能力不足而非崩溃/静默）与 111/154（Python 指纹与不支持项）**可验证**；
- Check 153 的判据（“受限 JS 通过固定 ECMAScript 测试集”）在本 ADR 下**不可满足**，
  维持未通过；如需修订 spec V-302，应按本 ADR 走需求变更，而不是悄悄改判；
- Check 112/155 取决于 Git Bash payload 证据；
- Check 114 的 V-304 项仍以 payload 校验与五类命令证据为准，不因本 ADR 豁免。

## 复审触发

1. 用户明确提出 JS 运行时需求，且给出可比基准场景；
2. Git Bash payload 进入发布包（届时需补分发、校验与升级路径）；
3. Windows 之外出现可运行的验收平台（ADR-013 变更）；
4. 现有 Python 子进程方案出现无法在契约内解决的安全问题（届时优先收紧而非扩展）。
