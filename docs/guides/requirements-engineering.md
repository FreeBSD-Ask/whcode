# 需求工程规范

**日期**： 2026-10-21（2026-10-29 增补 §2.1 任务认知卡先于 FR） | **依据**： ISO/IEC/IEEE 29148:2018、SWEBOK V4.0（需求知识域） | **适用**： 全部 FR/NFR

## 1. 需求生命周期

| 阶段 | 活动 | 本仓库落点 |
|---|---|---|
| 获取（Elicitation） | 用户指令、任务书、Issue、运行反馈 | `spec.md` Input 行；`.github/ISSUE_TEMPLATE/` |
| 分析（Analysis） | 冲突识别、边界划分、优先级、影响面 | `spec.md` Assumptions / Edge Cases；`decisions.md` |
| 规格化（Specification） | 编号、陈述、判据、归属 | `spec.md` FR/NFR；按本文件模板 |
| 验证（Verification） | 可测性审查、追溯检查 | `checklist.md` 的 Check |
| 管理（Management） | 基线、变更、追溯 | `tasks.md`、ADR、git tag、`CHANGELOG.md` |

## 2. FR 模板（必须六要素齐全）

```text
- **FR-<编号>**: <一句话陈述“系统必须…”>（P0/P1；交付归属 M<n>）
  - 判据：Given <前置>，When <动作>，Then <可观察结果>
  - 证据：<产物路径或测试名>
  - 依据：<任务书条款 / ADR / 用户指令>
```

**质量判据**（ISO 29148 的“良好需求”特征，逐条可判）：

| 判据 | 含义 | 反例（本仓库历史） |
|---|---|---|
| 无歧义 | 只有一种合理解读 | “尽可能快” |
| 可验证 | 有客观判据与证据 | “192MB 会 OOM”（未复现、无错误原文） |
| 可追溯 | 能向上追溯到来源、向下到任务与验收 | 只写 FR 未挂到 US/Check（曾发生：FR-612—615 未挂 US6） |
| 不绑定实现 | 说“做什么”，不说“用哪个库” | “必须用 React”（应表述为交互与预算） |
| 有优先级 | P0/P1 明确 | 全部 P1 等于没有优先级 |
| 有边界 | 明确不做什么 | 未声明 32 位平台是否在范围内（已由 ADR-013 补齐） |

## 2.1 任务认知卡先于 FR（宪法原则 X）

写 FR 之前先写任务认知卡：方向、目标、用户意图复述、非目标/边界、现有证据、手段（后置）。
FR 必须从认知卡的目标派生；手段（工具、框架、库）不得写成 FR。歧义处标 `[须提问]`，
按 `docs/guides/signal-chain-completeness.md` §2 的提问义务处理。字段与判定规则见
`docs/guides/knowing-before-doing.md` §3。

```text
方向（一句话：用户要改变什么/得到什么）：
目标（可判定；与验收判据一一对应）：
用户意图（复述；歧义标 [须提问]）：
非目标/边界（至少一条）：
现有证据（用户原话/工单/日志/复现命令）：
手段（后置；不构成需求，可替换）：
```

## 3. 追溯

三方编号约定：

- 需求：`FR-xxx` / `NFR-xxx`（`spec.md`）
- 任务：`Txxx`（`tasks.md`），任务行内注明来源 FR
- 验收：`Check xxx`（`checklist.md`），每 Check 注明来源 FR 与 Task

**抽查方法**（每里程碑执行一次，结果记入 PR 描述）：

```powershell
# 以 FR-617 为例：反查任务与 Check
findstr /n "FR-617" specs\001-whcode-harness\spec.md
findstr /n "FR-617" specs\001-whcode-harness\tasks.md
findstr /n "FR-617" specs\001-whcode-harness\checklist.md
```

任一处缺失即为断链，必须补齐后才可过 G1 复核。

## 3.1 证据层级与三次复查

需求与验收证据按可信度分层：

| 层级 | 证据 | 使用规则 |
|---|---|---|
| 1 | 代码、commit、测试、遥测 | 优先；可复现 |
| 2 | 邮件/issue/聊天记录 | 交叉验证；注意选择性 |
| 3 | 官方文档/发布说明 | 可能经过筛选 |
| 4 | 复盘/采访/博客 | 记忆重构；需一手支撑 |
| 5 | 二手研究/百科/AI | 不得作为唯一证据 |

三次复查：**查证**（回到一手）→ **交叉验证**（至少两个独立来源）→ **判定**
（确证/存疑/无法核验）。无法核验时标 `[待验证]`，不得默认为确证。

## 4. 变更控制

```text
提出（用户/缺陷/风险）
  → 影响分析（哪些 FR、任务、Check、测试、文档、CI）
  → 记录（ADR 新增；或 decisions.md 决策项变更）
  → 批准（用户明确同意；口头同意也必须落文）
  → 更新基线（spec/tasks/checklist 同步）
  → 打标签（如需基线快照）
```

规则：

1. **不得**只改实现不改需求（行为变了但 FR 未更新）——属过程违规；
2. **不得**只改需求不改验收（新增 FR 无 Check）——属断链；
3. **不得**以“以后补”关闭变更；未完成项必须保留在 `tasks.md` 且不得勾选。

真实案例：

- **ADR-013**（平台收敛）：影响 spec US1/Assumptions、`platform-matrix`、四个 CI workflow、README、
  `m0-report` 口径；批准后历史结论标注为“修订前证据”，而非删除。
- **ADR-012**（OOM 断言证伪）：不改默认值（缺反证），改夹具并保留实验记录器；旧断言在注释中
  标注为“未复现”，**不静默删除**历史。

## 5. NFR 与测量纪律

NFR 必须写明：指标、目标值、测量方法、测量条件（OS/硬件/编译类型/工具链/依赖版本/数据规模/
采样窗口/脚本）。分位数不得用平均值替代；不同平台不得合并平均（§5.2）。

当前状态：NFR-201—210 为**候选目标**，预算未冻结；冻结条件见 `docs/matrices/platform-matrix.md`。

- [ ] 每条 FR 有编号、优先级、归属里程碑
- [ ] 每条 FR 有可执行判据（Given/When/Then 或等价）
- [ ] 每条 FR 至少挂一个任务与一个 Check
- [ ] 范围外事项与延后事项有书面记录（ADR/Assumptions）
- [ ] 未验证项标注 `[待验证]` 且不得表述为已交付
