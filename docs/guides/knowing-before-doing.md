## 2. 命题

1. 主要困难在“知”：用户要改变什么、目标是什么、成功判据是什么、边界与非目标在哪里。这四项答不出，后续实现都只是猜测。
2. 手段是次要且可替换的变量：语言、库、框架、命令、目录结构都属手段；手段必须在“知”之后确定，且不得写进需求，否则一次工具更换会被误判为需求变更。
3. 知未完成就开工，等于用行动制造证据替代理解：动作越多越像在推进，产出越多返工越大。T116 的 72 小时白跑风险是同一结构——脚本能跑、输出格式合法，但“要测什么”没写清，null 就被读成“空闲期正确行为”。
4. 知不是一次性的：行动中发现“知”有误，要回到知修正方向陈述，而不是在错误方向上加速。
5. 知难行易不等于“先想很久再动”：可逆小步允许快速试错，但方向陈述不可跳过；不可逆决策（数据格式、协议、权限、并发）必须设计先行并留回退证据。

## 3. 任务认知卡

开工前填写，字段顺序固定；括号内是取值要求：

```text
方向（一句话，可判定；写要改变什么，不写怎么做）：
目标（一句话，可判定；至少对应一个 Check 或验收判据）：
用户意图（复述用户要解决的真实问题；须可被用户确认，不能确认标 [须提问]）：
非目标/边界（至少一条；写不做什么，以及不可越过的边界）：
现有证据（来源 FR、Check、实测或复现命令；未知标 [待验证]）：
手段（后置；晚于前五项填写，且不构成需求，可替换）：
```

判定规则：

1. 方向与目标各一句且可判定；目标至少对应一个 Check 或验收判据（`specs/001-whcode-harness/checklist.md`）。
2. 意图复述可被用户确认；不能确认时标 `[须提问]` 并提问（提问义务见 `docs/guides/signal-chain-completeness.md` §2，歧义无法用对照场景区分时不得默认）。
3. 非目标至少一条。
4. 手段必须晚于前五项填写，且不构成需求。

全部任务适用：已勾选任务以其来源 FR、验收判据与实现记录作为最小“知”证据，不补写；未勾选任务开工前写卡；任务块末标注卡的位置（不拆断跨行任务描述），口径依 `specs/001-whcode-harness/tasks.md` 的“全局执行前置”条款。

## 5. 反例

1. 先选工具／框架再补需求：先定框架或库，再反向编写“为什么需要它”的需求；手段被写进需求，替换成本被隐藏。
2. 把用户一句话当作已知：把“做个 TUI”直接展开为实现，不确认用户要解决的是可追踪还是可审计；意图未被确认即当已确认。
3. 用忙碌替代方向确认：连续提交、跑通构建、写长文档，方向陈述仍然缺失；行动量成为“理解”的替身。
4. 把 Code is cheap 读成无需想清楚：把“代码便宜”当作“先写再说”的许可；源文紧接着说的是“Show me the talk”，提出问题的价值高于堆代码。
5. null／空／零被合理化为正确行为（T116）：脚本三次冒烟全 null，被写成“空闲期正确行为”，实际没有被测进程；72 小时白跑的风险直到用户追问才暴露。
6. 歧义自行假设后大规模实现：需求有歧义时按自己的推断铺开实现，方向错了才发现，返工覆盖全部产出。
7. 为已勾选任务补写认知卡充历史证据：事后回填卡片，充作当时已理解；这是伪造证据（NFR-220），并让门禁失去判别力。

## 6. 正负和解

| 项 | 内容 |
|---|---|
| 正面 | 减少白跑与返工；用户可早期纠偏；验收判据在开工前就存在 |
| 负面 | 前置澄清耗时；小任务显得繁琐；提问可能打断用户 |
| 承担者 | 提出者承担澄清成本；用户在早期承担确认成本，换取后期少返工 |
| 边界 | 可逆低风险小改动可压成一行（方向、目标、非目标）；紧急故障可先处置，但同一批次补卡；不可逆决策（数据格式、协议、权限、并发）不得裁剪 |
| 和解理由 | 返工成本高于澄清成本，且有 T116 实测失败案例；但不把认知卡变成新仪式——答不出就标 `[待验证]` 并提问，不伪造 |

与既有原则的关系：0 信任——不信任自己对用户意图的推断，意图须由用户确认；信号链完备 §2——歧义无法区分时必须提问；一刻哲学第 17 章——证明世界先于改造，先验证问题与世界模型再动代码；反忙碌——不以行动量替代理解；可逆性分级——可逆快决、不可逆设计先行（与 ADR-015 的“设计先行”同口径）；三重时间——认知卡须写过去来源（FR、实测）、现在证据与将来失效条件（何时复审）。

## 7. 复审触发

1. `python .github/scripts/check-knowing-first.py` 失败即复审本文：落点被删、链接断裂、字段缺项均判失败，判据是“本文落点与仓库事实不一致”。
2. 连续两个变更批次写不出认知卡，或卡片字段从未改变任何决策，即复审字段是否过度或空壳；判定规则是“删除多余字段或降级本文”。
3. 用户判定本文已不改变开工行为，即删除或降级。
4. 源数据库 SHA256 变化即复核 §1 引用：重跑 §1 回查代码块，逐条比对 `file_id` 与 `block_index`；不一致即改写引用。
5. 每年至少一次复核；日期只作辅助，判定以第 1—4 条的命令与事实为准。

## 8. 局限

本文与门禁只保证认知卡存在与落点完整，不保证认知正确；正确性只能由用户确认与后续证据检验；填了卡片不等于理解了任务，不得以其宣称理解正确。门禁是结构检查，不是语义审查；`[待验证]` 字段不因卡片存在而转为已确认。

本文登记的落点已全部落地并由 `.github/scripts/check-knowing-first.py` 校验；该门禁只验结构完整，不验语义正确。落点被删除或链接断裂时，按 §7 第 1 条复审本文，不得改门禁迁就漂移。
