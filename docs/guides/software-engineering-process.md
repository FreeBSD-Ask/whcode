# 软件工程过程规范：迭代增量与 G0—G5 门禁

**日期**：2026-10-21 | **适用**：WHCode 全部里程碑（M0—M9）与全部变更 | **强制级**：里程碑推进必须有门禁证据

本文件把教科书式软件工程过程落到本仓库的**具体文件、命令与证据**上。它不是对
`specs/001-whcode-harness/spec.md` 的替代：需求冲突以 spec 为准，架构冲突以 ADR 为准，
过程冲突以本文件为准。本文件也不构成任何能力已交付的声明。

**规范依据**：

- ISO/IEC/IEEE 29148:2018：需求工程与 SRS 内容、需求属性；
- IEEE 1016：软件设计描述（SDD）的设计视图；
- SWEBOK V4.0：需求、架构、设计、构造、测试、配置管理、工程管理等知识域；
- ISO/IEC 25010:2023：产品质量模型（SQuaRE）；
- Parnas 信息隐藏与模块化、SOLID、KISS/YAGNI、关注点分离、契约式设计。

## 1. 目的、范围与判定用语

### 1.1 目的

1. 让每个里程碑都能回答四个问题：**输入是什么、做了什么、留下什么产物、凭什么判定通过**。
2. 让单人 + AI 代理的项目形态仍保留“评审”的实质：可执行门禁、证据留档、对抗式复核、
   用户批准，而不是以“看起来没问题”代替判定。
3. 让教科书产物与本仓库文件形成**双向映射**：从标准条款能定位到文件，从文件能说明它服务哪条标准。

### 1.2 判定用语

| 用语 | 含义 |
|---|---|
| 必须 | 门禁的强制条件；缺失即不得通过 |
| 应当 | 默认要求；偏离必须在 ADR 或门禁记录中说明理由 |
| 可以 | 可选做法，不构成通过条件 |
| 证据 | 可由第三方重复执行的命令输出、带环境条件的测量结果、带路径与行号的审查结论、带哈希的产物 |
| 声明 | 对外表述的能力或结论；没有证据的声明不得写入 README、发布说明或验收结论 |

### 1.3 范围与边界

- 覆盖：立项、需求、设计、实现、测试、集成、验收、发布、归档、变更控制。
- 不覆盖：语言教程、库 API 手册、运行时调优细节；这些由 `specs/`、`docs/adr/` 与代码内文档承担。
- 当前唯一验收目标是 Windows 11 amd64（ADR-013）。BSD 平台“延后”不等于“已支持”；
  任何 BSD 结论都必须来自该平台的真实构建与运行证据，见 `docs/matrices/platform-matrix.md`。
- 不考虑任何 32 位平台；门禁不得把 32 位结果纳入结论。

### 1.5 哲学基线

所有门禁共用 `docs/guides/philosophy.md` 的核心命题。工程上落为六项强制记录：

| 项 | 要求 |
|---|---|
| 形式主义审查 | 写明形式、矛盾、边界；答不出“不做会怎样”即不得实现 |
| 正负和解 | 正面、负面、承担者、和解理由；不得只写收益 |
| 三重时间依据 | 过去来源、现在证据、将来失效条件与复审触发 |
| 0 信任校验 | 报错、文档、外部事实与自身结论均须独立复核；单一来源不构成通过 |
| 自由审查 | 退出/导出/离线/默认值可撤销；无暗黑模式与强制账户/联网 |
| 安全审查 | 威胁模型、攻击面、证据、代价、失效条件；禁止以“最佳实践/合规”替代 |

**非教条条款**：现行硬约束（零 `unsafe`、Windows 唯一验收、禁用 GNU 工具、极简前端等）
是当前和解，不是永恒最佳实践；变更走 ADR，并写明复审条件。

**可移植版本**：本规范的方法论已抽到 `engineering-doctrine/`，可直接复制到其他项目；
本文件保留 WHCode 的具体落地与证据。

**一刻哲学补充**：`docs/guides/yike-philosophy.md` 把源文本翻译为六条工程规则：不伪造、反进步叙事、反苦难、自反文档、和解优先、去神圣化。G1/G2/G4/G5 分别检查假设与复审日期、文档自反、测量程序、知识过时登记。

## 2. 过程模型：迭代增量 + 阶段门禁

### 2.1 为什么不是瀑布

WHCode 的需求基线覆盖 M0—M9，但每个里程碑都独立产出可验收增量。因此采用**迭代增量**：
每个里程碑走一遍 G0—G5；范围变化时重新进入 G0，需求或设计变化时重新进入 G1/G2。
门禁不是一次性文档审批，而是**每个增量都可重复执行的最小充分检查**。

```text
             ┌──────────────── 变更控制（ADR / decisions）────────────────┐
             │                                                              │
             ▼                                                              │
G0 立项与范围 → G1 需求基线 → G2 设计基线 → G3 实现与单测 → G4 集成与验收 → G5 发布与归档
     ▲                              │                              │
     └──────── 范围变化时回流 ──────┴──────── 缺陷修复回流 G3 ─────┘
```

### 2.2 门禁与里程碑的关系

| 关系 | 规则 |
|---|---|
| 每个里程碑 | 必须依次经过 G1—G5；G0 在项目启动时执行一次，范围变化时重开 |
| 并行分支 | 可以并行开发，但每个分支在合并前必须补齐其所属增量的 G3 证据 |
| 门禁跳跃 | 禁止；例外必须走 ADR 并由用户明确批准，且在门禁记录中列出被跳过的判据 |
| 返工 | G4 发现需求或设计缺陷时回流 G1/G2，不得只在实现层打补丁 |
| 紧急缺陷 | 可先进入 G3 修复，但必须在同一提交内补需求/验收引用与 `CHANGELOG.md` 记录 |

### 2.3 当前里程碑位置

M0 已产出构建、依赖记录、数据库冒烟、写者基线、TUI 逻辑层与 SSH 客户端原型；Windows 侧
判定为 **Go**。但 M0 整体仍**未通过**，原因是：

- V-003 的交互式终端人工项未全部取得（resize 重绘与 Ctrl-C 仍待真实终端确认）；
- V-004 的服务端验收未开展（M0 仅完成客户端原型，四平台连通性属 M7）；
- V-006 的候选性能预算未冻结（缺跨平台与 72 小时数据）。

G5 已打标签 `v0.1.0-m0`，但 README 明确“未发布”。因此 M0 的准确表述是：
**G3 大部分完成、G4 部分通过、G5 标签已打但发布未宣称**。

### 2.4 过程裁剪规则

裁剪不等于跳过证据。不同变更类型的最低门禁如下：

| 变更类型 | 必须通过 | 可以裁剪 | 不可裁剪 |
|---|---|---|---|
| 纯文档/指南 | G3 的目录门禁、EOL 审计；G5 的变更记录（对外可见时） | G1/G2 的完整评审 | 链接与事实可核对 |
| 实现缺陷修复 | G3 全部门禁；涉及验收语义时补 G4 | 新的需求条目（若行为未变） | 失败路径测试、`CHANGELOG.md` 修复段 |
| 需求/范围变更 | G0 重开、G1、G2、G3、G4 | 无 | 用户批准、ADR、追溯更新 |
| 平台/依赖变更 | G0、G2、G3、G4 | 无 | ADR、平台矩阵、供应链校验 |
| 紧急修复 | G3；事后补 G1/G4 | 先修复后补文档 | 审计记录、用户知情、不得静默跳过 |

## 3. 门禁细则 G0—G5

每个门禁按六段写：输入、活动、产物、退出判据、评审方式、当前证据与缺口。退出判据均为
二值可判，不使用“基本完成”“整体良好”等表述。

### 3.1 G0 立项与范围

| 项 | 内容 |
|---|---|
| 输入 | 用户指令、技术任务书、现有仓库状态、平台与资源约束、已知风险 |
| 活动 | 界定问题与目标；列出范围内/范围外/非目标；确定平台与验收目标；识别外部依赖与阻塞；指定角色与决策人 |
| 产物 | `README.md` 的平台范围；`spec.md` 的 Input/Assumptions；范围类 ADR（如 ADR-013）；`docs/matrices/decisions.md` 的决策项（如 D-14）；`docs/guides/repository-layout.md` 的目录边界 |
| 退出判据 | 1）范围有书面结论；2）范围外事项逐条列出；3）平台承诺精确到 OS 版本 + 架构 + 目标三元组；4）外部阻塞有登记；5）用户批准记录可定位；6）纳入与排除项的代价承担者已写明 |
| 评审方式 | 用户批准（必须有原话或 ADR 批准记录）；架构角色检查范围与任务书是否矛盾；AI 代理以“找范围漏洞”为目标做对抗式复核 |
| 当前证据 | ADR-013 批准、D-14、README 平台表、ADR-011 |
| 缺口 | 无独立项目章程（charter）；范围结论分散在 README、spec 与 ADR，需读者自行拼接 |

### 3.4 G3 实现与单元验证

| 项 | 内容 |
|---|---|
| 输入 | G2 产物、任务清单、测试位置约定 |
| 活动 | 编码；单元测试与失败路径测试；静态检查；文档同步；任务状态更新 |
| 产物 | `crates/**`、`tests/**`、测试输出、`CHANGELOG.md` 条目、必要的模块文档更新 |
| 退出判据 | 1）`cargo fmt --all --check` 无差异；2）`cargo clippy --workspace --all-targets -- -D warnings` 零告警；3）`cargo test --locked --workspace` 全部通过；4）新增行为至少有一个正向与一个失败路径测试；5）`test_layering` 与 `test_layout` 通过；6）未完成任务不得勾选；7）`[待验证]` 不得以推断关闭；8）测试包含证伪路径，而非仅证明实现正确；9）并发实现有模型/差分/压力验证，汇编有回退与差分测试 |
| 评审方式 | 可执行门禁；`docs/guides/pr-checklist.md` 逐项；AI 代理按“反例优先”审查；涉及安全、权限、恢复的改动必须由用户复核 |
| 当前证据 | 154 例测试通过、0 失败；fmt/clippy 全绿；写者服务、迁移、游标分页、索引基准、概览预聚合与监控已补齐 |
| 缺口 | 无独立人类代码评审记录；TUI 人工交互项不能由单元测试替代 |

### 3.7 门禁记录的最小字段

每个门禁完成后，记录至少包含：

| 字段 | 要求 |
|---|---|
| 门禁 | G0—G5 之一 |
| 增量 | M0—M9 或具体变更编号 |
| 输入版本 | 相关文件路径 + commit 哈希 |
| 执行人/角色 | 作者、复核者、批准者分别标注；单人时说明合并规则 |
| 判据结果 | 逐条通过/不通过，不写“基本通过” |
| 证据 | 命令、输出摘要、产物路径、环境条件 |
| 未通过项 | 原因、影响、补做任务编号 |
| 批准 | 用户或授权角色；口头批准必须落 ADR/decisions |
| 形式审查 | 形式、矛盾、正负与承担者；空壳形式不得进入下一门禁 |
| 时间依据 | 过去/现在/将来依据与复审触发 |
| 0 信任 | 独立复核方式与原始证据位置；单一来源不算证据 |
| 并发/汇编 | 并发档案、文献依据、验证计划与回退；汇编须独立 ADR 与差分包 |

## 4. 角色、职责与合并规则

### 4.1 角色职责

| 角色 | 主要职责 | 不得做的事 |
|---|---|---|
| 产品负责人（用户） | 范围、优先级、验收与发布批准；强制放行的最终决定 | 不得以口头意见替代需求变更记录 |
| 架构负责人 | ADR、依赖方向、契约、数据所有权、技术风险 | 不得绕过 ADR 改变默认后端或平台承诺 |
| 开发负责人 | 实现、单元测试、失败路径、文档同步 | 不得把未验证能力写进 README 或验收结论 |
| 测试与质量 | 测试计划、验收判据、证据审计、追溯抽查 | 不得用“测试全绿”替代未执行的验收项 |
| 发布负责人 | 标签、变更记录、发布说明、可复现性 | 不得改写已发布标签或删除历史证据 |
| 安全负责人 | 权限、秘密、依赖许可、SSH/Web 边界 | 不得以“后续补”关闭安全缺口 |

### 4.2 单人 + AI 代理的合并规则

本项目当前是**单人 + AI 代理**，不假装存在独立评审委员会。合并规则如下：

1. **角色帽子必须显式声明**：同一人可以在不同门禁扮演不同角色，但记录中必须写清
   “作者/复核者/批准者”，不得混写。
2. **作者不得单独批准自己的门禁**：单人项目下，批准必须由用户以范围、验收或发布决策的
   形式给出；没有用户批准时，门禁只能记为“未通过”。
3. **可执行门禁优先**：能用测试、脚本、契约检查判定的，不得用文字评审代替。
   `test_layering`、`test_layout`、`cargo test`、`cargo clippy` 是硬证据。
4. **证据留档替代部分独立性**：评审结论必须能落到文件路径、行号、命令输出或产物哈希；
   不能落到“我看过了”。
5. **AI 代理不是独立评审人**：AI 可以起草、对照标准找缺口、以反例为目标审查、整理证据；
   AI 的结论必须可核验，且不得作为安全、平台承诺、性能预算的唯一批准依据。
6. **安全与平台承诺必须人类签收**：涉及权限、秘密、SSH/Web 对外监听、平台范围收敛的
   变更，必须由用户明确批准并写入 ADR 或 decisions。
7. **冲突时升级**：作者与复核者同一人且意见不一致时，按“证据优先”处理；仍不能判定时，
   登记为 `[待验证]` 并保留两种说法，不得强行二选一。
8. **补偿控制的边界**：上述机制是**补偿控制**，不等价于独立人类评审、外部审计、
   渗透测试或可用性测试；这些仍是已知缺口（见 §9）。

### 4.3 评审证据的最低形态

| 证据类型 | 最低要求 |
|---|---|
| 命令证据 | 命令全文、执行目录、输出摘要、退出码 |
| 测量证据 | OS/硬件/编译类型/工具链/依赖版本/参数/数据规模/采样窗口/脚本 |
| 产物证据 | 文件路径、生成命令、哈希或版本号；易变产物须可再生成 |
| 审查证据 | 文件路径 + 行号 + 判据条款编号；不得只写结论 |
| 用户批准 | 原话可定位，或 ADR/decisions 中的批准记录与日期 |

findstr /n "^- \*\*FR-" specs\001-whcode-harness\spec.md | Measure-Object
findstr /c:"Check " specs\001-whcode-harness\checklist.md | Measure-Object

## 7. 变更控制

任何**需求或范围**变更：提出 → 影响分析（FR/任务/Check/测试/文档）→ 记录（ADR 或
`docs/matrices/decisions.md`）→ 用户批准 → 更新基线 → 打标签。任何**实现级**缺陷修复：
直接进 G3，但必须在 `CHANGELOG.md` 的“修复”段落登记。任何**性能或安全**相关变更：
必须附测量条件或威胁分析（§5.2、§10）。

| 变更类型 | 最低影响分析 | 记录 | 批准 |
|---|---|---|---|
| 需求/范围 | FR ↔ 任务 ↔ Check ↔ 测试 ↔ 文档 | ADR 或 decisions + spec 修订 | 用户 |
| 架构/依赖 | C-01—C-08、契约、平台矩阵 | ADR + plan/data-model/contracts | 用户（平台/安全类必须） |
| 实现缺陷 | 测试、`CHANGELOG.md` | 修复段 | 主开发者（安全类用户复核） |
| 性能基线 | 测量条件、分位数、对比 | ADR 或修订记录 + `artifacts/` | 用户 |
| 文档/流程 | 链接、目录门禁、EOL | `CHANGELOG.md`（可观察时） | 主开发者 |

真实案例：

- **ADR-013**：平台范围从“五平台”收敛为 Windows 单目标 → 影响 spec US1、平台矩阵、CI、
  README 与 `AGENTS.md`；批准后重打基线口径，历史结论文档标注为“修订前证据”。
- **ADR-012**：T027 的 OOM 断言未复现 → 不改默认值，改夹具并补实验记录器；**不得**沿用旧断言。
- **ADR-014**：前端极简决策 → 影响 UI 预算、CI 审计与 `ui-design.md`；预算值进入验收清单。

## 8. 过程自检（每个里程碑收尾）

1. 本门禁的产物是否全部存在且可链接？
2. 退出判据是否**可判定**（不是“基本完成”）？
3. 未取得证据的项是否在 `m0-report.md`/`checklist.md` 明确标注？
4. 变更是否都有 ADR/`CHANGELOG.md` 记录？
5. 门禁命令是否全绿（含分层、目录、EOL、workflow 自检）？
6. 计数与追溯是否一致（FR、任务、Check 三处数量与编号）？
7. 结论是否超出证据范围（尤其平台、性能、安全）？

七项任一为“否”，不得进入下一门禁。

## 9. 已知缺口

| 缺口 | 影响 | 处理方向 |
|---|---|---|
| 无独立第三方评审 | 安全、平台承诺、预算的独立性弱 | 用户签收 + ADR + 证据审计；重大变更引入外部复核 |
| 无正式 CR 表单编号 | 变更历史依赖 ADR 编号 | 保持 ADR 唯一编号；必要时新增 CR 模板 |
| 无独立测试计划文档 | 测试范围与风险覆盖不集中 | 以 `checklist.md` 与 `tests/**/README.md` 承担，M1 起补测试计划 |
| IEEE 1016 视图不全 | 算法与资源视图缺失 | 在模块设计中按需补时序图与资源表 |
| ISO 25010 未逐条映射 | 质量属性覆盖不完整 | 在 `docs/matrices/` 增补质量属性映射 |
| 72 小时稳定性未测 | NFR-204 无数据 | 按 `tests/stability/README.md` 执行并归档 |
| V-003/V-004/V-006 未收口 | M0 G4 不能判定通过 | 人工终端取证、SSH 节点验收、预算冻结或 ADR 修订 |
| 无正式发布检查表 | G5 依赖人工核对 | 发布前按 §3.6 逐项留证，必要时新增模板 |
| 并发设计档案尚无范例 | NFR-216 缺少可复用样例 | 首个并发任务按 ADR-015 模板产出并归档 |
| 退出路径无端到端测试 | NFR-218 无法判定 | 在 M1/M2 增加导出—恢复—离线闭环测试 |

| 文档复审日期未逐项登记 | NFR-222 只能部分判定 | 在 M1 起为 ADR/指南补复审字段 |
