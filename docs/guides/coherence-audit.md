# 融洽性审计：形式理论 Γ、模型 M 与三阶段计算

**建立**：2026-11-17（ADR-085） | **强制级**：`pre` 阶段为开工前置门禁；`mid`／`end` 为记录型，连续两个批次无新增反例后硬化 | **判据**：`python .github/scripts/coherence.py`

本文定义一件事：把规则体系当作形式理论，把仓库当作模型，逐条计算哪些条款当前被满足，
把不满足的条款登记成反例。它不把规则说成形式系统，而是把规则中**本来就可判定的那一部分**
抽出来，交给程序判定；不可判定的部分显式登记，不用“门禁全绿”吸收。

## 1. 形式定义

| 符号 | 在本仓库的所指 | 单一事实源 |
|---|---|---|
| Γ | 规则体系：`AGENTS.md`、`specs/**`、`docs/adr/**`、`docs/guides/**` | 各文件原文 |
| γ | Γ 中的一条可判定条款 | `specs/001-whcode-harness/coherence/axioms.toml` 的一个条目 |
| M | 模型：当前工作区的代码、测试、脚本、CI、计数与台账 | 工作区文件与脚本输出 |
| M ⊨ γ | 对 γ 的求值器在当前 M 上返回满足 | `coherence.py` 的 `status = satisfied` |
| 反例 | M ⊭ γ，且不是标记为不可判定的条目 | `specs/001-whcode-harness/coherence/counterexamples.md` |

三点限定（0 信任）：

1. Γ 原文没有形式语义；`axioms.toml` 是**解释层**，一条 γ 的 `source` 字段必须能定位到原文
   的具体节或行，否则视为锚点缺失。
2. M 是工作区快照，不是提交树。工作区与提交树不一致时，报告必须写明 `git rev-parse HEAD`
   与 `git status --short`，不得把工作区结论冒充提交树结论（2026-11-17 已发生一例）。
3. `M ⊨ γ` 只是“程序在当前快照上判为满足”，不等于“条款在语义上被正确执行”。

## 2. 公理体系与条目结构

公理编号沿用 `docs/analysis/software-engineering-logic-sufficiency.md` 的 A1—A9（证据约束、
可证伪、意图预言机、单写者与单层 SQL、资源有界、不伪造、退出权、可修订、角色分离）与
R1—R8 推理规则；另设 M 组元公理，用于审计审计自身。

每个条目字段固定：

```toml
[[axiom]]
id = "COH-A2-01"          # 稳定编号，台账与报告引用它
axiom = "A2"              # 归入的公理或推理规则
statement = "…"           # 一句话，可判定，不写“良好”“基本”
source = "文件 §节"        # Γ 中的锚点，必须能在源文件里逐字定位
tier = "I"                # I 可判定 / III 半可判定 / IV 不可判定
phase = ["pre"]           # 参与哪几个阶段
severity = "hard"         # hard：pre 阶段反例即阻断；soft：只记录
evaluator = "direct:fr_closure"  # direct:* / delegate:* / registered:*
```

`evaluator` 三型：

| 型 | 含义 | 结果来源 |
|---|---|---|
| `direct:<谓词>` | 求值器内实现的解析谓词 | 读文件、解析台账、比对集合 |
| `delegate:<脚本>` | 复用既有门禁 | 子进程退出码（0 满足，非 0 反例） |
| `registered:<理由>` | 不可判定项 | 恒为 `unknown`，必须写补偿控制 |

`tier = "IV"` 的条目只能是 `registered:`，不得有 `direct:` 实现；反之 `tier = "I"` 的条目
不得只写 `registered:`，否则 `COH-M1-*` 元公理判红。

## 3. 三阶段计算

| 阶段 | 时机 | 计算内容 | 门禁强度 |
|---|---|---|---|
| `pre` | 开工前，写认知卡之后、动代码之前 | Γ 自身一致（字段、锚点、台账）＋要求可成立性（FR 闭包、认知卡、手段存在） | 硬阻断：任一 `hard` 反例即退出 1 |
| `mid` | 实现几轮后、批次提交前 | 主路径正向求值 ＋ 反向路径对账 | 记录；`--strict` 可升红 |
| `end` | G4／G5 收口 | 全量重算 ＋ 与 `mid` 报告比对 ＋ 台账收口 | 记录；`--strict` 或台账缺字段即失败 |

命令：

```powershell
python .github/scripts/coherence.py --phase pre
python .github/scripts/coherence.py --phase mid --independent
python .github/scripts/coherence.py --phase end --strict
python .github/scripts/coherence.py --ledger-check
```

报告写入 `artifacts/coherence/run-<phase>-<UTC 时间戳>.json`（默认不入库，属运行证据）。
批次收口时把摘要行与报告路径写进对应 Check 的取证段；要长期留证的报告按 `.gitignore`
放行单个文件，不放行整个目录。

## 4. 反向求值路径（中期的独立性）

同一份工作区事实，两条算法：

1. **主路径**：从 `axioms.toml` 出发，逐条求值；
2. **反向路径**：从产物出发，解析 `checklist.md` 的 Check 条目、`tasks.md` 的任务块与
   `spec.md` 的 FR 行，反推“哪些 FR 被任务覆盖、哪些任务被 Check 覆盖、引用的路径是否存在”，
   再与主路径的同类结论逐条比对。

差异写入报告的 `independent` 段，并作为反例候选。反向路径不读 `axioms.toml`，只读产物，
因此能发现“公理表少登记一条、主路径恰好不查”的漏项；它不能发现两条路径共用的误读。

## 5. 反例台账

位置：`specs/001-whcode-harness/coherence/counterexamples.md`。每条固定字段：

```text
- id：COH-CE-001
- axiom：COH-A2-01
- evidence：复现命令与输出摘要（文件路径＋行号）
- owner：责任角色
- exit：退出条件（可判定的判据，不写“尽快修复”）
- status：open / closed（closed 必须附修复证据的路径）
```

规则：

1. 登记不等于通过；`status = open` 的反例仍是未满足条款。
2. 当前运行出现、台账没有的反例：`pre` 判红；`mid`／`end` 记录并列入报告，下一次 `pre`
   仍会判红。
3. 销号必须指回修复证据；脚本检查 `closed` 条目是否带证据路径。
4. 条目字段缺失即 `COH-M1-03` 反例，按台账自身不合法处理。

## 6. 与 G0—G5 的映射

| 门禁 | 本文落点 |
|---|---|
| G0 立项与范围 | `pre` 阶段检查范围声明、认知卡与手段存在；不通过不得开工 |
| G1 需求基线 | `COH-A2-*`（FR 有任务与 Check）、`COH-R2-*`（追溯闭包） |
| G2 设计基线 | `registered` 条目承接设计优劣与威胁完备；不在本层判定 |
| G3 实现与单测 | `mid` 阶段；批次提交前跑一次，报告路径进入 PR 记录 |
| G4 验收 | `end` 阶段；与 `mid` 报告比对，反例台账收口 |
| G5 发布 | 发布检查表引用最近一次 `end` 报告；报告缺失即登记缺口 |

门禁跳跃仍按 `software-engineering-process.md` §2.2 处理；本文不新增跳跃例外。

## 7. 与 WHCode 产品的关系

FR-794／FR-795 把同一套判定搬进产品：执行前对要求—检查点—手段三元组计算，不通过拒绝执行；
执行中按轮次重算，结束时收口重算。产品侧的判定范围与本文一致：只判可判定片段，语义充分性
恒为 `unknown` 并交给用户确认。

产品实现边界：domain／store／app／turn／Web 已接线（T373—T374）；TUI／GUI 报告面板登记为
预留，反例不自动进入发现台账。未完成部分按任务清单登记，不宣称已交付。

## 8. 正负和解

| 项 | 内容 |
|---|---|
| 正面 | 三元组缺项在开工前暴露；审计结论可复跑；不可判定项显式；反例有台账 |
| 负面 | 公理表成为维护对象；锚点靠文本匹配；`mid`／`end` 默认不阻断；两条路径共享误读；登记项易被当成已处理 |
| 承担者 | 规则修订者同步公理表；批次执行者承担计算时延；用户承担 `pre` 阻断的开工延迟 |
| 和解理由 | 三元组不一致的返工成本高于计算成本，已有两例实测反例；先记录后硬化，避免台账时滞 |

## 9. 复审触发（绑定命令）

1. `python .github/scripts/coherence.py --phase pre` 失败且原因不是规则漂移 ⇒ 复审求值语义。
2. `python .github/scripts/coherence.py --ledger-check` 失败 ⇒ 复审台账字段与销号纪律。
3. 连续两个批次的 `mid`／`end` 报告无新增反例，且人工审计也未发现不一致 ⇒ 复审是否把
   `mid`／`end` 升为硬门禁。
4. 规则源新增无法归入 A1—A9 的硬约束 ⇒ 先改公理体系，再改脚本。
5. 本文一年未被任何批次引用，或用户判定它未改变任何开工决策 ⇒ 降级或删除。

## 10. 已知限制

1. 只覆盖可判定片段；语义充分性不可判定，只登记。
2. `source` 锚点是文本匹配，规则改写会误报；误报按修锚点处理，不得放宽匹配。
3. 反向路径与主路径共享工作区事实，无法发现共同的误读。
4. 报告是运行证据，不是验收结论；平台与性能结论仍按 ADR-013、ADR-037、ADR-025 判定。
5. 产品层 TUI／GUI 报告面板未实现（登记为预留），反例不自动进入发现台账；见 §7。

## 11. 证据充分性补充条目（2026-11-17 合并）

本节把 2026-11-17 公理体系审计的七条缺口并入公理表。编号沿用第 2 节的组：
A1 组承接证据索引、作用域、降级与样本规则；A2 组承接判据充分性与极性；A5 组承接资源预算。
直接判定的条目只在 `mid`／`end` 阶段参与求值且 `severity = "soft"`；存量债务由台账条目持有，
不把 `pre` 阶段变成无法开工的红灯。

1. 证据索引：已勾选的行为或性能类 Check 带 `index=` 或 run／commit 引用。
2. 作用域：预算与平台类 Check 带 `scope=` 作用域元组（OS、三元组、DPI、几何、硬件类、样本量）。
3. 降级：同判据后续反例必须使旧 Check 降级或追加复核记录。
4. 样本：单样本不得支撑全称预算结论，须声明样本量或复测规则。
5. 判据充分：正面 FR 的验收覆盖不得只由负极性 Check 承担。
6. 极性：Check 的极性（positive／negative）可判定且与 FR 极性相容。
7. 资源：资源预算四类占用可测且不静默放宽。

七条中 1、2、5、6 由求值器直接判定；3、4、7 属不可完全判定项，登记为 `registered`，
补偿控制分别是证据态升降级规则、ADR-025 的多样本纪律与 ADR-027／042 的探针复核。
补充满意的判据是：`python .github/scripts/coherence.py --phase mid` 的对应条目转为满足，
且台账中相应条目按退出条件销号。
