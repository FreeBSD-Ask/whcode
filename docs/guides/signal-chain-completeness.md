# 信号链完备原则（Signal Chain Completeness）

**建立**：2026-10-22 | **来源**：T116 复盘——稳定性脚本三次冒烟全 null 被合理化为
"空闲期正确行为"，实际是无被测进程（工作负载缺失）；用户追问后才发现 72h 白跑风险。

## 核心命题

> **交付 = 信号存在，而非执行存在。**

工具跑通、输出格式合法，只是交付的必要条件。输出的数据必须包含**可归因的信号**
（非 null、非空、可追溯到具体被测对象），否则视为未交付。

## 三条原则

### 1. 信号验证（Signal Validation）

null/空/零是**歧义证据**，不是确认证据。必须区分：

| 情形 | 含义 | 处置 |
|---|---|---|
| 正确的空 | 确实没有该数据（如空闲期无事件写入，null 合理） | 记录并继续 |
| **错误的空** | 前置条件缺失（没被测进程、没数据、没环境、没连接） | **= 工具未交付**，须补前置或提问 |

**区分方法**：构造已知有信号的**对照场景**，运行同一工具——对照场景仍空 =
前置缺失（错误的空）；对照场景有信号 = 正确的空。

### 2. 提问义务（Questioning Obligation）

歧义结果无法通过对照场景区分时，**必须提问，不得默认**。

- 提问成本 << 白跑成本（一次提问 1 分钟，72h 白跑 = 4320 分钟）；
- **自主推进不豁免提问义务**——"不问"是缺陷，不是效率；
- 默认操作（把歧义合理化为正确）= 变相伪造验收证据。

### 3. 信号链闭环（Signal Chain Closure）

工具 → 数据 → 结论，每一环都须验证有效：

| 断链 | 表现 | 后果 |
|---|---|---|
| 有工具、无数据 | 脚本运行成功但输出全 null | 白跑（T116 案例） |
| 有数据、无归因 | 输出有值但无法追溯到被测对象 | 不可审计 |
| 有归因、无结论 | 数据不支撑验收判断 | 证据不充分 |

任何一环断裂 = 未交付。

## 工程落点

| 环节 | 落地 |
|---|---|
| 工具交付（G3） | 交付采样/测试工具时**必须**附对照场景验证（已知有信号的场景 + 运行结果非空） |
| 冒烟运行 | 冒烟结果含 null/空/零时，必须在交付记录中**显式归因**（正确的空/错误的空）|
| 长时运行前置 | 72h/24h 等长时任务启动前，须先用短时探针验证信号链完备（10 分钟探针模式） |
| PR 清单 | 新增检查项：工具输出含可归因信号（非 null/非空/非零值——除非正确的空已归因） |
| 提问机制 | 歧义结果无法通过对照场景区分时，交付记录中标注 `[歧义-须提问]` 并停止该工具的验收 |

## 案例记录

**T116（2026-10-22）**：稳定性脚本三次冒烟全 null → 我写"null = 空闲期正确行为"
→ 实际是无被测进程（工作负载缺失）→ 72h 白跑风险存在至用户追问。
修复：脚本加工作负载模式（extreme_scale 循环 = 真实写入/查询/删除负载）+ 
10 分钟探针模式（`STABILITY_PROBE=1`）+ 冒烟归因义务。
