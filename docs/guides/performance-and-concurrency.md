# 性能与并发工程规范

**日期**：2026-10-21 | **依据**：用户决策（ADR-015）、NFR-201—217 | **强制级**：并发实现与汇编优化必须过本规范

本规范处理两个最容易“看起来很快、实际上不可维护”的领域：内存/CPU 优化与多线程并发。
核心规则只有两条：**并发设计先行，绝不原型先行**；**汇编是例外，不是常规手段**。
两条规则都必须接受 0 信任校验与形式主义审查（`docs/guides/philosophy.md`）。

## 1. 适用范围

- 新增或修改线程、任务调度、锁、无锁结构、内存序、共享缓存、异步运行时；
- 任何以“降低内存或 CPU”为目标的优化；
- 任何汇编、SIMD intrinsics、外部 C/ASM 符号或平台专用指令；
- 性能基准、容量规划与资源上限调整。

不适用：单线程纯函数重构、仅文档改动、不改变运行时行为的格式化。

## 2. 并发设计先行（NFR-216）

### 2.1 禁止原型先行

多线程与并发**不得**以“先写个原型跑跑看”为起点。原型先行会把偶然可运行误当成正确性，
把数据竞争、内存序错误与活锁藏到生产环境。设计未通过 G2 前，不得提交生产并发代码。

允许且要求的“先行”活动：

- 纸面分析、状态机与不变量推导；
- 非执行模型（TLA+、Alloy、Petri 网等）；
- 小模型可执行验证（Loom/Shuttle 的模型代码，不算生产原型）；
- 基线测量（只测现状，不实现目标并发设计）。

### 2.2 必读文献门槛

进入设计前必须完成文献研读并留下记录：

1. 至少 3 篇**一手来源**（论文、标准、权威手册，不含二手博客）；
2. 每篇写清：结论、适用条件、与本案的差异、可借鉴的约束、反例或失败条件；
3. 若文献结论互相冲突，必须写明取舍与验证方式；
4. 引用必须可定位（作者、标题、年份、DOI/URL/版本），不得只写“业界通常”。

推荐基线阅读（按设计类型选用，不替代具体检索）：

- Herlihy & Shavit, *The Art of Multiprocessor Programming*：线性化点、进展条件、无锁队列；
- Michael & Scott (1996), *Simple, Fast, and Practical Non-Blocking and Blocking Concurrent Queue Algorithms*；
- Vyukov (2010), bounded MPMC queue：有界队列的序列号与缓存行布局；
- Boehm (2012), *Can Seqlocks Get Along With Programming Language Memory Models?*；
- Batty et al. (2011), *Mathematizing C++ Concurrency*；Wickerson et al. (2017), 内存一致性模型比较；
- Rust Nomicon、`std::sync::atomic` 与 Loom 文档：Rust 内存模型与可执行验证工具。

### 2.3 并发设计档案（G2 必交）

任何并发实现前必须提交档案，字段不得省略：

| 字段 | 要求 |
|---|---|
| 问题与边界 | 并发发生在哪、共享什么、哪些状态不共享 |
| 不变量 | 任何交错下都必须成立的条件，逐条可判定 |
| 线性化点 | 每个操作的原子可见点；无法定义者说明原因 |
| 内存序 | 每个原子操作的 ordering 及理由；不得默认 `SeqCst` 了事 |
| 进展保证 | wait-free/lock-free/blocking 的分类与最坏情况 |
| 数据所有权 | 谁创建、谁释放、谁借用；生命周期如何跨越线程 |
| 失败模式 | 竞争、活锁、饥饿、ABA、伪共享、缓存行抖动、栈溢出 |
| 验证计划 | Loom/Shuttle 模型、压力测试、差分测试、TSAN/其他工具、测量条件 |
| 回退方案 | 出问题时如何退回单线程或更保守实现 |
| 文献依据 | §2.2 的记录与取舍 |
| 复审触发 | 线程数、负载、平台、依赖版本变化时何时重审 |

**完成判据**：档案中的不变量与进展保证可判定、验证计划可执行、回退方案可操作。
不以页数、工时或“设计了一百年”作为完成标准；设计先行不等于无限期分析。

### 2.4 验证

- 小模型优先用 Loom/Shuttle 穷举交错；模型覆盖真实状态机，不用玩具例子代替；
- 压力测试必须记录线程数、数据规模、运行时长与失败复现方式；
- 差分测试：新实现与保守实现（如单线程或粗锁）在同一输入下结果一致；
- 不得以“跑了几小时没崩”作为正确性结论；这是 0 信任原则的直接要求。

## 3. 内存与 CPU 优化（NFR-217）

优化顺序固定，不得跳步：

1. **测量**：固定夹具、记录 OS/硬件/工具链/参数/采样窗口；给出 p50/p95/p99 与资源曲线；
2. **定位**：热点、分配次数、缓存未命中、锁竞争、线程/句柄增长；
3. **建模**：说明瓶颈的机制与预期收益，给出可证伪的假设；
4. **设计**：算法/数据结构层面的替代方案优先于微优化；
5. **实现**：一次只改一个变量，保留可回退提交；
6. **复测**：同夹具前后对比；报告收益、代价与副作用；
7. **归档**：测量条件与结论进入 `artifacts/`，预算变更走 ADR。

禁止：无基线的“优化”、只报平均值不报分位数、把单次样本当结论、以“感觉更快”结项。

### 3.1 DuckDB 索引实测（T036，2026-10-21）

> 本节为 DuckDB 1.5.6 的历史实测；2.0.0 复测见 §3.2，两版结论一致。

固定夹具：单会话 5 万事件 / 2 万消息 / 5 千任务；Windows 11 amd64；DuckDB 1.5.6；
`EXPLAIN` 与 `EXPLAIN ANALYZE` 原文、行数与中位耗时写入
`artifacts/query-plan-report.json`。复现：

```text
cargo test -p whcode-tests --test query_plan -- --ignored --nocapture
```

实测结论（只对上述版本与夹具成立）：

1. **单列 ART 索引**：等值与范围谓词均触发 `Index Scan`（`request_id`、`tool_call_id` 查询）。
2. **复合索引**：`(session_id, seq)`、`(session_id, ts, id)`、`(session_id, stage)` 等
   在本机 1.5.6 上未触发扫描；不能据此断言“复合索引无用”，也不能据此删除——
   data-model.md §3 的逻辑要求仍然成立，收益须由 T054/T055 在大规模数据上复测。
3. **首屏与高命中率查询**：`ORDER BY ... LIMIT` 的首屏、以及命中 33%—50% 的任务过滤，
   顺序扫描（`SEQ_SCAN` + `TOP_N`）是合理计划；§7.2 不要求全表扫描一律失败。
4. **计划文本差异**：优化器 `EXPLAIN` 可能写 `SEQ_SCAN`，而实际执行在
   `EXPLAIN ANALYZE` 中显示 `Type: Index Scan`；判定索引使用以实际执行计划为准。

复审触发：DuckDB 升级、数据规模达到 10 万事件/1 万任务、查询模式变化，或出现新的
索引候选。任何“凭直觉加索引/删索引”的改动一律拒绝（FR-511、TBD-10）。

### 3.2 DuckDB 2.0.0 复测（Task T159，2026-10-24）

同一固定夹具在 DuckDB 2.0.0 + schema v6（`events.payload_json VARIANT`）下复跑，
报告见 `artifacts/query-plan-report-2.0.json`。结论与 1.5.6 一致：2/8 用例
（`request_id`、`tool_call_id`）走索引扫描，6/8 走顺序扫描；复合索引仍未触发扫描，
不得据此删除。`variant_type(payload_json)` 与 VARIANT→JSON 文本投影用例按设计为
顺序扫描（payload 无索引），中位约 1.1 ms / 2.4 ms；VARIANT 化没有把有界游标查询
退化为额外算子。索引集合不变。

### 3.3 写入吞吐观察（2.0.0，2026-10-24）

`whcode bench baseline`（release，192MB、`threads=4`）在 2.0.0 下中位 **4 054.6 条/秒**
（3 次重复；`artifacts/baseline-2.0.json`），仍高于 NFR-210 的 2 000 条/秒门槛，但相对
1.5.6 的 6 921 条/秒下降约 41%。该差异属引擎写路径/提交成本变化，登记为优化观察项；
不得据此放宽预算，也不得把单机样本当作因果结论。

## 4. 汇编例外（ADR-015）

汇编**仅在**同时满足下列条件时允许：

1. 有可复现测量证明确实是热点，且安全 Rust 与算法优化已排除或证明不足；
2. 有独立 ADR 批准（每次使用或每类使用），写明指令集、ABI、平台范围与回退；
3. 代码隔离：优先放入独立 crate（如 `whcode-asm`）或独立模块，**普通 crate 继续保持**
   `unsafe_code = "forbid"`；不得在业务代码中开洞；
4. 安全包装：对外只暴露安全函数，前置条件、对齐、长度、生命周期在包装层校验；
5. 回退路径：非目标架构、禁用 feature 或校验失败时自动走安全实现；
6. 差分测试：汇编路径与安全路径在相同输入下结果一致，覆盖边界与异常输入；
7. 安全评审：越界、未初始化、栈对齐、ABI 不匹配、侧信道与可执行内存风险逐项记录；
8. 可复现构建：汇编器版本、编译参数与产物哈希记录在依赖记录中。

当前项目为 14 个 crate；若批准汇编，新增独立 crate 须同步更新 `test_layering`
的成员列表与 `docs/guides/repository-layout.md`，不得静默扩列。

## 5. 与门禁的对应

| 门禁 | 本规范要求 |
|---|---|
| G0 | 性能/并发目标与资源预算进入范围；写明不做什么 |
| G1 | 每条性能/并发需求有可测判据与证伪条件 |
| G2 | 并发设计档案、文献记录、汇编 ADR 全部就绪，否则不得进入实现 |
| G3 | Loom/模型验证、差分测试、基线对比与回退路径测试 |
| G4 | 0 信任复测：换命令/环境/线程数复核；报告分位数与副作用 |
| G5 | 归档测量条件、复审触发与汇编使用记录 |

## 6. 反形式主义条款

- 设计档案不是文档表演：字段必须能改变实现或验证方案，否则删除该字段；
- 文献研读不是引用堆砌：每篇必须写出“与本案的差异”，否则视为未读；
- “设计一百年”不是无限期拖延：完成判据是**不变量与验证计划可判定**，不是时间长度；
- 汇编不是性能银弹：没有测量与差分测试的汇编优化一律拒绝；
- 本规范自身也要复审：当 Loom/TLA+ 工具链、平台或负载变化时，更新验证方法与门槛。
